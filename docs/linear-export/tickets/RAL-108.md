## The bug

When the AIP source records a line item **directly at a program or project level** (rather than only on leaf activities), the portal **saves the node (ref code + name) but silently drops all its other detail** — amounts, ESRE code, implementing office, schedule, expected outputs, funding source, climate-change.

**Confirmed** in the AIP detail view: the Provincial Legal Office's program/project rows show the name only, every other column blank, even though the source `.xlsm` populated them (e.g. program `1000-000-1-01-011-004` "DISASTER RESILIENT HUMAN RIGHTS AND JUSTICE PROGRAM" carries ₱50,000).

**Re-confirmed by code read 2026-07-21**: `backend/PPDO.Domain/Entities/AipProgram.cs` and `AipProject.cs` still only have `Id`/`RefCode`/`Name` (+`FunctionBand` on Program, added later for an unrelated WFP reason) — no line-item columns exist. Nothing has changed here since this was parked.

## Root cause

`AipProgram` and `AipProject` entities store only `RefCode` + `Name` — there are no columns for amounts or the other line-item fields, so the parser has nowhere to put them.

## Why it matters

* **Data loss on every normal AIP upload** that has this shape — this is a core import bug, not just an API concern.
* **Blocks manual AIP entry** at program/project level ([RAL-62](<https://linear.app/ralphoksiprojects/issue/RAL-62/ui-aip-entry-form-createedit>)) for the same reason — the form has nowhere to persist the detail.
* It also **blocks the program/project-level values in the external GSO API** ([RAL-105](https://linear.app/ralphoksiprojects/issue/RAL-105/external-aip-api-3-external-read-service-dtos-final-only-sector)/[RAL-103](https://linear.app/ralphoksiprojects/issue/RAL-103/epic-external-aip-api-for-gso-phase-2-implementation), Backlog) — the contract reserves the shape but the data isn't captured.

## Two options (both already prototyped once — see stale-branch warning above)

1. **Extend the model** — add the line-item columns to `AipProgram`/`AipProject` (+ parser, DTOs, detail view, WFP grid as needed). Prototyped in old PR [obiken-01/ppdo-portal#95](https://linear.app/ralphoksiprojects/review/fixaip-capture-programproject-level-line-item-detail-on-import-extend-9d9376f1d921) (closed, stale).
2. **Normalize (recommended)** — on import, materialize a program/project-level line item as a **synthetic leaf activity** so amounts always live on activities. Prototyped in old PR [obiken-01/ppdo-portal#94](https://linear.app/ralphoksiprojects/review/fixaip-capture-programproject-level-line-item-detail-on-import-ral-108-49247cc48c5c) (closed, stale). Recommended because WFP can only pull from `AipActivity` rows (`wfp_activities.aip_activity_id`) — the extend approach's program/project-level amounts aren't reachable from WFP without further work (full comparison was in old PR #95's description; re-derive fresh rather than trusting the stale numbers).
