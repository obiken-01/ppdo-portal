# RAL-273 — Modals close when a text selection is dragged from a field out onto the backdrop

**Reported by Ralph with a screen recording (2026-08-20).** On any modal with a text field: click and hold at the end of the field's content, drag the cursor to the start of the field and keep dragging *outside* the modal, then release. The modal closes and the edits are lost.

Recording shows the "Edit Office — GSO" modal (`/config/offices`): `01-015` selected in the AIP Ref Code Suffix field, cursor dragged left onto the backdrop, release → modal gone.

## Root cause — app bug, not browser behaviour

The browser is spec-compliant; the handler is naive. Per the UI Events spec, a `click` event is dispatched at the **nearest common inclusive ancestor of the** `mousedown` **and** `mouseup` **targets** — *not* at the element released over.

`Modal.tsx:71-73` closes on `click` and tests the target:

```tsx
function handleBackdrop(e: React.MouseEvent) {
  if (e.target === backdropRef.current) onClose();
}
```

The panel is a **child** of the backdrop, so a press inside the input and a release on the backdrop resolves to:

* `mousedown` target — the `<input>`
* `mouseup` target — the backdrop
* nearest common ancestor — **the backdrop**
* → `click` fires with `e.target === backdropRef.current` → `onClose()`

This also explains why the `onClick={(e) => e.stopPropagation()}` guards on the other modals' panels do not help: the click never traverses the panel, it originates at the backdrop.

### Second, unreported instance of the same defect

Pressing **on the backdrop** and releasing **inside the panel** also closes the modal today, by the same retargeting. Worth fixing in the same pass.

## Affected — backdrop is an ancestor of the panel

| File | Notes |
| -- | -- |
| `frontend/src/components/ui/Modal.tsx:71` | The shared base — every config Add/Edit form, CSV upload, WFP expenditure entry, AIP manual entry. What the recording shows. |
| `frontend/src/app/(portal)/resource-links/page.tsx:68` | Its own copy of the pattern, via a `data-backdrop` attribute check |
| `frontend/src/app/(portal)/dashboard/page.tsx:183` | Event detail modal, no target check at all. Read-only content so no data loss, but same defect class |

## Not affected

`ConfirmDialog.tsx` and the `Sidebar.tsx` mobile drawer render the overlay as a **sibling leaf element** rather than an ancestor of the panel. A retargeted click lands on their shared wrapper, which is not in the overlay's propagation path, so their handlers never fire. No change needed.

## Fix

Require the gesture to both start and end on the backdrop — track pointer-down rather than trusting `click`:

```tsx
const downOnBackdrop = useRef(false);

function handlePointerDown(e: React.PointerEvent) {
  downOnBackdrop.current = e.target === backdropRef.current;
}

function handlePointerUp(e: React.PointerEvent) {
  const shouldClose = downOnBackdrop.current && e.target === backdropRef.current;
  downOnBackdrop.current = false;
  if (shouldClose) onClose();
}
```

Matches how Radix and Headless UI solve it. Handles both directions:

* down inside → up on backdrop: flag false, no close
* down on backdrop → up inside: `e.target` is the inner element, no close
* down and up both on backdrop: closes, as intended

Escape-to-close and the × button are unaffected.
