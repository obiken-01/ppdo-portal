# RAL-224 — Create PR: clear "PR No. already exists" error instead of generic failure on duplicate submit

## Problem (reported from prod, 2026-08-12)

Ralph uploaded a PDF PR export via the GSO-import prefill on Create PR (parses fine, no issue there), then clicked **Submit**. The submission failed with a generic message and, on a later attempt, a duplicate PR ended up saved without a clear signal that a PR with that number already existed. Not a bug in the parsing/upload — an improvement to the submit error message so a duplicate is unmistakable instead of silently confusing.

## Root cause

`CreatePRInternalAsync` (`backend/PPDO.Application/Services/PurchaseRequestService.cs:249-335`) — the shared core for both the manual Create PR submit and the Excel bulk import — never checks whether `dto.PrNo` already exists before inserting (lines 288-291 use the caller-supplied `PrNo` as-is with zero uniqueness check). The repository already has `GetByPRNoAsync` (`backend/PPDO.Infrastructure/Repositories/PurchaseRequestRepository.cs:35`, interface `backend/PPDO.Domain/Interfaces/IPurchaseRequestRepository.cs:17`) but it is never called anywhere in the service.

The DB does have a unique index on `PRNo` (`backend/PPDO.Infrastructure/Data/Configurations/PurchaseRequestConfiguration.cs:80-83`), so an exact duplicate PR No. does get rejected at `SaveChangesAsync` — but as an **unhandled **`DbUpdateException`, uncaught anywhere in the call chain (no try/catch in the service, no exception middleware in `PPDO.Functions/Program.cs`). That surfaces as an opaque failure, which is what the frontend's generic fallback text papers over:

* Manual submit: `"Failed to submit PR. Please try again."` (`frontend/src/app/(portal)/inventory/create-pr/page.tsx:789`)
* Excel import: `"Import failed. Ensure the file follows the template format."` (`frontend/src/app/(portal)/inventory/create-pr/page.tsx:658`)

Neither message tells the user a PR with that number already exists — so instead of stopping, it's easy to retry with the PR No. field cleared (which triggers `GeneratePRNoAsync` to mint a fresh number) and end up creating a genuine duplicate PR under a new number.

## Fix — existing codebase pattern, not a new one

Every other feature service already guards uniqueness this way before insert (`ItemService.cs:119-122`, `OfficeService.cs:76`, `AccountService.cs:99`, `DivisionService.cs:88`, `FundingSourceService.cs:75`, `PriceIndexService.cs:81`) — `PurchaseRequestService` is the outlier. `ServiceResult<T>.Conflict(...)` already exists and `PurchaseRequestFunctions.ErrorResponse` already maps `ServiceErrorCode.Conflict` → HTTP 409 with a plain-text body (`PurchaseRequestFunctions.cs:373`), which the frontend's existing `err.response?.data` handling already surfaces as-is. **No Functions or frontend changes needed** — this is purely an Application-layer addition.
