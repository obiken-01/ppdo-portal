# RAL-122 — WFP: division-allocation ledger + AIP-budget/allocation ceiling blocking

> 🌿 **Working branch: **`release/1.4.0`. PRs target it, **not **`main`.
> 📌 Read the epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14) first, then `docs/v1.4/WFP_Rework_Requirements_Draft.md` §8 FULLY. Depends on [RAL-120](https://linear.app/ralphoksiprojects/issue/RAL-120/wfp-expenditure-schema-rework-periods-procurement-items-computation) (`wfp_expenditures` totals to sum).
> ✔ **Updated 2026-07-07 (Ralph's answers to open questions #6, #7):** this ticket's scope changed substantially from the original draft. Two changes, both below: **(1)** ceilings are enforced on **every save**, not just Finalize — the UI validates live AND the server rejects on save as a backstop ("Both", confirmed). **(2)** division-allocation remaining is tracked via a **dedicated ledger table linked to** `wfp_records`, not a live SUM query across expenditures ("introduce a new table … linked to wfp_records", confirmed).

## Why

Per the demo: users need to see, live, whether an expenditure's computed total pushes the activity over its AIP budget, or the division over its allocation ceiling — and the system must actually stop them from saving over either ceiling, not just warn.

## Scope

### 1. AIP-budget check (per activity) — unchanged from the original draft

`Σ(wfp_expenditures totals for this activity, across ALL divisions of the office)` vs. `AipActivity.Total × 1000` (⚠ **AIP is stored in thousands, WFP in pesos** — the ×1000 conversion must happen at this comparison boundary, following the existing convention in `AllocationService`'s doc comment: *"AIP totals are in thousands — the ×1000 conversion lives in the [caller] layer only and must never appear here"*).

### 2. Division-allocation ledger — ✔ NEW DESIGN (Ralph, 2026-07-07)

Introduce a dedicated table instead of a live aggregation query:

* `wfp_division_allocation_ledger`: `id, division_id, fiscal_year, wfp_record_id (FK), allocated_amount_snapshot (DivisionAllocation.Amount at the time this WFP started drawing against it), used_amount (this WFP record's current total draw), updated_at`.
* One row per `(division_id, fiscal_year, wfp_record_id)` — recomputed/upserted whenever that WFP record's expenditure totals change (on every expenditure save/update/delete).
* **Remaining allocation** = `DivisionAllocation.Amount` (current config value) `− Σ(used_amount across all ledger rows for that division+FY)` — now an O(1)-ish read against a small ledger table instead of aggregating across every expenditure/period row.
* This also gives a foundation for "other consumers" (raised in Ralph's answer) to post their own ledger rows later, tagged by `wfp_record_id` for now — do not over-engineer a generic polymorphic consumer type in this ticket; keep it WFP-scoped, but name the table/columns so it's obviously extensible (e.g. don't call it `wfp_only_ledger`).

### 3. Ceiling enforcement — ✔ CHANGED FROM "warn-on-save" TO "block on save AND Finalize" (Ralph, 2026-07-07)

* **Server-side:** the expenditure SAVE path ([RAL-120](https://linear.app/ralphoksiprojects/issue/RAL-120/wfp-expenditure-schema-rework-periods-procurement-items-computation)'s pipeline, not just `FinalizeAsync`) rejects (BadRequest) any save that would push either ceiling over its limit. This is a change to [RAL-120](https://linear.app/ralphoksiprojects/issue/RAL-120/wfp-expenditure-schema-rework-periods-procurement-items-computation)'s save endpoint — coordinate with whoever implements it, or implement both together if [RAL-120](https://linear.app/ralphoksiprojects/issue/RAL-120/wfp-expenditure-schema-rework-periods-procurement-items-computation) hasn't landed yet.
* **Client-side (ticket** [RAL-123](https://linear.app/ralphoksiprojects/issue/RAL-123/wfp-entry-ui-context-picker-expenditure-wizard-shell) **consumes this):** expose a live-check endpoint the wizard UI calls before/while the user types, so the Save button can be disabled BEFORE a rejected save round-trip — this is UX polish on top of the server-side rejection, not a replacement for it.
* `FinalizeAsync` keeps its own ceiling check too (belt-and-suspenders — a record shouldn't reach Final with any expenditure over ceiling, though if every save is already blocked this should never actually trigger).

### 4. Endpoint

`GET /api/budget-planning/wfp/ceilings?activityId=&divisionId=&fiscalYear=` returning `{ aipBudget, aipUsed, divisionAllocation, divisionRemaining }` — used by both the live client-side check and the save-time server check (same underlying computation, don't duplicate it).

## Acceptance Criteria

- [ ] `wfp_division_allocation_ledger` table exists, one row per `(division_id, fiscal_year, wfp_record_id)`, upserted whenever that record's expenditure totals change
- [ ] "Remaining division allocation" reads from the ledger, not a live aggregation across `wfp_expenditures`
- [ ] ×1000 conversion happens exactly once, at the AIP/WFP comparison boundary, matching `AllocationService`'s existing units discipline
- [ ] Saving ANY expenditure (Draft or otherwise) that would exceed either ceiling is **rejected** by the server, not just warned
- [ ] `FinalizeAsync` still independently checks both ceilings as a backstop
- [ ] The ceiling-check endpoint is shared by both the live client-side validation and the server-side save rejection — one computation, two callers
- [ ] Unit tests: under both ceilings (save succeeds), over AIP only (rejected), over allocation only (rejected), over both (rejected), exactly at the boundary (not a false rejection), ledger row correctly upserts as expenditure totals change
