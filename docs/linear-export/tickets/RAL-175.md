# RAL-175 — [bug] Dashboard calendar: row height inconsistent and Saturday events clipped on heavily-populated months

> 🐛 Found live by Ralph 2026-07-21 on the production Main Dashboard calendar (`/dashboard`). Standalone Dashboard/Calendar fix, same family as [RAL-173](<https://linear.app/ralphoksiprojects/issue/RAL-173/bug-dashboard-calendar-multi-day-events-render-one-day-short>) — not part of the WFP Rework epic ([RAL-116](<https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14>)), no parent.
> 📌 Frontend-only, investigation ticket — root cause below is a hypothesis to confirm, not a confirmed fix.

## Symptoms (screenshot: July 2026 month view, heavily populated)

1. **Week-row height is wildly inconsistent across the month.** Weeks with few events (e.g. Jul 5–11: one bar + two "Budget Forum" entries) render short; weeks with many events spread across different days (e.g. Jul 19–25: multiple 1–3-event days plus two multi-day bars) render dramatically taller. The month grid ends up visually lopsided instead of a uniform grid, and pushes the rest of the dashboard content down unpredictably.
2. **Events are not properly displayed in the Saturday column.** Event bars/titles in the rightmost (Saturday) column appear cut off (e.g. "Tree Planting @ DA Breed[ding Ground]", "Pickleball Tournament @[...]") in a way that looks like clipping, not just normal text truncation.

## Why (root cause hypotheses — confirm before implementing)

`frontend/src/components/dashboard/DashboardCalendar.tsx`:

* **Row height**: the calendar is rendered with `height="auto"` and `dayMaxEvents={3}` (line ~164-165). `dayMaxEvents` caps events *per day cell* (showing capped events + a "+N more" link once a cell overflows), but does **not** equalize row height across the 7 columns — a week's row height is the max of whatever any single column needs that week. With `height="auto"`, FullCalendar has no fixed per-row cap, so weeks with several different days each holding 2-3 stacked events (rather than one busy day) compound into a much taller row than a week where the same event count is concentrated in one day. Needs to be confirmed against FullCalendar's dayGrid row-sizing behavior — possible fixes include a fixed `dayMaxEventRows` value uniform across all weeks, or switching away from `height="auto"` to a fixed height with internal scrolling per week.
* **Saturday clipping**: the calendar's outer wrapper div has `overflow-hidden` (`DashboardCalendar.tsx:129`). If FullCalendar's internally-rendered table width doesn't land exactly on the container's content-box width (rounding, borders, or the calendar competing for space with the Resource Links sidebar on the same dashboard row — see the two-column dashboard layout), the last (Saturday) column's content could be getting visually clipped by that `overflow-hidden` rather than legitimately truncated. Needs to be confirmed by inspecting the rendered DOM/computed widths in a browser at the actual dashboard viewport width (not full-width), and checking whether the clipping persists with `overflow-hidden` removed or the sidebar not present.

## Investigation steps

1. Reproduce on a month with a similarly dense event spread (or seed test events) at the actual portal viewport width (dashboard has a fixed-width Resource Links sidebar competing for horizontal space — reproduce with it present, not in a maximized/isolated calendar).
2. Confirm/rule out the `dayMaxEvents` + `height="auto"` row-sizing hypothesis above; check FullCalendar docs/changelog for `dayMaxEventRows` vs `dayMaxEvents` and whether a fixed value produces uniform row heights.
3. Confirm/rule out the `overflow-hidden` clipping hypothesis on the Saturday column specifically — measure the rendered Saturday `<td>` width vs the other day columns and vs the container.
4. Check `frontend/src/app/globals.css` `.fc-ppdo` rules (lines ~155-228) for any width/overflow rule that could compound the issue.
