# RAL-254 — Security: admin reset sets a random password + forces a change, not the shared default

**V18-26** — plan: `docs/v1.8/Phase_Plan.md` §3.4. Security finding, found while designing the reset flow — `AIP_Requirements_Review.md` §2.2.

`UserService.ResetPasswordAsync` (and `CreateAsync`) sets **every** account to the same hardcoded default, `TamarawUser2026!`, and **nothing forces the user to change it**. There is no `MustChangePassword` flag anywhere. That password is also written down in `CLAUDE.md`, and usernames are guessable.

So today any reset account sits indefinitely on a known, documented password — for a system holding provincial budget data.

**Scope:**

* Generate a **random** temporary password per reset/creation; show it once to the admin to relay.
* Set `MustChangePassword` (schema from V18-22) and gate the portal on it: the user lands on Change Password and cannot navigate away until it is changed.
* Remove the shared default from `CLAUDE.md` and anywhere else it is documented.
* Audit the reset (V18-07).

⚠️ Independent of the rest of the reset cluster and worth shipping first — it is live in production today. Existing accounts still on the default should be flagged `MustChangePassword` in the same migration.

**Done when:** no code path can produce a predictable password, and an account that was reset cannot be used without changing it.
