# RAL-203 — Auth: add timeout to /auth/refresh calls so cold-start failures reach /reconnecting instead of hanging

## Symptom

Reported live by Ralph: idle in prod for 30+ minutes, then returned to the tab expecting either the [RAL-198](https://linear.app/ralphoksiprojects/issue/RAL-198/auth-explain-unexpected-logout-instead-of-silently-bouncing-to-login) `/login?reason=...` warning banner or the [RAL-199](https://linear.app/ralphoksiprojects/issue/RAL-199/auth-recover-from-cold-start-refresh-failures-instead-of-forcing) `/reconnecting` cold-start page. Neither appeared — the tab just showed no feedback.

## Root cause

None of the three `POST /auth/refresh` call sites set an axios `timeout`:

* `frontend/src/lib/api.ts` (response interceptor's silent-refresh call)
* `frontend/src/app/(portal)/layout.tsx` (portal auth guard's mount-time refresh call)
* `frontend/src/app/(public)/reconnecting/page.tsx` (the reconnecting page's own retry loop)

`classifyRefreshFailure`'s `isNetworkError` check (`frontend/src/lib/auth-redirect.ts`) only runs inside a `.catch()`. When Azure Functions is cold (Consumption plan scales to zero after ~10 min of no traffic) or Azure SQL Free has auto-paused (~1 hr), a slow-but-eventually-successful response never rejects the axios promise — it just hangs. So the request sits pending indefinitely and the app never reaches the `/reconnecting` redirect that [RAL-199](https://linear.app/ralphoksiprojects/issue/RAL-199/auth-recover-from-cold-start-refresh-failures-instead-of-forcing) built specifically for this case. From the user's perspective the tab looks frozen/broken with zero explanation.

## Fix

Added a shared `REFRESH_TIMEOUT_MS = 20_000` constant in `lib/auth-redirect.ts` (kept below the existing `/health` check's 30s timeout) and applied it to all three `/auth/refresh` axios calls above. A stuck cold start now rejects within a bounded time, gets classified as `"unreachable"`, and correctly routes through the existing `/reconnecting` retry-with-backoff flow instead of hanging silently forever.

## Note

The classification (`!error.response`) can't actually distinguish "cold start" from other no-response causes (client offline, DNS/CORS/firewall block) — the `/reconnecting` copy is deliberately hedged ("**may be** waking up") rather than asserting cold start specifically. Not changed as part of this ticket; flagged for awareness only.
