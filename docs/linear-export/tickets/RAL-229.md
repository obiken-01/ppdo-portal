# RAL-229 — Clamp GET /budget-planning/dashboard/office to the caller's own office (IDOR)

🔴 Critical — an insecure direct object reference. Any Budget Planning user can read any office's dashboard by changing one query parameter.

## Context — read first

* `docs/v1.8/Office_User_Path_Findings.md` §3.3 (this bug) and §4 (the pattern to copy)
* `backend/PPDO.Functions/Functions/BudgetPlanningDashboardFunctions.cs` — the affected handler
* `backend/PPDO.Functions/Functions/WfpReportFunctions.cs` — the [RAL-136](https://linear.app/ralphoksiprojects/issue/RAL-136/wfp-report-preview-division-scope-for-non-finance-users-finance-sees) division clamp, the closest existing precedent in the same feature area
* `CLAUDE.md`, `docs/TEST_CONVENTIONS.md`

## Problem

`GET /api/budget-planning/dashboard/office` reads `officeId` straight from the query string after only a `CanAccessBudgetPlanning` check:

```csharp
(_, HttpResponseData? denied) = await ConfigHttp.AuthorizeAsync(
    req, _jwt, u => _permissions.CanAccessBudgetPlanningAsync(u), cancellationToken);
if (denied is not null) return denied;

if (!int.TryParse(req.Query["officeId"], out int officeId) || ...)

OfficeDashboardDto result = await _service.GetOfficeDashboardAsync(officeId, fiscalYear, ct);
```

Note the discarded caller (`(_, ...)`) — the handler never looks at who is asking. Any authenticated Budget Planning user, PPDO or office, can read any office's readiness data.

This leaks in **both** directions between offices, and it is live today. It is only not yet exploitable in production because no office-user accounts exist.

The sibling endpoint on the same class already gets this right for divisions — `GetDashboard` clamps `divisionId` server-side and deliberately exposes no client-supplied division param at all. The office dimension was simply never given the same treatment.

## Steps

1. **Capture the caller** — stop discarding it in the `AuthorizeAsync` destructure.
2. **Clamp** `officeId` **to the caller's own office** using the helper from the `OfficeScope` ticket:
   * Office user → always their own office, whatever the query string says. **Clamp, do not reject** — consistent with `LdipFunctions`' clamp-on-write and with `WfpReportFunctions`' division clamp, both of which silently substitute rather than 403. No error path to get wrong, and no way to probe for valid office ids by watching which ones 403.
   * PPDO user → the requested `officeId` passes through unchanged. Cross-office visibility is legitimate for PPDO; this ticket does not restrict it.
3. **Add a header comment** on the handler in the same style as `GetDashboard`'s existing [RAL-161](https://linear.app/ralphoksiprojects/issue/RAL-161/budget-planning-dashboard-rework-ppdo-scoped-queries-per-divisionfund) note, so the next reader sees the clamp is deliberate and does not "simplify" it away.
4. **Tests** in `PPDO.Tests/Functions/`:
   * Office user requesting **another** office's id → receives their own office's data, not the requested one.
   * Office user requesting **their own** id → unchanged behaviour.
   * PPDO user requesting any office id → passes through unchanged.
   * Missing/malformed `officeId` → still a clean 400 (do not regress the existing validation).
5. **Check for sibling exposure before closing. **`GetRecentActivity` on the same class also takes an optional `officeId` query param (`GET /api/budget-planning/activity?officeId=`). Verify whether it needs the same clamp and fix it here if so — it is the same class, the same dimension, and the same one-line omission.
