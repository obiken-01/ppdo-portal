# RAL-233 — Price index management grid: server-side pagination + server-side sort

Follow-up to [RAL-232](https://linear.app/ralphoksiprojects/issue/RAL-232/price-index-slim-the-list-payload-157-mb-and-stop-the-config-dashboard), flagged as out of scope there. `docs/PERFORMANCE_GUIDELINES.md` recommends server-side pagination for tables that grow; the price-index catalogue is 6,397 rows and is the largest single-page table list in the app.

## Context — read first

* `docs/PERFORMANCE_GUIDELINES.md`
* `frontend/src/components/ui/DataTable.tsx` — the `serverPagination` prop, already built and already used
* `frontend/src/app/(portal)/config/audit-log/page.tsx` — the sibling config page using it; the pattern to copy
* `frontend/src/app/(portal)/inventory/pr-register/page.tsx` — server-side **sort**, the other half this ticket needs (raw TanStack `manualPagination`/`manualSorting`, not `DataTable` — different mechanism, same idea)
* `backend/PPDO.Infrastructure/Repositories/AuditRepository.cs:GetPagedAsync` — the backend template
* `backend/PPDO.Infrastructure/Repositories/PriceIndexItemRepository.cs` — has `Filtered()` ([RAL-232](https://linear.app/ralphoksiprojects/issue/RAL-232/price-index-slim-the-list-payload-157-mb-and-stop-the-config-dashboard)) to build this on
* `frontend/src/app/(portal)/config/price-index/page.tsx`
* `CLAUDE.md`, `docs/TEST_CONVENTIONS.md`

## Why this is smaller than a typical pagination retrofit

The price-index management page already uses the shared `DataTable` component, and `DataTable` already has a `serverPagination` prop (`{ page, pageSize, totalCount, onPageChange }`) built for `config/audit-log` — the identical component, in the same Config section. This is not a from-scratch pagination build; it's the audit-log pattern applied to a second page. The real work is backend.

## ⚠️ The sort trap — read this before touching the frontend

`DataTable`'s own doc comment on `serverPagination`:

> Client-side sorting is still applied, but only within the current page — pair with non-sortable columns (or server-side sort params) for large/unbounded tables.

The price-index grid currently has **all nine columns sortable** (Name↕, Unit↕, Stock Card No.↕, Category↕, Unit Price↕, Price Updated↕, Days Field↕, Status↕). Turning on `serverPagination` without also pushing sort server-side would silently change "sort all 6,397 rows by price" into "sort the 50 rows on this page by price" — it keeps working, looks identical, and returns wrong results. That is worse than no pagination at all.

**Decision for this ticket: push sort server-side too**, following `pr-register`'s precedent ([RAL-192](https://linear.app/ralphoksiprojects/issue/RAL-192/inventoryservice-scoped-queries-list-pagination)) rather than removing sortability from the grid.

## Backend

1. `IPriceIndexItemRepository.GetPagedAsync(bool? isActive, string? search, string? sortColumn, bool descending, int page, int pageSize, ct)` returning `(IReadOnlyList<PriceIndexItem> Rows, int TotalCount)` — built on the `Filtered()` helper from [RAL-232](https://linear.app/ralphoksiprojects/issue/RAL-232/price-index-slim-the-list-payload-157-mb-and-stop-the-config-dashboard) so the WHERE can never drift from the count/list/picker reads that already share it.
2. Whitelist sortable columns explicitly (don't accept an arbitrary string into `OrderBy`) — mirror whatever guard `pr-register`'s dynamic sort-key selector already uses; do not invent a new pattern if one exists.
3. `PriceIndexService.GetPagedAsync` + a `PagedResult<PriceIndexItemDto>`-shaped DTO — check whether `AuditLog`'s or `PurchaseRequestSearch`'s paged response shape is already generic/reusable before defining a new one.
4. New endpoint, e.g. `GET /api/config/price-index/paged?...` (or extend `List` with page/pageSize/sortColumn/sortDescending params if that fits the existing convention better — check how `pr-register`'s search endpoint decided this).
5. Tests per `docs/TEST_CONVENTIONS.md`: page/pageSize honored, total count correct under a filter, each whitelisted sort column produces correct order, an unknown sort column doesn't 500 or open a SQL-injection surface.

## Frontend

1. `page`/`totalCount` state on `config/price-index/page.tsx`, `serverPagination` prop wired to `DataTable`, matching `audit-log`'s pattern.
2. Sort state (`sortColumn`, `sortDescending`) passed to the fetch; reset `page` to 1 whenever a filter OR sort changes (audit-log already does this for filters — extend it to sort).
3. Confirm the CSV export path (`GET /api/config/price-index/csv`) is unaffected — it must still export everything, not just the current page.

## Verify live

* Sort a column, confirm it changes on data outside the current page (not just the visible 50 rows) — the exact failure mode this ticket exists to prevent.
* Page through with an active search/status filter applied; confirm total count matches the filter.
* CSV export still produces the full catalogue.

## Out of scope

Anything to the price-index import/CSV-upsert flow — unrelated to read-side pagination.
