# RAL-204 — Fix two SQL anti-patterns: non-SARGable user lookups + WfpService N+1 count

Two real instances of well-known SQL anti-patterns found in an audit of the backend. Both are invisible at current data volumes; both are wrong patterns that get copied.

## 1. `LOWER()` on indexed columns defeats the index (non-SARGable predicate)

`backend/PPDO.Infrastructure/Repositories/UserRepository.cs:24` and `:34`

```csharp
u => u.Username.ToLower() == username.ToLower() && u.IsActive
u => u.Email != null && u.Email.ToLower() == email.ToLower() && u.IsActive
```

EF Core translates these to `WHERE LOWER(username) = @p`. Wrapping the column in a function makes the predicate non-SARGable, so SQL Server cannot seek `IX_Users_Username` / `IX_Users_Email` (both defined and unique in `UserConfiguration.cs:64` and `:70`) — it scans instead.

The `ToLower()` is also **redundant**: Azure SQL and local SQL Server Express both default to a case-insensitive collation (`SQL_Latin1_General_CP1_CI_AS`), so a plain `==` comparison is already case-insensitive.

**Fix:** drop `.ToLower()` from both sides on both methods. This is on the login hot path (`FindByUsernameAsync`).

**Verify before merging:** confirm the DB collation really is case-insensitive — if it were case-sensitive, removing `ToLower()` would change login behaviour.

```sql
SELECT DATABASEPROPERTYEX('PPDOPortalDev', 'Collation');
```

## 2. N+1 query that also loads full rows only to count them

`backend/PPDO.Application/Services/WfpService.cs:419-421`

```csharp
int expenditureCount = 0;
foreach (WfpActivity activity in activities)
    expenditureCount += (await _expenditureRepo.GetByWfpActivityIdAsync(activity.Id, ct)).Count;
```

Two violations of `docs/PERFORMANCE_GUIDELINES.md` §1 in three lines: one round trip per activity, and each round trip materialises full `WfpExpenditure` entities purely to read `.Count`.

**Fix:** add `IWfpExpenditureRepository.CountByWfpActivityIdsAsync(IReadOnlyList<int> activityIds, CancellationToken ct)` — a single `CountAsync` with a `WHERE wfp_activity_id IN (...)`. Mirrors the existing `GetLinesByActivityIdsAsync` batch shape used two lines below it, so the call site becomes symmetric.

Caller is `WfpService.CleanupScopedAsync` (the dev-only scoped reset tool), so blast radius is small.

## Explicitly out of scope

Found in the same audit, deliberately not included:

* `WfpCeilingService.cs:170` — `(await _divisionRepo.GetAllAsync(ct)).FirstOrDefault(d => d.Id == divisionId)`, a §1 violation. Needs a division by-id repo method; separate ticket.
* `WfpCeilingService.cs:215` — `GetActivityByIdAsync` per distinct AIP activity id (N+1).
* `AipService.cs:699`/`:712` and `LdipService.cs:69` — one `GetOfficeGroupsAsync` per record. These are **deliberate** and carry a comment saying so ("list is small: one doc per office per planning period"). Leave them.

## Non-findings worth recording

The many `foreach … await _repo.AddAsync/DeleteAsync` loops across the Application services are **not** N+1. `Repository<T>.AddAsync`/`DeleteAsync` (`Repository.cs:35`, `:47`) only touch the EF change tracker; the service owns the single `SaveChangesAsync`. That is correct EF batching — do not "fix" it.

## Context

On the current Azure tier, cold start and SQL auto-resume dominate perceived latency (`docs/PERFORMANCE_GUIDELINES.md` §8). Neither fix will be felt by users. The payoff is vCore-seconds and not propagating bad patterns into new code.

## Testing

Backend suite must stay green (`cd backend && dotnet test`). Add a regression test asserting `CountByWfpActivityIdsAsync` is called once, not once per activity.
