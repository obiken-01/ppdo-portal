# RAL-207 — Transaction boundary for multi-save operations + EF transient-fault retry

Two halves of one underlying problem: **the data layer assumes a database that is always awake and never fails mid-operation.** Neither is true on this Azure tier. Found while assessing a backend-architecture post against our code (the "Saga pattern" slide — Saga itself is wrong for us, since we have one database and real ACID transactions available; the useful question it raised was whether we actually *use* them. We don't.)

## Part 1 — Bulk stock-balance import can commit partially

`backend/PPDO.Application/Services/StockBalanceService.cs:342-409` (`CommitImportAsync`) calls `SaveChangesAsync` **inside** the row loop:

```csharp
foreach (CreateStockBalanceDto row in dto.Rows)
{
    // ... validate, upsert, compute variance ...
    await _stockBalances.SaveChangesAsync(cancellationToken);   // line 378 / 404
    await _audit.LogAsync(...);
}
```

There is no enclosing transaction, so a failure at row *n* leaves rows `1..n-1` committed and returns an error to the caller. The user sees "Import commit failed", reasonably concludes nothing was saved, and moves on — while half the file is live.

**The per-row save is correct and must stay.** The comment at line 376 explains why: each row must be flushed before the next row's `ComputeSystemOnHandAsync` runs, so multiple rows for the same StockNo in one file stack correctly. Do **not** "fix" this by batching the saves — that would break the running-total semantics. Wrapping the loop in a transaction preserves the per-row flush (reads inside a transaction see its own uncommitted writes) *and* makes the file atomic. One change buys both.

### Severity notes — read before prioritising

Lower than it first appears:

* The frontend previews first and filters invalid rows before committing (`stock-balances/page.tsx:328` — `previewRows.filter((r) => !r.error)`), so the bad-data trigger is largely already handled. The in-loop `Validate()` is a defensive re-check.
* The upsert key is StockNo + EffectiveDate, so re-uploading the same file overwrites rather than duplicates. A user who retries heals the partial state without realising.

Still real:

* The live trigger is **infrastructure failure mid-loop**, not bad data — Function timeout, Azure SQL auto-resume stall, dropped connection. Each row costs a find + a save + a system-on-hand computation + an audit write, so a 50-row file is 200+ round trips against a database that may be resuming from auto-pause.
* The failure is **silent**, and `stock_balances` has no approval step (flagged in [RAL-200](https://linear.app/ralphoksiprojects/issue/RAL-200/api-audit-trail-logging-for-inventory-prs-deliveries-distributions)) — wrong computed on-hand values sit there unnoticed.

## Part 2 — No transient-fault retry in EF

`backend/PPDO.Functions/Program.cs:85` is a bare `options.UseSqlServer(connectionString)` — no `EnableRetryOnFailure`. Against a database that auto-pauses after ~1 hr (`docs/PERFORMANCE_GUIDELINES.md` §8), EF has zero retry on transient faults. We mitigate at the edges only: the `GET /api/health` pre-warm on the login page, and `callWithRetry` in the frontend's `api.ts` / auth guard. Nothing at the data layer.

This directly raises the probability of Part 1's trigger.

**Ordering gotcha:** with no retry configured today, a manual transaction works normally. **Once** `EnableRetryOnFailure` **is enabled, manual transactions must be wrapped in** `Database.CreateExecutionStrategy().ExecuteAsync(...)` **or EF throws.** So either do Part 1 first and adjust when Part 2 lands, or do Part 2 first and write Part 1 against the execution strategy from the start. Don't do them in parallel on separate branches.

## The architectural decision this needs

`IRepository<T>` (`backend/PPDO.Domain/Interfaces/IRepository.cs`) has **no transaction concept** — only `SaveChangesAsync`. CLAUDE.md forbids using `AppDbContext` outside repositories, so this can't be fixed locally in the service. Options:

1. Add `BeginTransactionAsync()` to `IRepository<T>` returning an abstraction over `IDbContextTransaction`.
2. Introduce a separate `IUnitOfWork` abstraction that services depend on for multi-step writes.
3. Keep it narrow — a single `ExecuteInTransactionAsync(Func<Task>)` method on the repository, used only where needed.

Option 3 is the smallest change and the easiest to not misuse. **Whatever is chosen becomes a codebase convention — decide deliberately and document it in CLAUDE.md.**

## Also worth checking (not confirmed)

`AipService.CopyOfficeFromPriorYearAsync` (saves at lines 517, 601, 612) and `SeedProgramsFromLdipAsync` (758, 805, 814) have the same three-saves-in-one-method shape. I read the line positions but did **not** trace whether private helpers sit between them — verify before assuming they're affected.

For contrast, `AipService.ConfirmImportAsync` gets this right today (line 310: "single transaction — all-or-nothing") by deferring to a single `SaveChangesAsync`. That approach works when one save is possible; the import loop is the case where it isn't.

## Out of scope

Distributed-systems patterns (Saga, event sourcing, compensating actions). We have one database with real transactions — the fix is a transaction, not a saga.
