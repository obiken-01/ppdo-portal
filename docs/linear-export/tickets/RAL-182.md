# RAL-182 — Audit Log: auto-refresh grid (focus + 15-min poll) with opt-in background polling toggle

**Frontend-only.** Keep the Audit Log grid fresh without a manual reload, so a SuperAdmin who leaves the tab and comes back sees current data. Rides along in the v1.5 release; unrelated to the PPMP-report theme.

Page: `frontend/src/app/(portal)/config/audit-log/page.tsx` (SuperAdmin-only, route `/config/audit-log`). It already has a `load()` callback that refetches the current page + filters from `GET /api/config/audit-log`. This ticket just calls `load()` on new triggers, silently. **No backend change.**

## Behaviour (agreed with Ralph)

Two triggers, split by role:

1. **Refetch when the tab becomes visible** (`document.visibilitychange` → visible, and/or `window.focus`). This is what actually delivers "fresh the moment I come back" — a blind interval can't, since you'd see up-to-15-min-stale data until the next tick.
2. **15-minute interval while the tab is visible** — the steady "update while I'm watching it" heartbeat, and it keeps the backend warm during active use.

Default = **visible-only**: when the tab is hidden, no interval runs (an idle background tab costs nothing; the visibility-refetch covers the return case). The one downside — the return may hit a ~10–30s Azure cold start (Functions scale to zero ~10 min, SQL auto-pauses ~1 hr) — is already tolerated elsewhere in the app via `callWithRetry`.

3. **Opt-in background-polling toggle.** Add a small on/off control on the page ("Background refresh" / "Keep refreshing when tab is hidden"). When **on**, the 15-min interval *also* runs while the tab is hidden — keeping Functions + SQL warm so the return is instant, at the cost of the backend never sleeping while that tab is open. Default **off**. Persist the choice in `localStorage` so it survives reloads, and show a clear indicator when it's on (the user is deliberately keeping the server warm).

The refresh must be **silent**: do not toggle the page's main `loading` skeleton, do not reset scroll or jump the page/filter. Show a subtle "Updated h:mm:ss AM/PM" line (and/or a spinner on the toggle) so it's visibly live. Preserve the current page number, filters, and sort exactly — `load()` already reads them from state, so just call it.

## Steps

1. Extract a `refresh({ silent })` wrapper around the existing fetch: `silent` refetches without `setLoading(true)` and without clearing the grid, so the visible rows never flash. Keep the initial/filter-driven load non-silent.
2. Add a 15-min interval that calls `refresh({ silent: true })`. Gate it: run while `document.visibilityState === "visible"`, OR always when the background-toggle is on. Re-evaluate on `visibilitychange`. Clear the interval on unmount and when a manual load supersedes it.
3. Add a `visibilitychange`/`focus` listener that calls `refresh({ silent: true })` when the tab becomes visible (skip if a load is already in flight).
4. Add the background-refresh toggle: `localStorage`-persisted boolean, default off, with an on-state indicator. When on, the interval keeps running while hidden.
5. Add a small "Updated {time}" indicator, set on each successful refresh.
6. Guard against overlap: never run two fetches at once (an in-flight ref/flag); a filter/page change should cancel-and-supersede a pending silent refresh, not race it.

## Out of scope / Do NOT

* No backend change — the endpoint, service, DTO, and pagination stay as-is.
* Do NOT introduce a websocket/SSE or a real-time push layer — simple polling only.
* Do NOT auto-advance or reorder the grid under the user (e.g. don't yank them to page 1 when new rows land) — refetch the *current* view in place.
* Do NOT make the interval configurable in this ticket — 15 min is fixed. (A future ticket can expose it if wanted.)
* Do NOT poll while hidden unless the toggle is explicitly on.
