# RAL-178 — AIP: allow re-uploading a corrected file into an existing AIP record

> 🔧 **Follow-up fix, 2026-07-21 (same PR #175, pushed after the ticket was already Done):** manual testing found that re-uploading into a Draft AIP whose activities were already referenced by a WFP failed. `wfp_activities.aip_activity_id` is `DeleteBehavior.Restrict` against `aip_activities` — the replace's delete-then-reinsert cascades through `AipOffice → AipProgram → AipProject → AipActivity`, and the DB rejected the delete once real WFP rows pointed at those activities. That threw an unhandled exception, surfaced to the user as a generic "Confirm failed." Fixed by:
>
> * `IWfpRepository.AnyForAipRecordAsync(aipRecordId)` — new scoped existence check.
> * `AipService.ReplaceImportAsync` now calls it before touching the hierarchy and returns a clean `400` ("Cannot re-upload — a Work Financial Plan has already been built from this AIP...") instead of crashing.
> * `AipRecordDetailDto.HasWfpUsage` (new field, populated in `GetByIdAsync`) — the frontend detail page uses it to hide/disable the "Re-upload File" button up front, with an inline amber explanation, so the user never hits the error.
> * 4 new unit tests in `AipServiceTests.cs` (guard rejection + both `HasWfpUsage` states). Verified live against a real Draft AIP with 39 linked `wfp_activities` rows — confirmed the original 500 is gone, the button is hidden, and the AIP's own data was untouched by the earlier failed attempt (EF's implicit transaction rolled back cleanly).
>
> Net effect: once a WFP is built from an AIP, that AIP can no longer be re-uploaded — only Archive + fresh upload (loses lineage) or the future Amendment/Supplemental copy flow ([RAL-78](<https://linear.app/ralphoksiprojects/issue/RAL-78/feature-amendmentsupplemental-copy-flow-finalizeunlock-transitions>)) will be able to correct it going forward.

## 0. Why this exists

Confirmed by code read: once an AIP is uploaded, there is **no way to correct it**. `IAipService`/`AipFunctions` expose List/Get/Upload+Preview/ConfirmImport/Finalize/Unlock/Archive and two single-field updates (program `FunctionBand`, activity `IsCreation`) — nothing else. `aip/detail/page.tsx` is explicitly documented as a **read-only** view. If PPDO finds a mistake after uploading (a typo, a wrong amount, an unmatched funding source), today's only option is Archive-and-re-upload-as-a-brand-new-record — different `Id`/`RefCode`, no continuity, and the Archived original still consumes a WFP-blocking slot if anything already referenced it.

LDIP hit the exact same problem and already solved it ([RAL-114](<https://linear.app/ralphoksiprojects/issue/RAL-114/ldip-no-way-to-correct-an-uploaded-multi-office-record>), "Option A"): re-upload a corrected file, targeting the SAME existing record, full-replacing its hierarchy while keeping `Id`/`RefCode`/`CreatedAt`/`CreatedById` unchanged. This ticket is that same fix for AIP.

## 1. Current architecture (mirrors what [RAL-114](https://linear.app/ralphoksiprojects/issue/RAL-114/ldip-no-way-to-correct-an-uploaded-multi-office-record) found for LDIP, verified fresh for AIP)

* `backend/PPDO.Application/Services/AipService.cs` — `ConfirmImportAsync` always **creates a new **`AipRecord`. There is no "re-import into an existing record" path.
* `backend/PPDO.Application/DTOs/BudgetPlanning/AipDtos.cs` — `AipImportConfirmDto` has no target-record concept.
* `frontend/src/app/(portal)/budget-planning/aip/page.tsx` (list) — only Finalize/Archive actions exist; no "Re-upload" entry point.
* `frontend/src/app/(portal)/budget-planning/aip/detail/page.tsx` — read-only, no edit/replace entry point.

## 2. Implementation — same shape as [RAL-114](https://linear.app/ralphoksiprojects/issue/RAL-114/ldip-no-way-to-correct-an-uploaded-multi-office-record)

* Extend `AipImportConfirmDto` with an optional `TargetRecordId` (int?). When present, `ConfirmImportAsync`:
  1. Loads the target record, verifies it exists, `Status == "Draft"`.
  2. Full-replaces its hierarchy (delete existing `AipOffice`→Program→Project→Activity tree, reinsert from the freshly parsed payload).
  3. Bumps `UploadedAt`; updates `OriginalFilename` to the new file's name.
  4. When `TargetRecordId` is absent, behaves exactly as today (create new record).
* Frontend: "Re-upload" action on the AIP detail page (Draft + Upload entry-source only), routing to `aip/new`'s Upload tab with `?replaceId=X`; confirm redirects back to the SAME record.

## Acceptance Criteria

- [X] `AipImportConfirmDto.TargetRecordId` (optional) — when set, `ConfirmImportAsync` full-replaces that record's hierarchy instead of creating a new one
- [X] Guard: target record must be `Status == "Draft"`; otherwise a clear validation error (Final needs Unlock first)
- [X] Guard: target record must be Upload entry-source (Manual records can't be re-uploaded into)
- [X] Guard: target record must have no WFP built from it (added in the follow-up fix above)
- [X] `Id`/`CreatedById`/original creation timestamp unchanged on replace; an audit log entry recorded as Update, not Create
- [X] "Re-upload" entry point for Draft AIP records, reusing the existing upload/preview UI
- [X] Confirming a re-upload redirects back to the SAME record, not a new one
- [X] Existing "create new record" upload flow (no target id) is unaffected
- [X] TDD: extended `AipServiceTests.cs` — target-not-found, target-not-Draft, target-manual-entry, target-has-wfp-usage, successful replace preserving identity
