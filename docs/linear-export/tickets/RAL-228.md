# RAL-228 — OfficeScope primitive + office-clamp helper for Budget Planning

Foundation ticket for office-user data isolation. The two leak-fix tickets in this milestone consume what this builds; the AIP redesign (Track 2) will consume it too.

## Context — read first

* `docs/v1.8/Office_User_Path_Findings.md` — the full assessment, especially §3.6 (no shared primitive) and §4 (the LDIP pattern to copy)
* `backend/PPDO.Application/Common/DivisionScope.cs` — the existing sibling primitive this mirrors
* `backend/PPDO.Functions/Functions/LdipFunctions.cs` — the only feature that currently enforces office isolation ([RAL-61](https://linear.app/ralphoksiprojects/issue/RAL-61/ui-ldip-entry-form-createedit)); its `DenyForeignOfficeAsync` and clamp-on-write are the proven in-repo pattern
* `backend/PPDO.Application/Services/PermissionService.cs` — how `user.OfficeId` already discriminates PPDO vs office users
* `CLAUDE.md`, `docs/TEST_CONVENTIONS.md`

## Problem

`DivisionScope` gives the codebase a clean, tested way to resolve "which division's data may this caller see", with an explicit guard that a null division resolves to **nothing**, never **everything**. There is no equivalent for office.

Every place that needs office isolation therefore hand-rolls it. Today that is exactly one file (`LdipFunctions.cs`), which is why the inconsistency has not bitten yet — but Track 1's leak fixes, Track 2's AIP redesign, and Track 3's reviewer flow all need the same resolution logic, and hand-rolling it four times is how the §3.3 IDOR happened in the first place.

## Steps

1. **Add** `OfficeScope` in `backend/PPDO.Application/Common/`, mirroring `DivisionScope`'s shape and XML-doc style:
   * `All` — PPDO-internal caller (`user.OfficeId is null`): no office filter.
   * `For(int officeId)` — office user: scoped to their own office.
   * `Resolve(User user)` — `user.OfficeId is int id ? For(id) : All`.
   * **Note the deliberate asymmetry with** `DivisionScope`**:** there is no `Nothing` state. A null `OfficeId` means PPDO-internal (full access), not "unassigned". Document this explicitly in the XML comment — a reader coming from `DivisionScope`, where null means *see nothing*, will otherwise assume the same rule and invert the security check.
2. **Add a clamp helper** alongside `ConfigHttp`'s existing helpers, so endpoints do not re-implement the pattern:
   * A read-guard equivalent of `LdipFunctions.DenyForeignOfficeAsync` — given the caller and a resolved owning office id, return a 403 response or null.
   * A clamp for query/body-supplied office ids — given the caller and a requested office id, return the id the caller is actually allowed to use (their own if they are an office user, the requested one if PPDO).
   * **Prefer clamping over validate-and-reject** where the endpoint semantics allow it — see findings §4. There is no error path to get wrong and no way for a client to probe for other offices' ids.
3. **Unit tests** in `PPDO.Tests/Application/` (new `OfficeScopeTests.cs`), naming per `docs/TEST_CONVENTIONS.md`:
   * PPDO user (null `OfficeId`) → `All`, for each role.
   * Office user → `For(theirOfficeId)`.
   * Clamp returns the caller's own office when an office user requests a different one.
   * Clamp passes the requested id through for a PPDO caller.
   * SuperAdmin/Admin **with** an `OfficeId` set — decide and pin the behaviour in a test. Recommendation: office wins (the field is the scoping dimension, and role bypass is about *feature* flags, not *data* scope), but flag it in the PR either way since it is a judgement call.
4. **Do not wire it into any endpoint in this ticket.** The two leak-fix tickets do that. Keeping this PR to the primitive plus tests makes it independently reviewable.
