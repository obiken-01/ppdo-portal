# RAL-176 — Budget Planning Dashboard "Remaining" column shows office-wide unallocated ceiling instead of division's actual WFP remaining budget

> 🐛 Found live by Ralph 2026-07-21: on the Budget Planning Dashboard (`/budget-planning`), every division's row in "WFP Status by Division" shows a blank top-level Remaining cell, and every expanded per-fund row shows ₱0.00 Remaining — for every fund, every division. But opening the WFP Entry Wizard (`/budget-planning/wfp/entry`) for those exact same division+fund combinations shows a correct, nonzero remaining (e.g. Administrative Division / General Fund: "6,854,499.76 original · 3,213,286.16 remaining"; Statistics Monitoring and Evaluation Division / General Fund: "1,811,336.15 original · 1,341,358.07 remaining").
> 📌 Backend + frontend. Root cause confirmed by code read below — this ticket scopes the fix; child of epic [RAL-116](<https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14>) (Budget Planning Dashboard family, same as [RAL-161](<https://linear.app/ralphoksiprojects/issue/RAL-161/budget-planning-dashboard-rework-ppdo-scoped-queries-per-divisionfund>)/[162](<https://linear.app/ralphoksiprojects/issue/RAL-162/budget-planning-dashboard-rework-ppdo-scoped-ui-per-division-pie>)).

## Why — confirmed root cause

Two different "remaining" metrics exist in the codebase and the dashboard is showing the wrong one for a per-division table:

* **WFP Entry Wizard** (`WfpCeilingService.GetStatusAsync`, `backend/PPDO.Application/Services/WfpCeilingService.cs:53-91`) computes, per division+fund: `remaining = allocation − usedForFund`, where `usedForFund` comes from `IWfpAllocationLedgerRepository.SumUsedAmountAsync` — the actual WFP expenditures entered so far against that division's allocation for that fund. This is "how much of MY allocation do I have left to spend in WFP."
* **Budget Planning Dashboard** (`BudgetPlanningDashboardService.BuildCeilingByFundAsync`, `backend/PPDO.Application/Services/BudgetPlanningDashboardService.cs:200-228`) computes, per fund only (not per division): `remaining = ceiling − allocations.Sum(a => a.Amount)` — the fund's office-wide ceiling minus what's been divided up among ALL divisions. This is "how much of the office ceiling hasn't been assigned to any division yet," an entirely different, office-level fact that is intentionally identical for every division (see the doc comment at line 213-214: *"Remaining" is an office-wide fact and must reflect the true unallocated portion regardless of who's viewing*).

The frontend then compounds this by reusing that office-wide value per division row: `frontend/src/app/(portal)/budget-planning/page.tsx`'s `DivisionRow` component renders `fundRemaining.get(f.fundingSourceId)` (line 422-424) — a `Map` built from `dashboard.ceilingByFund` (line 545-547) — inside each division's expanded per-fund breakdown, displaying the SAME office-wide number for every division. In this environment each fund's ceiling is already fully allocated across its divisions (`ceiling − sum(allocations) == 0`), so every fund shows ₱0.00 here regardless of division, even though divisions individually still have plenty of unspent allocation.

Separately: the top-level division row's Remaining `<td>` (`page.tsx:402`) is entirely empty — `<td className="px-4 py-2.5" />` — no value is wired up there at all, not even the (wrong) office-wide figure.

## Scope of the fix

1. **Backend**: extend the per-division WFP status data (`DivisionWfpStatusDto` / `DivisionFundAmountDto` in `backend/PPDO.Application/DTOs/BudgetPlanning/PpdoDashboardDtos.cs`, populated in `BudgetPlanningDashboardService.BuildWfpByDivisionAsync`, `backend/PPDO.Application/Services/BudgetPlanningDashboardService.cs:149-198`) to carry each division+fund's actual `used`/`remaining`, sourced the same way `WfpCeilingService` does — via `IWfpAllocationLedgerRepository.SumUsedAmountAsync(divisionId, fiscalYear, fundId, ...)` — rather than leaving the table to fall back on `ceilingByFund`. Sequential awaits only (existing method already loops per division — `DbContext` is not thread-safe, per CLAUDE.md).
2. **Frontend**: `DivisionRow` in `frontend/src/app/(portal)/budget-planning/page.tsx` should render the new per-division-per-fund remaining in both the expanded breakdown rows (replacing the `fundRemainingById` lookup) and the top-level Remaining cell (currently empty) — likely summed across funds, or left per-fund only in the expanded view with the top-level cell showing a total.
3. Keep `FundCeilingDto.remaining` / `ceilingByFund` as-is for the "Ceiling and Allocation by Fund" pie-chart cards above the table — that office-wide-unallocated-ceiling metric is correct and intentional for THAT section, per its own doc comment. Do not change its meaning; only stop reusing it in the per-division table.

## Out of scope

* The "Ceiling and Allocation by Fund" pie charts (`FundCeilingCard`) — correct as-is, not touched.
* Any change to `WfpCeilingService` or the WFP Entry Wizard — already correct, used only as the reference implementation to copy the calculation approach from.

When a fix is implemented, commit with:
`fix(budget-planning): show division's actual WFP remaining instead of office-wide unallocated ceiling (RAL-XXX)`
