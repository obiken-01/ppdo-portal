# RAL-268 — User Management form: restructure into permission sections

**V18-08** — plan: `docs/v1.8/Phase_Plan.md` §3.1. Last ticket in the permissions cluster — depends on V18-02 ([RAL-243](https://linear.app/ralphoksiprojects/issue/RAL-243/pbo-ceiling-permission-overridecanmanagepboceiling-set-budgetceiling)), V18-03 ([RAL-244](https://linear.app/ralphoksiprojects/issue/RAL-244/reviewer-permission-overridecanreviewbudgetplanning)), V18-05 ([RAL-257](https://linear.app/ralphoksiprojects/issue/RAL-257/lfc-permission-the-first-cross-office-flag-bypasses-officescope)) and V18-20 ([RAL-262](https://linear.app/ralphoksiprojects/issue/RAL-262/permission-aware-landing-selector-user-form-division-config-office)), since it renders all of their fields.

After this phase the user form carries role, office, division, **~11 permission flags** and a landing page. As one flat list of checkboxes that is unreadable, and unreadable permission UI is how the wrong box gets ticked for a real person.

**Scope:** group the form into sections — suggested: **Identity** (name, username, position, contact) · **Placement** (role, office, division, landing page) · **Budget Planning** (access, upload AIP, PPDO allocation, PBO ceiling, reviewer, LFC) · **Inventory** · **Administration** (manage users, manage config, manage resource links).

Two things worth doing while in there:

* Show each flag's **effective** value, not just the override — a null override reading "off" when the division grants it is actively misleading.
* Mark the flags that are **per-user grants** (allocation, PBO ceiling, reviewer, LFC) distinctly from the ones that **inherit from the division**. They behave differently and the form currently gives no hint.

Frontend only — no permission logic changes here. Reuse the existing form components; flat design per `docs/DESIGN_SYSTEM.md`.
