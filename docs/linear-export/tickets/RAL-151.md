# RAL-151 — [not a bug] WFP entry: reserve override field takes precedence over the 10% default — resolved with user

> 📌 No code change. Documentation only — closing out a user-reported issue as working-as-intended.

## Report

A user reported that after updating an expenditure, the reserve amount shown at the bottom of the Add/Edit Expenditure modal didn't recompute to the expected 10%.

## Root cause (confirmed with the user)

This is not a bug. The reserve amount override field (the `MoneyInput` shown under the "Apply reserve" checkbox, next to the text "Leave amount blank to use the default") had a leftover value from a previous entry. Per design ([RAL-121](https://linear.app/ralphoksiprojects/issue/RAL-121/wfp-reserve-rule-wiring-10percent-hard-cap-default-only-prefill)/[RAL-139](https://linear.app/ralphoksiprojects/issue/RAL-139/wfp-entry-make-the-apply-reserve-checkbox-read-only-driven-by-the)), when that field is populated it **always** takes precedence over the computed `10% × Net Appropriation` default — this lets a user deliberately override the reserve for accounts where the flat 10% doesn't apply. The modal was doing exactly what it's supposed to: showing the explicit override, not the computed default, because a value was present.

## Resolution

Discussed with the user — he will clear (empty) that field himself whenever he wants the automatic 10% computed instead of an override. No code change needed; the existing behavior (override field wins when non-blank, computed 10% only when blank) is correct and matches the account-driven reserve design from [RAL-121](https://linear.app/ralphoksiprojects/issue/RAL-121/wfp-reserve-rule-wiring-10percent-hard-cap-default-only-prefill)/[RAL-139](https://linear.app/ralphoksiprojects/issue/RAL-139/wfp-entry-make-the-apply-reserve-checkbox-read-only-driven-by-the).

## Out of scope

If this recurs and the actual ask becomes "make it more obvious in the UI that a manual override is active" (e.g. a small "(override)" badge next to the amount), that would be a new, separate UX ticket — not raised as part of this report.
