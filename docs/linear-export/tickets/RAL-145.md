# RAL-145 — [bug] Function Band default "Core" never persists unless the dropdown is touched — program lands in UNASSIGNED on the WFP report

> 🌿 Working branch: off `main`. PR now retargeted to `release/1.4.1` (2026-07-13, per Ralph) so this (and [RAL-146](https://linear.app/ralphoksiprojects/issue/RAL-146/wfp-entry-warn-before-discarding-unsaved-changes-in-the-addedit), bundled into the same PR) merges to `main` together with [RAL-144](https://linear.app/ralphoksiprojects/issue/RAL-144/bug-aip-activity-total-blankzero-when-source-excel-cell-is-blank) in one consolidating PR, instead of separate direct merges. Child of epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> 📌 Found live 2026-07-13 by Ralph.

## Symptom

In the WFP entry wizard's context picker, the Function Band dropdown for a selected Program visually shows "Core" selected by default. If the user never touches the dropdown (since it already looks correct), the WFP report preview still categorizes that program under **UNASSIGNED FUNCTIONS**, not CORE FUNCTIONS.

## Root cause

`frontend/src/app/(portal)/budget-planning/wfp/entry/page.tsx` (~line 1315):

```tsx
<select
  value={selectedProgram.functionBand ?? "CORE"}
  onChange={(e) => handleFunctionBandChange(selectedProgram.id, e.target.value)}
  ...
>
```

`value={selectedProgram.functionBand ?? "CORE"}` is a **display-only** fallback — it makes the `<select>` render "Core" as selected whenever the underlying `functionBand` is `null`, but nothing calls `handleFunctionBandChange` (which persists via `updateAipProgramFunctionBand`) unless the user actually fires the `<select>`'s `onChange` — i.e. picks a *different* value and (for Core specifically) there's no event at all if the user leaves it alone, since it already visually matches. The real `functionBand` in the database stays `null`.

`backend/PPDO.Application/Services/WfpReportService.cs`'s `BuildSections`:

```csharp
string band = string.IsNullOrWhiteSpace(program.FunctionBand)
    ? UnassignedFunctionBand
    : program.FunctionBand;
```

buckets a `null`/blank `FunctionBand` under `UNASSIGNED FUNCTIONS` — so the UI and the report silently disagree.

This affects any program whose `function_band` is still `NULL` in the DB. Per project memory: a one-time dev-DB-only backfill set existing null rows to `'CORE'` back on 2026-07-11 ([RAL-126](https://linear.app/ralphoksiprojects/issue/RAL-126/wfp-program-function-band-corestrategicsupport-activity-creation-flag) side task) but was **never applied to production** — so any program from the original production AIP import that predates that fix can still have `function_band = NULL` today, and this bug is how it stays that way even after a user "reviews" it in the entry wizard.

## Fix

Auto-persist the CORE default the instant a program with `functionBand == null` is selected in the wizard, so the displayed value and the saved value can never drift apart — mirrors the same "default shown ≠ default saved" bug class as [RAL-144](https://linear.app/ralphoksiprojects/issue/RAL-144/bug-aip-activity-total-blankzero-when-source-excel-cell-is-blank) (AIP Total) and the earlier v1.4.1 WFP office/division auto-select bug, just in a different field.

```tsx
useEffect(() => {
  if (selectedProgram && selectedProgram.functionBand == null && savingProgramId !== selectedProgram.id) {
    handleFunctionBandChange(selectedProgram.id, "CORE");
  }
}, [selectedProgram?.id, selectedProgram?.functionBand]);
```

**Bundled in the same PR**: [RAL-146](https://linear.app/ralphoksiprojects/issue/RAL-146/wfp-entry-warn-before-discarding-unsaved-changes-in-the-addedit) (warn before discarding unsaved changes in the Add/Edit Expenditure modal) — found while manually verifying this ticket, fixed on the same branch per Ralph's request.

## Test plan

* Manual: select a program with `function_band = NULL` in the entry wizard, do NOT touch the Function Band dropdown, navigate away, then check the DB / report preview — program should now show `function_band = 'CORE'` and appear under CORE FUNCTIONS.
* Confirm a program that already has a real `FunctionBand` (CORE/STRATEGIC/SUPPORT) is untouched — the effect only fires when `functionBand == null`.
* Confirm manually picking STRATEGIC/SUPPORT still works and persists as before (unchanged code path).

## Data note (2026-07-13, confirmed live)

Ralph found a real production example of this gap: PPDO program `1000-000-1-01-010-013` (PARTNERS program) still shows under UNASSIGNED FUNCTIONS on the live WFP report. This fix only prevents the illusion going forward for any program touched in the entry wizard from now on — it does not retroactively backfill remaining production `function_band IS NULL` rows. A production-ready backfill script (`backfill-function-band-all-offices.sql`, all offices, excludes one deliberate STRATEGIC exception) is prepared and handed to Ralph to run — pending execution.

## Out of scope

The SQL backfill itself (prepared separately, not part of this code PR).
