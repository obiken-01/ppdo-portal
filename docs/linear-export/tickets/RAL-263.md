# RAL-263 — One resolveLandingPath() helper — replace the five hardcoded redirect sites

**V18-18** — plan: `docs/v1.8/Phase_Plan.md` §3.3. Depends on V18-17 ([RAL-261](https://linear.app/ralphoksiprojects/issue/RAL-261/expose-the-resolved-landingpath-on-authme)).

The landing target is currently hardcoded in **five** places, each with slightly different logic. All five verified present on `release/1.8.0`:

| Site | Today |
| -- | -- |
| `frontend/src/app/(public)/login/page.tsx:137` | `me.officeId != null ? "/budget-planning" : "/dashboard"` |
| `frontend/src/app/(portal)/layout.tsx:215` | office-user gate → `/budget-planning` or `/account` |
| `frontend/src/components/layout/Sidebar.tsx:167` | logo link → `/dashboard` |
| `frontend/src/app/manifest.ts:36` | `start_url: "/dashboard"` |
| `/reconnecting` | `?next=` default → `/dashboard` |

Replace them with a single `resolveLandingPath(me)` helper reading the server-resolved `landingPath` from `/auth/me`, with a safe fallback for the case where `me` is not loaded yet.

The manifest is the odd one out — it is static and cannot read a user, so it gets its own ticket (V18-19).

⚠️ The portal layout's office-user gate is a **guard**, not a preference: it must keep working after this change. Resolve-then-guard, not guard-replaced-by-resolve.

**Done when:** no route string is duplicated across those files, and login / logo click / reconnect all land on the same page for the same user.
