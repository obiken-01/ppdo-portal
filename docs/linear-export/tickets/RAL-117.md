# RAL-117 — Config: Chart of Accounts rework — expense_class, default_nature, default_apply_reserve

> 🌿 **Working branch: **`release/1.4.0`. PRs target it, **not **`main`.
> 📌 Read the epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14) first, then `docs/v1.4/WFP_Rework_Requirements_Draft.md` §7.3 and §7.3.1 FULLY.
> ✔ **Updated 2026-07-07 (Ralph's answer to open question** [obiken-01/ppdo-portal#11](https://linear.app/ralphoksiprojects/review/featinfra-add-jwtmiddleware-currentuserservice-permissionservice-ral-ac8d4c027e6e)**):** reserve is a **default-only** column, same pattern as `default_nature` — see Scope point 1 below. No hard eligibility gate.

## Why

`accounts.AccountType` (PS/MOOE/CO) is currently **derived at query time** from the `AccountNumber` prefix (`5-01-`=PS, `5-02-`=MOOE, `5-03-`=CO) — see `Account.cs`'s doc comment. The new WFP form's Capital Outlay lines use **asset accounts starting** `1-07-xx` (Motor Vehicles, ICT Equipment, etc.), plus `1-04-xx` semi-expendables — prefix-derivation breaks for these. The form also needs two new per-account attributes with no current home: a reserve default and an optional default procurement-nature.

## Scope

1. **Add three stored columns to** `Account`**:**
   * `expense_class` (string, PS/MOOE/CO) — **replaces** prefix-derivation; `AccountType` in `AccountDto` becomes a stored value, not computed
   * `default_nature` (string?, nullable — `Procurement`/`Non-Procurement`/`Combined`) — **optional, default-only** (§5.3 ✔ resolved): pre-fills the per-expenditure Nature field in WFP entry, never enforced, always overridable
   * `default_apply_reserve` (bool, default false) — **✔ RESOLVED 2026-07-07, replaces the originally-scoped** `is_reserve_eligible` **hard gate.** Ralph's answer to open question #11: this is a **default-only** flag, identical in spirit to `default_nature` — it pre-fills the reserve toggle in WFP entry (ticket [RAL-123](https://linear.app/ralphoksiprojects/issue/RAL-123/wfp-entry-ui-context-picker-expenditure-wizard-shell)) when a user picks that account, but **any account can have its reserve toggle turned on regardless of this flag** — it is never an enforced restriction. This also resolves the earlier contradiction found in the source workbook (a sample line reserved against a Salaries/PS account, outside the "42 accounts with reserve" list) — under this design that's simply a valid override, not a data error.
2. **Import the expanded chart.** Seed from `D:\RalphFiles\PPDO\PPDO\AIP\accounts_nature_draft.csv` (306 accounts) via the existing CSV upsert flow — this is a **data seed**, not a hard-coded migration seed. The 42 "Accounts with Reserve" flagged in that CSV's `is_reserve_eligible` column become the seed value for `default_apply_reserve = true` (rename the CSV's column meaning accordingly when importing — same source data, different semantics: a default, not a gate). Canonicalize `account_number` format (dash-separated, matching the existing config convention — the WFP-NEW workbook's VALIDATION sheet uses space-separated codes, which must be normalized wherever future WFP-file imports read account codes).
3. **Update** `AccountDto`**/**`UpsertAccountDto` to include the three new fields; update the CSV export/import round-trip (`ExportCsvAsync`/`ImportCsvAsync`) to read/write them.
4. **Update the Account Config page** (`config/accounts`) to show/edit the three new columns — `expense_class` as a select (PS/MOOE/CO), `default_nature` as an optional select (blank/Procurement/Non-Procurement/Combined), `default_apply_reserve` as a checkbox labeled clearly as a default ("Reserve applies by default" or similar — not "eligible for reserve", to avoid implying a restriction).

## Acceptance Criteria

- [ ] `Account` has `expense_class`, `default_nature` (nullable), `default_apply_reserve` (bool) columns; migration is additive (no data loss)
- [ ] `AccountDto.AccountType` reads the stored `expense_class`, not a prefix-derived computation
- [ ] CSV upload seeds all 306 accounts from the draft file with correct values (42 reserve-flagged accounts seed `default_apply_reserve = true`)
- [ ] `default_nature` accepts null and all three enum values; API rejects any other string
- [ ] `default_apply_reserve` is a plain bool with NO validation tying it to whether a WFP expenditure can set `apply_reserve` — any account may reserve ([RAL-121](https://linear.app/ralphoksiprojects/issue/RAL-121/wfp-reserve-rule-wiring-10percent-toggle-eligibility-gate) owns the actual cap/validation logic)
- [ ] Existing WFP/AIP code paths that read `AccountDto.AccountType` are unaffected (same shape, different source)
- [ ] Config page shows/edits all three new fields, with `default_apply_reserve` labeled as a default, not a restriction
