# RAL-168 — Dashboard calendar: allow event owner to edit their own event

> 🌿 Working branch: `release/1.4.5`. PR targets `release/1.4.5` (NOT `main`). Child of epic [RAL-116](<https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14>).

Requested by Ralph 2026-07-17, unrelated to the performance-audit Tier 1 tickets ([RAL-163](https://linear.app/ralphoksiprojects/issue/RAL-163/allocationservice-eliminate-repeated-full-table-ceilingallocation)–167) but bundled into the same `release/1.4.5` branch per his "fold in what we finish" plan.

## Why

On the main Dashboard's calendar (`frontend/src/app/(portal)/dashboard/page.tsx`), Ralph wants an event to be editable **only by the user who created it** (the owner) — no one else, including other Admins/SuperAdmins.

**Confirmed by reading the current code — this is net-new, not a bug fix**: there is no edit capability for calendar events at all today.

* `IDashboardService`/`DashboardService.cs` only has `CreateEventAsync`, `GetPendingEventsAsync`, `ReviewEventAsync` (admin approve/reject), `DeleteEventAsync` (creator-or-admin), and `GetEventsAsync`. No `UpdateEventAsync`.
* `DashboardFunctions.cs` has no `PUT`/`PATCH` route for a single event — only `GetDashboardEvents`, `CreateDashboardEvent`, `GetPendingEvents`, `ReviewCalendarEvent`, `DeleteCalendarEvent`.
* The frontend's event-detail modal (`dashboard/page.tsx:153-218`) is view-only — no Edit button, no Delete button either (even though the backend already supports delete).
* `CalendarEventDto` (`backend/PPDO.Application/DTOs/Dashboard/CalendarEventDto.cs`) does **not** include `CreatedById` — the frontend currently has no way to know who owns an event. This has to be added before an "is this mine?" check can work client-side.

## Scope decision (confirm before/while implementing, not assumed)

* **Owner-only, no admin override** — this is a deliberate difference from `DeleteEventAsync`'s existing `isAdmin || isCreator` gate. Ralph's exact ask was "edited by the owner only." If that's wrong once he sees it, it's a one-line change (`isCreator` → `isAdmin || isCreator`) — flag it to him rather than silently matching Delete's looser rule.
* **Editing an already-Approved Office event**: recommend resetting `Status` back to `Pending` (re-triggers admin review) when a non-admin owner edits an Approved Office event — mirrors the create-flow's approval rule (`CreateEventAsync`: non-admin Office event → Pending). Personal events never need approval regardless of edits. Confirm this with Ralph before implementing if it's not obvious from the PR description.

4. New `DashboardFunctions` handler (`PUT /api/dashboard/calendar-events/{id}` or match the existing route naming convention in that file) — JWT validation per CLAUDE.md's standard pattern, call the service, map ServiceResult → HTTP response.
5. Frontend: add `createdById` to `CalendarEventResponse` (`types/dashboard.ts`), add an `updateEvent` API call (`lib/api.ts` convention).
