# RAL-237 — Move Function App to Southeast Asia — fix cross-region latency

## Problem (confirmed, not guessed)

`ppdo-portal-api` (Function App) runs in **Central US**; `ppdo-portal-db` (SQL Database) runs in **Southeast Asia** — confirmed 2026-08-17 directly from both resources' Overview pages in Azure Portal.

This produces two cross-Pacific hops on every request:

1. **Browser → Functions**: `NEXT_PUBLIC_API_BASE_URL` is baked into the frontend build pointing straight at the Central US Function App URL (SWA Free tier doesn't support the managed API-link proxy). Every user in Occidental Mindoro makes a direct PH→US round trip just to reach the API.
2. **Functions → SQL**: confirmed via Application Insights Live Metrics — every `Executed DbCommand` trace showed ~196-198ms, nearly identical regardless of query complexity or table. That uniformity is the signature of fixed network round-trip latency, not variable query cost. Since `DbContext` isn't thread-safe (no `Task.WhenAll` over one context, per CLAUDE.md), queries run sequentially, so this ~200ms tax multiplies per query within a request — matches observed Request Duration readings of 2-10sec.

DTU capacity was ruled out first: `ppdo-portal-db` DTU% baseline sits at 0-20% (max 6% over a clean 24h window), nowhere near the 5 DTU Basic-tier ceiling. This is not a database horsepower problem.

## Why Southeast Asia (not moving the DB to Central US)

Philippines is much closer to the Southeast Asia region than to Central US. Moving the Function App to Southeast Asia fixes **both** hops (browser↔API and API↔DB) at once. Moving the DB to Central US instead would only fix the second hop and leave the larger, more user-perceptible browser↔API hop untouched — it's the structurally worse fix.

It's also lower-risk and cheaper to execute:

* Functions are stateless — this is "stand up new resource, test, cut over," not an in-place risky operation on a live data store.
* SQL Basic tier doesn't support active geo-replication (needed for a near-zero-downtime DB region move) — moving the DB would require temporarily upgrading off Basic first.
* Function App Consumption pricing is regionless — no ongoing cost increase.

## Files to check before starting

* `.github/workflows/deploy.yml` — current CI/CD deploy target (ZIP deploy via publish profile, per CLAUDE.md's v1.0.1 patch notes)
* `frontend/.env` / wherever `NEXT_PUBLIC_API_BASE_URL` is set for the GitHub Actions frontend build (per CLAUDE.md: "baked into the Next.js build via `.github/workflows/deploy.yml`")
* `backend/PPDO.Functions/CorsFunctions.cs` and `Program.cs` `worker.Use()` CORS middleware — must be replicated on the new Function App (Azure Portal → CORS; `host.json` CORS does not work for isolated worker, per CLAUDE.md bug-fix notes)
* Storage account `ppdoportalstorage`'s region (check in Portal) — decide whether `AzureWebJobsStorage` also needs a Southeast Asia storage account, or whether reusing the existing one cross-region is an acceptable minor compromise (host bookkeeping, not request-critical path)
* `CLAUDE.md` Production Deployment table — needs updating once the new URL is live

No application code changes are required — this is infra + CI config + docs. TDD is not applicable.

## Steps

 1. Create a new Function App (base name `ppdo-portal-api`, Azure will assign a new unique suffix) in **southeastasia**, matching current config: Windows, `dotnet-isolated` worker, .NET 9, Consumption (Y1) plan.
 2. Decide on `AzureWebJobsStorage`: reuse `ppdoportalstorage` or create a Southeast Asia storage account (see "Files to check").
 3. Create or reuse an Application Insights resource colocated in Southeast Asia for the new app (optional, but avoids the same cross-region ingestion tax — low priority since it's not in the user-facing request path).
 4. Copy all App Settings from the old Function App into the new one via Azure Portal/CLI directly — `SqlConnectionString`, `Jwt__SecretKey`, `Jwt__Issuer`, `Jwt__Audience`, `Jwt__AccessTokenExpiryMinutes`, `Jwt__RefreshTokenExpiryDays`, `APPLICATIONINSIGHTS_CONNECTION_STRING`, `FUNCTIONS_WORKER_RUNTIME`. Never commit these to a file.
 5. Set CORS on the new Function App (Portal → CORS) to match the current prod app's allowed origins.
 6. Deploy current `main` backend code to the new Function App (manual `func azure functionapp publish` for the first verification pass is fine — don't wire CI to it yet).
 7. Smoke-test the new Function App directly at its own URL before touching the frontend: `GET /api/health`, then a JWT-protected endpoint with a manually obtained token. Confirm login/refresh flow works against it.
 8. Update `.github/workflows/deploy.yml`: point the backend deploy step at the new Function App (new `AZURE_FUNCTIONS_PUBLISH_PROFILE` GitHub secret).
 9. Update the frontend build's `NEXT_PUBLIC_API_BASE_URL` to the new Southeast Asia Function App URL, then push to `main` to redeploy the frontend through the normal pipeline.
10. Re-verify CORS against the live SWA origin once the frontend is redeployed.
11. Verify end-to-end in prod: login, a few protected endpoints, and check Application Insights Live Metrics on the new app — `Executed DbCommand` timings should drop from ~200ms toward single digits, since Functions and SQL are now colocated.
12. After a day or two of stable operation, delete the old Central US Function App (and its dedicated Storage/App Insights if not shared) to avoid orphaned resources.
13. Update `CLAUDE.md`'s Production Deployment table with the new Function App name, URL, and region.

## Out of scope / do NOT

* Do not touch the SQL Database's region or tier as part of this ticket — that was evaluated and rejected as the weaker fix (see "Why Southeast Asia" above).
* Do not set up a custom domain as part of this — neither the current Function App nor SWA uses one; not needed for this fix.
* Do not attempt to migrate mid-cutover by editing the old Function App in place — this is a parallel stand-up-and-switch, not an in-place change.

## When done, commit with

`chore(infra): relocate Function App from Central US to Southeast Asia (RAL-237)`

## How this was found

Session-based investigation starting from a ~₱21K/year Azure subscription budget question, which led to checking the SQL DB's DTU metrics (ruled out as the bottleneck — max 6% over 24h), then Application Insights Live Metrics screenshots showing suspiciously uniform ~200ms `Executed DbCommand` timings, which pointed at network round-trip latency rather than query cost. Confirmed by reading both resources' regions directly in Azure Portal.
