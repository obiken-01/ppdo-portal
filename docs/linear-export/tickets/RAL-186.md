# RAL-186 — Fix PR create/import division resolution + add optional PR No. to Excel template

## Problem

PR creation and Excel import were completely broken. The Create PR, PR List, and

Distribution pages hard-coded the fixed Division enum retired in v1.2 ([RAL-97](https://linear.app/ralphoksiprojects/issue/RAL-97/divisions-permission-model-rebuild-retire-permissiongroupdivision)):

`["Admin", "Planning", "RM", "MIS", "SPD"]`. None of these match any seeded PPDO

division name ("Administrative Division", "Sectoral Planning Division", ...), so

PurchaseRequestService's name-based resolution returned null for every submission.

## Root causes found (3, while fixing live)

1. **Division matching** — PurchaseRequestService.ResolveDivisionByNameAsync matched

   Name only, and matched across EVERY office (names are unique only within an

   office — "Administrative" exists under both PTO and PHO). Fixed: scoped to

   PPDO's own divisions via IOfficeRepository.GetByCodeAsync("PPDO"), matches

   Name OR Code case-insensitively, falls back to all active divisions if the

   PPDO office row is missing.
2. **Missing Division include** — PR List showed a blank Division column even

   after fix [obiken-01/ppdo-portal#1](https://linear.app/ralphoksiprojects/review/chorescaffold-scaffold-net-9-solution-with-5-projects-ral-24-7cfacf3d54aa), because none of Repository<T>.GetAllAsync(),

   GetByDivisionAsync, GetWithItemsAsync, or GetWithItemsAndDeliveriesAsync ever

   did `.Include(pr => pr.Division)`. Create's own response only looked correct

   by EF Core relationship-fixup coincidence. Predates this ticket — [RAL-97](https://linear.app/ralphoksiprojects/issue/RAL-97/divisions-permission-model-rebuild-retire-permissiongroupdivision)

   added the FK but never the Include anywhere it's read back. Fixed: added the

   Include (depth 1) to all four methods.
3. **PR No. missing from the Excel template** — the GSO paper form has a PR No.

   field; the portal's downloadable template didn't. Added as optional (no

   required-field asterisk, same "leave blank to auto-generate" contract as the

   manual Create PR form's PrNo field), threaded through ParsePRImport ->

   PurchaseRequestImportRow -> CreatePRDto.PrNo.

## Verification

Live end-to-end: logged in locally, submitted a PR through the UI (201 Created),

downloaded the real template, filled in PR No. "101-1041-GF-2026-07-29-999",

imported it via direct API call, confirmed the created PR carried that exact

number. 878/878 backend tests passing (10 new).
