# RAL-137 — WFP cleanup endpoint (delete WFP expenditures/records for a scope) — for live testing

> 🌿 Working branch: `release/1.4.2` (off `main`). PR targets `release/1.4.2`. Child of epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> 📌 Backend. Operational/testing tool — must be tightly access-gated.

## Why

During live testing we need to reset WFP data (expenditures and/or WFP records) for a given scope so a fresh test run starts clean, without hand-deleting rows in the DB.

## Scope

* Add an admin-only endpoint to purge WFP data for a scope — e.g. `DELETE /api/budget-planning/wfp/cleanup?officeId=&fiscalYear=&divisionId=` (parameters to be confirmed). It should delete `WfpExpenditure` rows (and their child period / procurement-item rows) and, if requested, the parent `WfpRecord` for the scope.
* Gate on `SuperAdmin`/`Admin` (or `CanManageConfig`) — NOT `CanAccessBudgetPlanning`. This is destructive; it must never be reachable by a regular WFP user.
* Respect the existing Final-lock rule? Decide whether cleanup can also purge Final records (likely yes for a testing tool, but confirm) — if so, document that it bypasses the `WfpService` Final lock deliberately.
* Log every purge at `LogWarning` with the scope + row counts (this is a destructive admin action).
* Return counts of what was deleted.

## Open questions

* Exact scope granularity (per office+FY, per division, per WFP record id?).
* Should it be removed / feature-flagged before the module is opened to real users, or kept as a permanent admin utility?

## Out of scope

Any UI — this is an API-only utility for now (invoke via REST client / admin tooling).
