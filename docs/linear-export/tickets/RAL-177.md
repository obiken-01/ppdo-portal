# RAL-177 — Allocation: PPA→Division Multi/Single toggle reverts to "Single" on reload despite correct multi-division data

> 🐛 Found live by Ralph 2026-07-21 on the Allocation page's "PPA → Division" tab (`/budget-planning/allocation`). Frontend-only, standalone fix. Child of epic [RAL-116](<https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14>) (Budget Planning / Allocation family, same as [RAL-163](https://linear.app/ralphoksiprojects/issue/RAL-163/allocationservice-eliminate-repeated-full-table-ceilingallocation)).

## Symptom

1. On a program row, click the Single/Multi toggle to switch it to "Multi".
2. Check an additional division's checkbox (e.g. OG-CSO) alongside whatever was already assigned.
3. Click Save — succeeds, backend persists the full `divisionIds` array correctly (verified: the additional division's checkbox stays checked, the PPA is genuinely visible to that division elsewhere in the app, and the per-division assigned-count in the table header updates).
4. Refresh or navigate away and back to the Allocation page — the toggle badge for that program shows **"Single"** again, even though the program still has multiple divisions assigned and the checkboxes (once toggled back to Multi) show the correct multi-division state.

The underlying data was never wrong — only the toggle's own displayed state was stale.

## Root cause (confirmed by code read + live reproduction)

`frontend/src/app/(portal)/budget-planning/allocation/page.tsx` — the Multi/Single toggle is driven entirely by client-only React state, `multiDivision: Record<string, boolean>` (line ~451), which is NOT persisted anywhere server-side (`ProgramAssignmentDto` only carries `DivisionIds`, no multi/single flag — confirmed in `backend/PPDO.Application/DTOs/BudgetPlanning/AllocationDtos.cs:28-33`). On every data load (the `load()` effect that fires on mount and whenever office/FY changes — line ~519-589), the code unconditionally reset this state to an empty object:

```ts
setMultiDivision({});
```

Since `isMulti = multiDivision[key] ?? false`, every program defaults back to "Single" (`false`) after any reload — regardless of how many divisions are actually assigned — until the user manually re-toggles it in that session. `handleSavePpa` (line ~687) never touches `multiDivision` and never triggers a reload itself, which is why the bug is invisible until a refresh/revisit.

## Fix

`multiDivision` must be re-derived from the loaded data on every load, not reset to blank — a program with more than one division assigned MUST be Multi (Single mode's `<input type="radio">` can only ever represent one selection), so it's derived as `divisionIds.length > 1`. Changed the same block that builds `localAssignments` from `progs` to also build a `multi` map alongside it and call `setMultiDivision(multi)` instead of `setMultiDivision({})`.

## Verification (live, local dev DB)

* Toggled "NATIONAL IDENTITY, MORAL RECOVERY, AND CULTURAL PRESERVATION PROGRAM" (originally Single, ADMIN-only) to Multi, added OG-CSO, saved — confirmed via network inspection the `PUT /api/budget-planning/allocation/programs` request body carried `divisionIds: [1, 6]` (ADMIN + OG-CSO) with a 200 response.
* Reloaded the page fresh: toggle correctly showed **Multi**, both ADMIN and OG-CSO checkboxes remained checked — bug reproduced pre-fix, confirmed fixed post-fix.
* Restored the test program back to its original ADMIN-only assignment afterward; local dev DB left as found.
* `npx tsc --noEmit` / `npx eslint` on the changed file — both clean.

## Out of scope

* No backend or DTO changes — the fix is entirely a frontend state-derivation bug, nothing needed persisting server-side.
* Did not address the pre-existing (unrelated, not user-reported) rapid-double-click race in `handleProgramCheck` where two synchronous checkbox clicks before a re-render can silently drop one of the two — not reproducible under normal single-click usage, noted here only so it isn't rediscovered as a surprise later.
