# RAL-191 — GeneratePRNoAsync: push the sequence lookup to SQL

**Highest-value backend fix in the v1.7.0 milestone** — the only write-path finding in the whole 2026-07-16 performance audit.

Full spec: `docs/v1.7/Mobile_And_Inventory_Findings.md` §3.1. Draft implementation prompt: `docs/v1.7/Ticket_Prompts.md` "RAL-E". Also read `docs/PERFORMANCE_GUIDELINES.md` ("query at the database, not in memory") and `docs/Performance_Audit_2026-07-16.md` §"Tier 3 — Inventory".

## Problem

`PurchaseRequestService.cs:443` (`GeneratePRNoAsync`) loads the **entire **`purchase_requests` table into memory on every single PR creation and string-parses every `PRNo` to find the max sequence. Degrades linearly and forever — the sequence is global, not reset per day.

## Preserve exactly

The sequence is **global and monotonic** — max sequence across ALL PRs ever, not per-day, so `101-1041-GF-2026-07-29-004` can legitimately follow `...-2026-07-28-003`. CLAUDE.md documents the format but not the reset rule — do NOT "fix" this to a per-day reset without Ralph confirming. Write a test that pins current behavior first.

## Scope (TDD — extend `PurchaseRequestServiceTests.cs` with failing tests first)

1. Add `IPurchaseRequestRepository.GetMaxPrSequenceAsync(CancellationToken)` returning `int`, implemented as a single SQL aggregate — no materialized rows.
2. Preserve `ParseSequence`'s tolerance for malformed PRNos (skip, don't fail) so legacy/imported rows can't break creation.
3. Replace the `GetAllAsync` call in `GeneratePRNoAsync` with the new method. Delete `ParseSequence` only if nothing else uses it.
4. Check whether `purchase_requests.PRNo` has a unique index — note the concurrency hole (two simultaneous creates reading the same max) as a follow-up in the PR body rather than expanding scope.

Test cases: empty table → 001; existing max 007 → 008; malformed PRNo rows skipped not fatal; caller-supplied PRNo still bypasses generation.

## Do NOT

Change the PR No. format. Change Manila-timezone date handling. Touch delivery/issue ref generators.
