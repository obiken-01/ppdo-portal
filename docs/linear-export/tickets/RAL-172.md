## Why

The Budget Planning Dashboard's Recent Activity panel showed timestamps that don't look converted to Manila time — e.g. entries reading "7:58:41 AM" for events that happened in the afternoon.

**Root cause**: `AuditService.LogAsync` (`backend/PPDO.Application/Services/AuditService.cs:51`) always writes `ChangedAt = DateTime.UtcNow`, but SQL Server's `datetime2` column type does not persist `DateTimeKind` — every EF Core read of `AuditLog.ChangedAt` comes back with `Kind = Unspecified`, even though the value is genuinely a UTC instant. `System.Text.Json`'s built-in `DateTime` converter only appends a trailing `"Z"` when `Kind == Utc`; for `Unspecified` it emits a bare ISO-8601 string with no timezone marker (e.g. `"2026-07-17T07:58:41.1234567"`). The browser's `new Date(...)` then parses that bare string as **local time**, not UTC — producing a value 8 hours off from the real Manila time it represents.

This bug dates back to [RAL-77](https://linear.app/ralphoksiprojects/issue/RAL-77/api-audit-logging-for-budget-planning-config-records) (`AuditService`) / [RAL-80](https://linear.app/ralphoksiprojects/issue/RAL-80/ui-budget-planning-dashboard) (`RecentActivityDto`/`GetRecentActivityAsync`) — it's pre-existing, not a regression from the recent [RAL-161](https://linear.app/ralphoksiprojects/issue/RAL-161/budget-planning-dashboard-rework-ppdo-scoped-queries-per-divisionfund)/162 Dashboard rework. [RAL-148](https://linear.app/ralphoksiprojects/issue/RAL-148/bug-recent-activity-timestamps-show-browser-locale-time-not-manila-ral) (2026-07-14) already touched this exact panel, but only fixed the **display-side** timezone (`toLocaleString("en-PH", { timeZone: "Asia/Manila" })` in `frontend/src/app/(portal)/budget-planning/page.tsx:722`) — that pins how the browser *renders* a `Date` object, but can't correct a `Date` object that was already constructed from the wrong instant during parsing. Recent Activity is the one place in the UI that renders a full date+time (`toLocaleString`, not just `toLocaleDateString`), which is why the bug is visibly wrong here specifically and not on other pages that only show a calendar date (an 8-hour shift rarely flips the day).

## What shipped

Re-stamped `DateTimeKind.Utc` on `ChangedAt` when building `RecentActivityDto` in `BudgetPlanningDashboardService.GetRecentActivityAsync` (`backend/PPDO.Application/Services/BudgetPlanningDashboardService.cs:224-234`), matching the project's "all timestamps are UTC by convention" rule (CLAUDE.md).

## Verification

* `dotnet test` — 701/701 backend tests pass, including a new regression test `GetRecentActivityAsync_ChangedAtHasUnspecifiedKind_DtoStampsItUtc` that constructs an `AuditLog` with `Kind=Unspecified` (mirroring what EF Core actually returns from a `datetime2` round-trip) and asserts the returned DTO's `ChangedAt.Kind == Utc`.
* **Not yet verified live** — CI runners are currently unavailable (flagged by Ralph), and this session has no live dev-server verification against real audit data yet. Do that once a runner/local server is available.

## Out of scope (flagged, not fixed here)

This `DateTimeKind`-loss-on-SQL-round-trip pattern is **systemic**, not limited to Recent Activity — every `DateTime`-typed field returned by the API has the same latent exposure: `CreatedAt`/`UpdatedAt` (auto-stamped on every entity via `AppDbContext.SaveChangesAsync`'s interceptor), `CalendarEvent.StartDate`/`EndDate`, and dozens of other DTO fields across Users, Announcements, WFP, LDIP, AIP, Config, Delivery, Items, and PurchaseRequest. A proper global fix (an EF Core `ConfigureConventions` value converter stamping every `DateTime` property `Utc` on read, in `AppDbContext.cs`) would close this for good in one place — but it touches every entity's read path across the whole app and needs its own dedicated audit + regression pass, not a drive-by bundled into this narrow fix. Worth a follow-up ticket if more full-timestamp (not just date) displays get added elsewhere.
