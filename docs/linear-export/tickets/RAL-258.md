# RAL-258 — Office config: default landing page + host-office flag (DECISION F)

**V18-12** — plan: `docs/v1.8/Phase_Plan.md` §3.2. **Scope widened 2026-08-25 — size S → M.** This ticket now carries two parts: the landing-page field (Part 1, as originally written) and the settled DECISION F host-office change (Part 2). Depends on V18-16 ([RAL-251](https://linear.app/ralphoksiprojects/issue/RAL-251/landing-page-schema-resolution-chain-user-division-office-fallback)) for the schema and the enum.

Surface the office-level default landing page on the Office config page (`config/offices`) — the third link in the resolution chain, used when neither the user nor their division has a preference. In practice this is what makes "every user in GSO opens on Budget Planning" a one-line setup rather than 20 per-user edits.

**Scope:**

* The `LandingPage` field on the office form, using the permission-aware selector from V18-20.
* Include it in the page's **CSV download/upload round-trip** — that is how offices are seeded, and a column that exists in the form but not the CSV will quietly reset on the next bulk upload.
* `CanManageConfig` gate as with the rest of the page.

Part 1 is independently shippable and does not depend on Part 2.

## Part 2 — DECISION F: retire `OfficeId == null` as the PPDO discriminator

**✅ Decided 2026-08-25** (`docs/v1.8/Phase_Plan.md` §3.1, and the V18-12 detail table in §3.2). Ralph chose the full change over the half-measure.

**Implementation status — built, not merged.** Steps a–h all landed in commit `f35c47c` (62 files) on `feature/v1.8.0-ral-252-258-259-landing-cluster`; PR #257 is **open** against `release/1.8.0`. Verified in the branch: the filtered unique index `UX_offices_is_host_office` enforces one-host-office-only in the database rather than in application code; the backfill runs as `UPDATE Users SET OfficeId = @hostOfficeId WHERE OfficeId IS NULL`; `OfficeScope.Resolve` is now `IsHostOfficeUser(user) ? All : For(...)`; `.Include(u => u.Office)` is on five `UserRepository` paths; and `PpdoOfficeCode` / `GetByCodeAsync("PPDO")` / `PPDO_OFFICE_CODE` return **zero** hits outside tests. ⚠️ **CI does not run EF migrations** — this release needs a manual `dotnet ef database update` against Azure SQL before deploy, and the backfill is not reversible in the way a schema-only migration is (the down path leaves every user pointing at the host office).

**The problem.** PPDO is identified two different ways today, and neither points at the other:

1. PPDO as a **data owner** — a real `offices` row, found by three hardcoded `"PPDO"` string lookups.
2. PPDO as a **person** — `users.office_id IS NULL`, which is what grants cross-office access.

Nothing enforces that the two agree. Worse, the null is inverted against `DivisionScope`: a null division means *sees nothing*, a null office means *sees everything*. Its only defence today is a 15-line warning comment in `OfficeScope.cs`.

**Why now, in Phase 1.** There are no production office accounts yet, so the backfill is a single `UPDATE`. And Phase 2's V18-32 (AIP ownership FK) builds directly on the scope resolver — changing after that means re-touching every ownership check.

**✅ Flag name settled 2026-08-25: **`IsHostOffice` (column `offices.is_host_office`). Chosen over `IsPpdo` because what it governs is cross-office authority, not which office happens to hold it — it survives the office being renamed or restructured. The tracker's `IsPpdo` is superseded.

**⚠️ Open sub-question raised during implementation — what a null **`users.office_id` **means afterwards.** Today null *positively* means PPDO. Once the flag is the discriminator, null becomes genuinely "unassigned", and the safe reading flips from *see everything* to *see nothing*. Two routes: make `users.office_id` NOT NULL (schema-level certainty, but the user form must then assign the host office explicitly instead of leaving it blank), or keep it nullable and give `OfficeScope` the `SeeNothing` state its doc comment currently says it deliberately lacks — that asymmetry with `DivisionScope` only existed *because* null meant PPDO, so it stops being justified here.

**Unblocks:** Phase 2 no longer waits on DECISION F. V18-32 (AIP ownership FK) now blocks on DECISIONS A and E only.
