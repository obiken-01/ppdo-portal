# RAL-238 — AIP import: detect hierarchy level from the description column, not the ref-code segment count

`AipXlsmParser` decides whether a row is an Office / Program / Project / Activity by counting `-` segments in the AIP reference code (`CountSegments()`, `switch (segments)` cases 5/6/7/8). The province's real FY2027 AIP does not encode reference codes consistently, so this misreads 82 of 2,887 rows and silently loses or misfiles ₱679.2M.

Verified against `AIP_2027_PGOM_Test.xlsm` (the province's own FY2027 AIP — 2,887 titled rows, 1,452 money lines, ₱17.78bn). Two copies were compared and are byte-identical in content, so this is the province's encoding, not a local edit.

The reliable indicator is **which description column holds the text**: B = Office, C = Program, D = Project, E = Activity. Columns B:E are merged as `B8:E9` in the header and function as indent columns.

## Three distinct failure modes

**1. Mis-coded level creates phantom offices with empty names — SOCIAL, ₱627.8M misfiled.**
Six rows carry a 5-segment (Office) code but their text sits in column C, i.e. they are visually Programs. `case 5:` reads the office name from column B, which is blank, so the parser creates a nameless `ParsedAipOffice` and every following row attaches to it instead of the real office above.

| Row | Ref code | Activities absorbed | Amount |
| -- | -- | -- | -- |
| 24 | `3000-000-1-01-003` | 1 | ₱1,836,614 |
| 27 | `3000-000-1-01-004` | 1 | ₱1,962,308 |
| 30 | `3000-000-1-01-005` | 2 | ₱6,000,000 |
| 35 | `3000-000-1-01-006` | 2 | ₱1,561,570 |
| 40 | `3000-000-1-01-007` | 10 | ₱3,870,000 |
| 56 | `3000-000-1-01-008` | 32 | ₱612,575,000 |

The real owning offices (`OFFICE OF THE GOVERNOR - AKAP-HUB` r23, `- HOUSING` r34, `- LOCAL SCHOOL BOARD` r55) end up missing that work.

**2. Segment count outside 5–8 is silently dropped — ECONOMIC, ₱38.5M lost.**
The `switch` has no default branch (comment: *"Other segment counts are skipped (totals rows, etc.)"*). Seven activity rows under `OFFICE OF THE PROVINCIAL AGRICULTURIST` carry 9-segment codes with their text in column E, so they vanish with no error:

`8000-000-1-01-016-004-001-003-001` (₱2,032,945) · `-003-002` (₱2,071,300) · `-003-003` (₱12,128,060) · `-004-001` (₱6,163,921) · `-005-001` (₱659,081) · `-005-002` (₱13,582,375) · `-006-001` (₱1,875,000)

**3. Blank ref code on a Project row orphans its children — OTHERS, ₱12.9M lost.**
`OTHERS_FY2027` row 228 has a project description in column D but an empty column A. Blank col A is treated as a multi-line continuation of the previous *activity*, but the previous row (227) was a Program, so `lastActivity` is null and the row is skipped without creating a project. Rows 229–233 then hit `case 8: if (currentProject is null) break;` and are all dropped — ₱12,892,500 under `ENVIRONMENT AND NATURAL RESOURCES OFFICE` › `SUSTAINABLE MINERAL PROGRAM`.

## Scope note — PPDO's own data is unaffected

Both PPDO blocks are clean: `GENERAL` rows 380–571 (190 titled rows, 127 money lines) and `ECONOMIC` rows 1051–1056 (6 rows, 4 money lines), zero mismatches, code depths strictly 6/7/8. All 82 mismatches belong to five other offices — Governor's Office sub-units (Local School Board 39, Housing 20, AKAP-HUB 10), Provincial Agriculturist 11, Provincial Engineer's 2. So this is not corrupting anything of PPDO's today, which is why it is scheduled rather than hotfixed.

## Why now

D2 is confirmed: the printable AIP form will be derived from this same structure (v1.8.0 requirements review, answered 2026-08-19 from the sample file). Deriving an exporter from a level-detection rule that is wrong on 2.8% of real rows bakes the defect into the output side too.

TDD: extend `backend/PPDO.Tests/Infrastructure/AipXlsmParserTests.cs` with failing tests first, then implement.

1. Add a `DetectLevel(IXLWorksheet ws, int row, int segments)` helper returning a level. Resolution order: **first non-blank of columns B, C, D, E wins** (B=Office, C=Program, D=Project, E=Activity); fall back to the segment count only when B–E are all blank. Keep `CountSegments` for that fallback.
2. Replace `switch (segments)` with `switch (level)`. Remove the silent skip for out-of-range segment counts — a row with text in a description column must be classified even at 9 segments. Rows with no description text and no usable segment count keep being skipped (header rows, `TOTAL`, `GRAND TOTAL`).
3. Handle failure mode 3: when column A is blank but description column C or D holds text, treat the row as a Program/Project node rather than an activity-name continuation. Continuation applies only when the blank-A row's text is in column E **and **`lastActivity` is not null. Generate a synthetic ref code for such a node (e.g. parent ref + `-` + ordinal) so downstream FKs still have a key — document the format in the XML doc block.
4. Make the guard clauses in the Program/Project/Activity cases non-silent. When a node arrives without its parent (`currentProject is null` on an activity), synthesize an "(unassigned)" parent under the current office rather than dropping the row. Losing ₱12.9M with no error is the worst property of the current code; nothing should be discarded silently.
5. Update the XML doc block at the top of the class — the documented "Hierarchy detection: segment count in the ref code" rule is what led to this defect.
6. Verify `TryParseLineItem` ([RAL-108](https://linear.app/ralphoksiprojects/issue/RAL-108/aip-import-capture-line-item-detail-at-programproject-level-currently) synthetic leaves) still fires for Program/Project rows carrying line-item columns — it keys off the same level decision.
