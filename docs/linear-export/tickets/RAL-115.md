## 0. Why this exists

[RAL-114](https://linear.app/ralphoksiprojects/issue/RAL-114/ldip-no-way-to-correct-an-uploaded-multi-office-record) fixes "no way to correct an uploaded LDIP record" by letting PPDO re-upload a corrected file to replace the whole document's hierarchy. That covers every correction case, but it's coarse — fixing one typo in one program's name means re-editing the source Excel and re-uploading all ~31 offices / ~205 programs again. This ticket is the finer-grained alternative: edit a single program's fields directly in the app, no file round-trip required.

## 1. Scope

Two independent capabilities, either or both may ship:

1. **Edit an existing program's fields in place** — name, budget, and the full [RAL-113](https://linear.app/ralphoksiprojects/issue/RAL-113/ldip-file-upload-activity-level-fields-mirror-aip-upload) upload-detail set (implementing office, start/end date, expected outputs, funding source raw text, PS/MOOE/CO, CC adaptation/mitigation/typology, PDP/RDP, SDGs, Sendai Framework, NDRRM Plan, NSP, PDPDFP). Ref code is **unchanged** — no renumbering needed since nothing is added or removed.
2. **Add/remove a single program within an existing office group** (optional, bigger lift) — needs to extend or renumber that specific ref-code group's sequence without touching other groups/offices in the document, unlike the full-document rebuild `BuildHierarchy` already does for [RAL-113](https://linear.app/ralphoksiprojects/issue/RAL-113/ldip-file-upload-activity-level-fields-mirror-aip-upload)/[RAL-114](https://linear.app/ralphoksiprojects/issue/RAL-114/ldip-no-way-to-correct-an-uploaded-multi-office-record).

## 2. Design sketch

* **New endpoint**: `PUT /api/budget-planning/ldip/{id}/programs/{programId}` — gated by `CanUploadAip`. Accepts the full field set as a DTO. Re-resolves `FundingSourceRaw` → `FundingSourceId`/`FundingSourceSnapshot` via the same lookup `BuildHierarchy` already uses. Updates only that program row; `RefCode` untouched.
* **If add/remove is in scope**: `POST .../programs` and `DELETE .../programs/{programId}` — extract the "renumber a group's programs continuously" logic out of `BuildHierarchy` into a reusable helper so both the full-rebuild path and this scoped path share one implementation.
* **Frontend**: `LdipForm`'s "Created Programs" table rows become editable in place. Save/Cancel per row.
* **Open question to confirm before building**: should this editing capability extend to MANUALLY-created programs too? Recommendation: start upload-detail-only.

## 3. Why this is more work than [RAL-114](https://linear.app/ralphoksiprojects/issue/RAL-114/ldip-no-way-to-correct-an-uploaded-multi-office-record) (Option A)

* New endpoint(s) + DTOs for partial program updates, vs. [RAL-114](https://linear.app/ralphoksiprojects/issue/RAL-114/ldip-no-way-to-correct-an-uploaded-multi-office-record) reusing the existing upload/confirm endpoints with one extra field.
* Real inline-edit UI covering ~19 fields per row, vs. [RAL-114](https://linear.app/ralphoksiprojects/issue/RAL-114/ldip-no-way-to-correct-an-uploaded-multi-office-record) reusing the already-built upload/preview pages with zero new form fields.
* If add/remove is included: a new "renumber one ref-code group in isolation" code path that must stay behaviorally identical to `BuildHierarchy`'s full-rebuild numbering.

## Acceptance Criteria (edit-in-place only; add/remove is a stretch goal within this ticket)

- [ ] `PUT /api/budget-planning/ldip/{id}/programs/{programId}` updates one program's editable fields, re-resolving FundingSourceRaw
- [ ] RefCode, LdipOfficeId, and program identity are immutable through this endpoint
- [ ] Gated by `CanUploadAip`; validates the parent record is `Status == Draft`
- [ ] `LdipForm`'s Created Programs table supports per-row inline edit (Save/Cancel, field-level errors) instead of only the read-only detail panel
- [ ] Existing manual "+ Add Program" flow and [RAL-114](https://linear.app/ralphoksiprojects/issue/RAL-114/ldip-no-way-to-correct-an-uploaded-multi-office-record)'s re-upload flow are both unaffected
