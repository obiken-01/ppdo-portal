## 0. Why this exists

[RAL-178](https://linear.app/ralphoksiprojects/issue/RAL-178/aip-allow-re-uploading-a-corrected-file-into-an-existing-aip-record) fixes "no way to correct an uploaded AIP" by letting PPDO re-upload a corrected file to replace the whole document's hierarchy. That covers every correction case but is coarse — fixing one typo in one activity means re-editing the source Excel and re-uploading potentially hundreds of activities across every office again. This ticket is the finer-grained alternative: edit a single node's fields directly in the app, no file round-trip.

## 1. Scope

Edit an existing **activity's** fields in place first (name, ESRE code, implementing office, schedule, expected outputs, funding source, PS/MOOE/CO, CC fields) — activities already have every field column (`backend/PPDO.Domain/Entities/AipActivity.cs`), so this can ship independently of [RAL-108](https://linear.app/ralphoksiprojects/issue/RAL-108/aip-import-capture-line-item-detail-at-programproject-level-currently).

Program/project-level field editing is blocked on [RAL-108](<https://linear.app/ralphoksiprojects/issue/RAL-108/aip-import-capture-line-item-detail-at-programproject-level-currently>) shipping first (those entities have nowhere to store the detail yet) — sequence that sub-scope after [RAL-108](https://linear.app/ralphoksiprojects/issue/RAL-108/aip-import-capture-line-item-detail-at-programproject-level-currently), or drop it from this ticket entirely and let the synthetic-leaf/extend approach's own follow-up cover it, whichever [RAL-108](https://linear.app/ralphoksiprojects/issue/RAL-108/aip-import-capture-line-item-detail-at-programproject-level-currently) lands as.

Ref code, hierarchy position (which project/program/office a node belongs to), and record identity are NOT editable through this endpoint — moving a node is a bigger structural change, not a field correction.

## 2. Design sketch (mirrors [RAL-115](https://linear.app/ralphoksiprojects/issue/RAL-115/ldip-inline-per-program-editing-for-uploaded-records-option-b-follow)'s shape)

* New endpoint: `PUT /api/budget-planning/aip/{id}/activities/{activityId}` — gated by `CanAccessBudgetPlanning` (unlike upload, which is `CanUploadAip`-only — editing an already-imported record's fields is a correction, not a new import, so it doesn't need the PPDO-only upload gate; confirm this reasoning holds before shipping, since it's a deliberate deviation from [RAL-115](https://linear.app/ralphoksiprojects/issue/RAL-115/ldip-inline-per-program-editing-for-uploaded-records-option-b-follow)'s LDIP equivalent which stayed `CanUploadAip`-gated because LDIP's upload-detail fields were considered upload-owned data). Accepts the editable field set as a DTO. Re-resolves `FundingSourceSnapshot` from a `FundingSourceId` the same way import does.
* Frontend: `aip/detail/page.tsx`'s activity rows (currently plain read-only `<td>`s, see the file's own doc comment: "AIP Detail page — read-only hierarchy view") need an edit affordance — likely an "Edit" toggle per row swapping cells to inputs (`MoneyInput` for PS/MOOE/CO/CC amounts), Save/Cancel per row, not a whole-page submit. This is a bigger UI lift than [RAL-115](https://linear.app/ralphoksiprojects/issue/RAL-115/ldip-inline-per-program-editing-for-uploaded-records-option-b-follow)'s LDIP table since the detail page is a deep collapsible tree (office→program→project→activity), not a flat table.
* Only allowed when the parent `AipRecord.Status == "Draft"`.

## 3. Why this is more work than [RAL-178](https://linear.app/ralphoksiprojects/issue/RAL-178/aip-allow-re-uploading-a-corrected-file-into-an-existing-aip-record)

* New endpoint + DTO for partial activity updates, vs. [RAL-178](https://linear.app/ralphoksiprojects/issue/RAL-178/aip-allow-re-uploading-a-corrected-file-into-an-existing-aip-record) reusing the existing upload/confirm endpoints with one extra field.
* Real inline-edit UI on a nested collapsible tree view, not a flat table like LDIP's `LdipForm` — more layout work than [RAL-115](https://linear.app/ralphoksiprojects/issue/RAL-115/ldip-inline-per-program-editing-for-uploaded-records-option-b-follow) had.

## Acceptance Criteria (activity-level edit-in-place only; program/project-level is a stretch goal blocked on [RAL-108](https://linear.app/ralphoksiprojects/issue/RAL-108/aip-import-capture-line-item-detail-at-programproject-level-currently))

- [ ] `PUT /api/budget-planning/aip/{id}/activities/{activityId}` updates one activity's editable fields, re-resolving `FundingSourceId` → `FundingSourceSnapshot`
- [ ] RefCode, ProjectId, and activity identity are immutable through this endpoint
- [ ] Validates the parent `AipRecord.Status == "Draft"`
- [ ] `aip/detail/page.tsx`'s activity rows support per-row inline edit (Save/Cancel, field-level errors) instead of pure read-only display
- [ ] Existing upload/re-upload ([RAL-178](https://linear.app/ralphoksiprojects/issue/RAL-178/aip-allow-re-uploading-a-corrected-file-into-an-existing-aip-record)) flows are unaffected

## Out of scope

* Program/project-level field editing (blocked on [RAL-108](https://linear.app/ralphoksiprojects/issue/RAL-108/aip-import-capture-line-item-detail-at-programproject-level-currently); revisit once that ships).
* Moving a node to a different parent, or renumbering ref codes.
* [RAL-178](https://linear.app/ralphoksiprojects/issue/RAL-178/aip-allow-re-uploading-a-corrected-file-into-an-existing-aip-record)'s re-upload flow — this ticket is purely additive to it.
