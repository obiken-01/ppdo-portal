# RAL-158 — WFP Report: fix N+1 queries in report generation (~30s load, 100% CPU)

> Bundled into **v1.4.3** at Ralph's request (not part of the fund-source scope, but shipping on the same release branch). Child of the WFP Rework epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> Working branch: `release/1.4.3`. Feature branch off `release/1.4.3`; PR targets `release/1.4.3` (NOT `main`).
> Backend-only.

## Why

Live Application Insights "Live metrics" trace (2026-07-15, production `ppdo-portal-api`) captured generating the WFP Report ("all divisions consolidated") taking **~30 seconds** with **CPU pegged at 100%**, dominated by a burst of dozens of sequential `Executed DbCommand` calls (~195-197ms each) each filtered by a single `@__expenditureId_0`-style parameter — the classic N+1 signature. This also isn't free: every one of those ~150 round trips burns vCore-seconds on the Azure SQL serverless tier, which contributes directly to hitting the monthly free-compute cap sooner (we hit that cap earlier today).

Root cause is **three nested layers of N+1**, all in the WFP report read path:

1. `WfpReportService.BuildWfpActivityMapAsync` (`backend/PPDO.Application/Services/WfpReportService.cs:179-196`) loops over every `WfpRecord` (one per division with a started WFP) and calls `_wfpRepo.GetActivitiesByWfpIdAsync(record.Id, ct)` once per record.
2. `WfpReportService.GetReportAsync` (same file, lines 143-151) loops over every `AipActivity`, then over every `wfpActivityId` for it, calling `_expenditures.GetByActivityIdAsync(wfpActivityId, ct)` once per (activity × division) pair. The class doc (lines 8-24) already flags this layer as a known, accepted N+1 — but that comment predates layer 3 below, which is the one actually dominating the 30s.
3. `WfpExpenditureService.GetByActivityIdAsync` (`backend/PPDO.Application/Services/WfpExpenditureService.cs:76-88`) loops over every `WfpExpenditure` row and fires **two** separate queries per row — `GetPeriodsByExpenditureIdAsync` and `GetProcurementItemsByExpenditureIdAsync` (`backend/PPDO.Infrastructure/Repositories/WfpExpenditureRepository.cs:19-32`), each `WHERE ExpenditureId == expenditureId`.

For "all divisions consolidated" this is roughly `(# WfpRecords)` + `(# wfp_activity rows across all divisions)` + `2 × (# WfpExpenditure rows across all those activities)` round trips — consistent with the observed ~150-query, ~30s burst.

Same method also has two smaller `CLAUDE.md`-violating spots (Query at the database, not in memory): `GetReportAsync` loads `_officeRepo.GetAllAsync()` then does `.FirstOrDefault(o => o.Id == officeId)`, and `_aipRepo.GetAllAsync()` then filters/orders in memory to find the primary AIP record for the fiscal year. Both should push the filter to SQL via the already-exposed `IRepository<T>.Query()` IQueryable, not add a new repository method.

## Scope

Batch the three N+1 layers into `IN (...)`-style queries (the codebase already has this exact pattern — see `IWfpRepository.GetLinesByActivityIdsAsync(IReadOnlyList<int> activityIds)`). No change to the report's output/DTO shape, no change to the WFP entry wizard's endpoints (the singular `GetByActivityIdAsync`/`GetActivitiesByWfpIdAsync` methods stay, used by other callers), no change to ceiling/fund-scoping logic from [RAL-154](https://linear.app/ralphoksiprojects/issue/RAL-154/fund-source-scoped-ceiling-allocation-and-wfp-check-backend)/155/156.

## Steps

1. `IWfpExpenditureRepository` + `WfpExpenditureRepository`: add `GetByWfpActivityIdsAsync(IReadOnlyList<int> wfpActivityIds)` (`WHERE WfpActivityId IN (...)`), `GetPeriodsByExpenditureIdsAsync(IReadOnlyList<int> expenditureIds)`, `GetProcurementItemsByExpenditureIdsAsync(IReadOnlyList<int> expenditureIds)` (each `WHERE ExpenditureId IN (...)`) — mirror `IWfpRepository.GetLinesByActivityIdsAsync`'s existing shape exactly.
2. `IWfpRepository` + `WfpRepository`: add `GetActivitiesByWfpIdsAsync(IReadOnlyList<int> wfpIds)` (`WHERE WfpId IN (...)`).
3. `WfpExpenditureService`: add `GetByActivityIdsAsync(IReadOnlyList<int> wfpActivityIds, ct)` — calls the 3 new batched repo methods once each, groups periods/items in memory by `ExpenditureId` (`ToLookup`/`Dictionary<int, List<T>>`), returns expenditures grouped by `WfpActivityId`. Keep the existing singular `GetByActivityIdAsync` untouched (still used by the entry wizard).
4. `WfpReportService.BuildWfpActivityMapAsync`: replace the per-record loop with one call to `GetActivitiesByWfpIdsAsync(wfpRecords.Select(r => r.Id).ToList())`, then group the single result set in memory by `WfpId`/`AipActivityId`.
5. `WfpReportService.GetReportAsync`: replace the nested per-`wfpActivityId` loop with one call to the new `GetByActivityIdsAsync` across every `wfpActivityId` collected from `wfpActivityIdsByAipActivityId`, then re-key the single result into `expendituresByAipActivityId` using that same map.
6. Same method: replace `(await _officeRepo.GetAllAsync(ct)).FirstOrDefault(o => o.Id == officeId)` with `await _officeRepo.Query().FirstOrDefaultAsync(o => o.Id == officeId, ct)`; replace the AIP-record `GetAllAsync().Where(...).OrderBy(...).FirstOrDefault()` with the same filter/order pushed through `_aipRepo.Query()...FirstOrDefaultAsync(ct)`. Both use the already-exposed `IRepository<T>.Query()` — no new interface method.
7. Run the full backend test suite; confirm report output is unchanged for a real multi-division fixture.
8. Verify live: reproduce the original "Generate Preview" scenario (all divisions consolidated) in Application Insights Live Metrics — confirm the `@__expenditureId_0` burst is gone, total DbCommand count for the request drops from ~150 to roughly 5-8, and request duration drops from ~30s to low single-digit seconds.
