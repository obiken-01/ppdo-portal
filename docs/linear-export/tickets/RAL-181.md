# RAL-181 — AIP: create an office's programs from its LDIP (LDIP → AIP program list)

> 🌿 Working branch: `release/1.5.0` (off `main`). PR targets `release/1.5.0`, NOT `main` directly. Child of epic [RAL-59](<https://linear.app/ralphoksiprojects/issue/RAL-59/budget-planning-management-feature-ldip-aip-and-wfp-web-pages>).
> 📌 Created 2026-07-22 from Ralph's request: when creating a new AIP for an office, seed its **programs** (not projects/activities) from that office's existing **LDIP** — since an LDIP is a multi-year planning document that's really just "a list of programs" per office/sector.
> 📌 **Sibling ticket: **[RAL-180](<https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry>) is the same idea but sourced from a *prior AIP* (full Office→Program→Project→Activity depth, amounts carry over). This ticket sources from the office's **LDIP** instead — structurally shallower (LDIP is Office→Program only, confirmed below) and semantically different (LDIP amounts are multi-year totals, not a single fiscal year's budget — see "why amounts don't carry over" below). Reuse [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry)'s find-or-create-target-record/office plumbing where it overlaps; the two are separate tickets because the source data shapes are different enough to need separate mapping logic.

## 0. Why this exists

An LDIP (`backend/PPDO.Domain/Entities/LdipRecord.cs`, [RAL-61](https://linear.app/ralphoksiprojects/issue/RAL-61/ui-ldip-entry-form-createedit)) is a multi-year document (`FiscalYearStart`–`FiscalYearEnd`) that lists an office's planned programs, one per `LdipProgram` row. It's genuinely only a 2-level hierarchy — confirmed by `LdipProgram`'s own doc comment: *"Unlike AIP (Office → Program → Project → Activity), the real LDIP source file is only a 2-level hierarchy — the 6-segment Program row IS the leaf."* When PPDO starts a new fiscal year's AIP for an office that already has an approved LDIP, the program list shouldn't be retyped by hand — it should seed straight from the LDIP. This ticket adds that seed step; the resulting AIP programs still need their Projects/Activities (this year's actual budget breakdown) filled in afterward via [RAL-62](<https://linear.app/ralphoksiprojects/issue/RAL-62/ui-aip-entry-form-createedit>)'s manual entry.

## 1. Why LDIP amounts do NOT carry over (unlike [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry))

`LdipProgram.Budget` is documented as *"Combined budget for the document's full year range, in thousands"* — a multi-year total across `FiscalYearStart`–`FiscalYearEnd`, not a single fiscal year's figure. Splitting that into one year's PS/MOOE/CO isn't something the system can do validly — it needs a human decision. So this ticket copies **names and ref codes only**; `Budget`/`Ps`/`Mooe`/`Co`/`FundingSourceId`/schedule/`ExpectedOutputs`/CC fields on `LdipProgram` are **not** copied anywhere. (Contrast [RAL-180](<https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry>), which copies amounts as-is — there the source IS a single prior fiscal year's real AIP budget, a valid starting estimate for the next year.)

## 2. Scope

Single office + sector (an `LdipOffice` row), matching how [RAL-62](<https://linear.app/ralphoksiprojects/issue/RAL-62/ui-aip-entry-form-createedit>)'s `AddOfficeAsync` and [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry) both operate one office+sector at a time:

1. User picks a **target fiscal year** and a **target office** (+ sector, since an office can have multiple `LdipOffice` sector groups in one LDIP — same "office can span sectors" reality as AIP, see [RAL-62](<https://linear.app/ralphoksiprojects/issue/RAL-62/ui-aip-entry-form-createedit>)'s office-name fix).
2. System resolves the matching `LdipOffice` (via `LdipRecord.OfficeId` = the config office, then that record's `LdipOffice` row for the chosen sector). No match → nothing to seed from, surface a clear message ("this office has no LDIP for the X sector").
3. That `LdipOffice`'s programs are listed as checkboxes — **Select All checked by default** (same UX shape as [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry)).
4. On confirm: find-or-create the target `AipRecord` (Manual entry-source) for the fiscal year, find-or-create the target `AipOffice` (same `RefCode`/`Name`/`Sector` as the `LdipOffice` — reuse [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry)'s find-or-create logic verbatim, it's identical here). For each selected `LdipProgram`, create an `AipProgram`:
   * `RefCode` = the `LdipProgram`'s own `RefCode` **as-is** — its doc comment confirms it's already a correctly-formatted AIP program ref code (parent ref code + 3-digit sequence), so no recomputation needed, same reuse-source-ref-codes approach as [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry).
   * `Name` = `LdipProgram.Name`.
   * `FunctionBand` defaults to `CORE` (LDIP has no equivalent field — same default [RAL-62](<https://linear.app/ralphoksiprojects/issue/RAL-62/ui-aip-entry-form-createedit>) uses for manually-added programs).
   * No `AipProject`/`AipActivity` rows are created — the program is a bare shell until the user fills it in.
5. Collision guard: if a program with that `RefCode` already exists under the target office, reject the whole request with a clear message listing the collisions (identical behavior to [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry) — don't silently skip/overwrite).

## 3. Design sketch

* Likely a new endpoint, e.g. `POST /api/budget-planning/aip/seed-programs-from-ldip`:

  ```json
  { "targetFiscalYear": 2028, "officeConfigId": 7, "sector": "GENERAL", "ldipProgramIds": [12, 13, 15] }
  ```

  `CanAccessBudgetPlanning`-gated, same reasoning as [RAL-62](<https://linear.app/ralphoksiprojects/issue/RAL-62/ui-aip-entry-form-createedit>)/[RAL-179](<https://linear.app/ralphoksiprojects/issue/RAL-179/aip-inline-per-node-editing-for-existing-records-option-b-follow-up-to>)/[RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry).
* Frontend: likely lives alongside [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry)'s "copy from a prior year" entry point — the AIP creation flow may end up with FOUR ways to seed content (Upload / Manual Entry / Copy from Prior AIP / Seed from LDIP). Consider whether these should be four tabs or a single "start from…" picker; implementer's call, but keep the actual seeding logic in the backend service, not duplicated per source type.
* TDD: extend `AipServiceTests.cs` — find-vs-create target record/office (shared pattern with [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry)'s tests, may be extractable into a shared test helper if [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry) ships first), RefCode reuse fidelity, FunctionBand defaults to Core, collision guard, no Project/Activity rows created, no LDIP budget/detail fields leak into the new AipProgram, no-matching-LdipOffice-for-sector error message.

## Acceptance Criteria

- [ ] New endpoint creates `AipProgram` rows (Name + RefCode only, `FunctionBand = CORE`) from a selected office+sector's `LdipOffice.Programs`
- [ ] Target `AipRecord`/`AipOffice` found-or-created using the same rules as [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry)
- [ ] `LdipProgram.RefCode` is reused as-is for the new `AipProgram.RefCode`
- [ ] No `AipProject`/`AipActivity` rows are created — programs come in as bare shells
- [ ] No `LdipProgram` budget/funding-source/schedule/CC/alignment-tag fields are copied anywhere
- [ ] Collision guard: a `RefCode` that already exists under the target office is rejected with a clear error, not silently skipped/overwritten
- [ ] Clear error when the office has no `LdipOffice` for the chosen sector
- [ ] Frontend: office+sector+program picker, checkboxes, Select All checked by default

## Out of scope

* Carrying `LdipProgram`'s budget/funding-source/schedule/expected-outputs/CC fields into the new AIP in any form (including as a synthetic Activity per [RAL-108](<https://linear.app/ralphoksiprojects/issue/RAL-108/aip-import-capture-line-item-detail-at-programproject-level-currently>)'s pattern) — explicitly rejected per the "why amounts don't carry over" reasoning above. Revisit only if Ralph asks for it separately.
* Creating Projects/Activities under the seeded programs — that's [RAL-62](<https://linear.app/ralphoksiprojects/issue/RAL-62/ui-aip-entry-form-createedit>)'s manual entry, unchanged.
* Any lineage/source tracking between the LDIP and the new AIP programs (no schema for it today, same "no lineage" call as [RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry)).
* A unified "start from…" picker UI across Upload/Manual/[RAL-180](https://linear.app/ralphoksiprojects/issue/RAL-180/aip-copy-an-offices-programsactivities-from-a-prior-fiscal-year-carry)/this ticket — nice-to-have, not required for this ticket to ship.
