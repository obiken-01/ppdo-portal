# RAL-231 — WFP entry: 1.58 MB price-index fetch blocks the AIP/Office selectors on mount

Found during the 2026-08-13 branch audit (see the `archive/*` tags and `docs/v1.8/`). The last unlanded piece of the v1.4.6 performance work — but the reason it is still worth doing turned out to be different from what that branch assumed.

## Measured, not assumed

Against local dev (`price_index_items` = **6,398 rows**), the four mount-time fetches in `wfp/entry`:

| Endpoint | Warm time | Payload |
| -- | -- | -- |
| `config/price-index?active=true` | ~113 ms | **1,578 KB** |
| `budget-planning/aip` | ~20 ms | 5 KB |
| `config/offices?active=true` | ~13 ms | 2 KB |
| `config/accounts/reserve-rate` | ~3 ms | <1 KB |

All four are bundled into one `Promise.all` (`wfp/entry/page.tsx` ~line 927), and `resourcesLoading` gates the whole selector row on it. So the AIP/Office/Division dropdowns cannot paint until **1.58 MB** has transferred.

## Why the existing "deliberately bundled" comment does not settle it

The comment above that call says the bundling is intentional so "the rest of the session never waits on a fetch for this data again". That was written by `f841184` (2026-07-18), which fixed the *query* — `PriceIndexService.GetAllAsync` was loading the whole table into memory before filtering; it now pushes the WHERE/ORDER BY to SQL.

That fix is real and is not in question. But it addressed **latency**, and the remaining cost is **payload**: 1.58 MB still crosses the wire before the selectors appear. On a provincial-office connection that is seconds of blank dropdowns, and `CLAUDE.md`'s own guidance ("don't ship heavy fields a view never renders — a fat AIP DTO produced a 1.2 MB response") points the same way.

So the two same-day approaches were complementary, not alternatives: `f841184` made the query fast, and the abandoned branch made it non-blocking. Only the first landed.

## Scope

Decouple the price-index fetch from the mount `Promise.all` so the selectors paint on the fast three. The catalogue is only needed once the user opens the Procurement/Combined expenditure wizard, which is several interactions later.

Reference (do **not** cherry-pick — it conflicts, the branch is ~262 commits behind):

```
git show archive/fix/v1.4.6-budget-planning-query-perf
```

That version fired the fetch and swallowed errors silently. Improve on it: if the user reaches the item picker before the catalogue arrives, they must not see a silently empty search. Thread a `priceIndexLoading` flag down to `WfpProcurementItemTable` and swap the `Lookup` placeholder while it loads. Do not disable the control — the "Free-typed item (no price index link)" path must stay usable throughout.

## Steps

1. Remove `listPriceIndex` from the mount `Promise.all`; keep `resourcesLoading` covering only the fast three.
2. Add a separate effect + `priceIndexLoading` state for the catalogue.
3. **Replace the "Deliberately loaded together" comment** — it will be actively misleading. Record why the split is now correct and that `f841184`'s query fix is untouched.
4. Thread `priceIndexLoading` through `ExpenditureWizard` into both `WfpProcurementItemTable` call sites (~751, ~824) and the wizard at ~1767.
5. Loading placeholder on the `Lookup`; keep free-typing available.
6. Verify live: selectors paint before the 1.58 MB response completes; item picker still works once loaded; opening the wizard early shows the loading affordance, not an empty list.

## Out of scope

Slimming the price-index DTO itself (~250 bytes/row × 6,398). That is the deeper fix and probably the right long-term one, but it is a separate change with its own blast radius — worth its own ticket.
