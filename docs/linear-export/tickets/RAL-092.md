# RAL-92 — Perf: recent-activity audit query — stop loading the entire audit_log

## Context

Scalability audit (2026-06-22) flagged this as the **fastest-degrading** query in the portal. The dashboard "recent activity" feed loads the **entire** `audit_log` **table plus ALL users** into memory just to display the last 10 rows.

> 🌿 **Working branch:** create feature branch off `hotfix/1.1.1` — PR targets `hotfix/1.1.1` (NOT main)

Unlike every other table (offices ~16, accounts ~143, PRs/items bounded per year), the audit log is **append-only and never purged** — it grows on every write across the whole application. So this query gets linearly slower forever while everything else has a natural ceiling. Small effort, self-contained, worth doing before the log accumulates.

### Root cause

`BudgetPlanningDashboardService.GetRecentActivityAsync` (`backend/PPDO.Application/Services/BudgetPlanningDashboardService.cs:116`):

```csharp
IReadOnlyList<AuditLog> audits = await _auditRepo.GetAllAsync(ct);   // entire table
IReadOnlyList<User>     users  = await _userRepo.GetAllAsync(ct);    // all users
// ...filter by office in memory, OrderByDescending(ChangedAt).Take(10)
```

`audit_log` is accessed via the generic `IRepository<AuditLog>` — there is no dedicated audit repository with a scoped query. `DashboardService` and the audit service follow the same full-load pattern.

### Approach

Add a dedicated `IAuditRepository` with a server-side recent-activity query (`ORDER BY changed_at DESC … OFFSET/FETCH`), mirroring the existing targeted repos (`PurchaseRequestRepository.GetByDivisionAsync`, `CalendarEventRepository.GetByDateRangeAsync`). Keep the user-name resolution but fetch only the users referenced by those 10 rows (`WHERE Id IN (...)`), not the whole table.

---

## Backend — no migration

1. `IAuditRepository` (Domain/Interfaces) + `AuditRepository : Repository<AuditLog>` (Infrastructure):
   * `Task<IReadOnlyList<AuditLog>> GetRecentAsync(int take, int? officeId, CancellationToken ct)`.
   * Server-side: filter by office when provided (join/where on the actor's `OfficeId`), `OrderByDescending(a => a.ChangedAt)`, `.Take(take)`. Office filtering may need a join to `users`; if a clean SQL join is awkward, at minimum push the `ORDER BY … TAKE` to the DB and resolve the small set of users by id afterwards.
   * Register in `Program.cs` DI.
2. `BudgetPlanningDashboardService.GetRecentActivityAsync`: call `_auditRepo.GetRecentAsync(10, officeId, ct)`; resolve actor names via `WHERE Id IN (referenced ids)` instead of `GetAllAsync()` on users.
3. While here, check `DashboardService` / `AuditService` for the same `GetAllAsync` on audit and apply the scoped query where it's a recent-list read (do **not** touch audit *writes*).
