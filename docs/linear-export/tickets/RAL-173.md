# RAL-173 — [bug] Dashboard calendar: multi-day events render one day short

> 🌿 Branch `fix/dashboard-calendar-multiday-exclusive-end` off `main`. PR [obiken-01/ppdo-portal#164](https://linear.app/ralphoksiprojects/review/fixdashboard-multi-day-calendar-events-render-one-day-short-c717cd265489), commit `895b8fa`. Standalone Dashboard/Calendar fix — not part of the WFP Rework epic ([RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14)), no parent.
> 📌 Frontend-only, small.
> 🐛 Found live by Ralph 2026-07-20: a "Meeting/Evaluation" event set Jul 13 → Jul 17 on the production Dashboard calendar only highlighted through Jul 16.

## Why

**Root cause**: FullCalendar treats an all-day event's `end` as **exclusive** — an event whose last real day is Jul 17 needs `end = Jul 18`, or FullCalendar stops rendering the day before. This app stores/displays end dates **inclusive** everywhere else (the Create/Edit modal's "End Date" field, the database), so `DashboardCalendar.tsx`'s `toFcEvent()` (`frontend/src/components/dashboard/DashboardCalendar.tsx:34-54`) was passing the stored inclusive end date straight through to FullCalendar's `end` prop unmodified — visually clipping every multi-day event by one day.

## What shipped

* `toFcEvent()` now adds 1 day (via a new `shiftIsoDate` helper, UTC-arithmetic so it never depends on the browser's local timezone) before handing an all-day event's end date to FullCalendar.
* `handleEventClick()` does the mirror-image -1 day when reading FullCalendar's own (exclusive) `endStr` back out. This second fix is not optional: `dashboard/page.tsx`'s `onEventClick={setSelectedEvent}` → `setEditingEvent(selectedEvent)` feeds this value **directly** into the Edit modal with no re-fetch from the API — leaving it unfixed would have introduced a *new* +1-day bug in the Edit modal's End Date field the instant the render side was corrected.

## Verification

Live-verified (local dev DB, via a temporary IIS/LAN test deployment — no automated test suite covers the FullCalendar rendering layer):

* Created a test event spanning Jul 21–24 (4 days). Calendar bar measured via `getBoundingClientRect()` at exactly 4 day-cell-widths (was 3 before the fix — confirmed by disabling the fix and re-measuring).
* Clicked the event → Edit → confirmed the End Date field shows `2026-07-24` unchanged, not `2026-07-25` — proving the round-trip stays consistent.
* Deleted the test event afterward (`DELETE` → 204 No Content); local dev data left as found.
* `npx tsc --noEmit` and `npx eslint` on the changed file — both clean.
