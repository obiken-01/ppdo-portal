# RAL-269 — Login page: Forgot password? flow

**V18-24** — plan: `docs/v1.8/Phase_Plan.md` §3.4. Depends on V18-23 ([RAL-265](https://linear.app/ralphoksiprojects/issue/RAL-265/password-reset-backend-request-verify-endpoints-throttle-audit)).

The user-facing half of Option B, on the public login page:

1. **"Forgot password?"** link → a form asking for the **username** only.
2. The recovery question for that account is shown; the user types their answer.
3. On success, a **randomly generated temporary password** is displayed once, with a "copy" affordance and a plain instruction that it must be changed at login.
4. On failure — wrong answer, unknown username, or a locked account — **the same generic message every time**. The UI must not leak which case it was; that is the enumeration guard from V18-23 and it is easy to undo accidentally with a helpful error string.

Keep it to the smallest number of screens that works — Ralph's brief was *"do not make it complicated"*.

Note the login page also carries the health-check indicator that pre-warms Azure Functions; the reset flow should not fight it for the user's attention. Public route, so no JWT — but it should still behave sensibly during a cold start (a slow first request is normal here).
