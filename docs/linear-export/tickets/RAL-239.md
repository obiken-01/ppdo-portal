# RAL-239 — Division config: make both Code and Name editable via a code-keyed upsert

## Problem

Division `Name` cannot be edited. `DivisionService.UpdateAsync` deliberately skips it — see the comment at `backend/PPDO.Application/Services/DivisionService.cs:147`:

> `// Name is the upsert key — not editable via update (only via CSV re-seeding).`

And CSV re-seeding does not rename either: the upsert matches on `(officeId, name.ToLowerInvariant())` (`DivisionService.cs:268`), so changing a name in the CSV creates a **new** division row and leaves users/data attached to the old one.

### Correcting the original premise

The initial assumption was that `Code` is treated like a primary key. It is not:

* `Division.Code` is **nullable**, max 20, with **no unique index at all**.
* `UpdateAsync` already assigns `entity.Code` freely (`DivisionService.cs:137`) with no collision check.
* The only unique index is `IX_divisions_office_id_name` on `(office_id, name)` — **Name** is the de-facto key.

So `Code` is already editable; `Name` is the blocked one.

### Why the originally proposed (code, name, office_id) UK was rejected

A composite unique across all three is *weaker* than today's constraint — it would allow two active divisions in the same office both named "Planning Division" with different codes. `PurchaseRequestService.ResolveDivisionByNameAsync` (`PurchaseRequestService.cs:93`) matches name via `FirstOrDefault`, so PR Excel imports would silently bind to whichever row SQL returned first. It also unlocks nothing, since Code is already editable.

## Renaming is safe at the data layer (verified)

No table persists a division name as text. All seven referencing entities use the `DivisionId` FK: `User`, `PurchaseRequest`, `Distribution`, `WfpRecord`, `DivisionAllocation`, `ProgramDivision`, `WfpDivisionAllocationLedger`. Names are resolved at read time, so a rename propagates automatically — [RAL-236](https://linear.app/ralphoksiprojects/issue/RAL-236/distribution-all-distributions-for-stockno-table-shows-numeric) just fixed the last place that wasn't doing that.

## Approach — code-keyed upsert

1. **Schema:** keep `(office_id, name)` unique. Add a **filtered** unique index on `(office_id, code)` `WHERE code IS NOT NULL` (Code stays nullable, so a plain unique index would collide on multiple NULLs under SQL Server). This is needed independently: the PR resolver already falls back to Code, and duplicate codes are nondeterministic today.
2. **Migration guard:** existing prod rows may already hold duplicate or blank codes. The migration must detect collisions and fail loudly rather than silently dropping data.
3. **CSV upsert:** match on `code` when present, falling back to `name` for codeless rows — so a renamed row with a stable code updates in place instead of duplicating.
4. **UpdateAsync:** allow `Name` edits, with an explicit `(office_id, name)` collision check returning BadRequest, and a matching `(office_id, code)` check.
5. **Resolver hardening:** make `ResolveDivisionByNameAsync` deterministic.

## Also in scope — [RAL-236](https://linear.app/ralphoksiprojects/issue/RAL-236/distribution-all-distributions-for-stockno-table-shows-numeric) follow-ups

Code-quality items found reviewing the merged [RAL-236](https://linear.app/ralphoksiprojects/issue/RAL-236/distribution-all-distributions-for-stockno-table-shows-numeric) fix, folded in here since they touch the same read path:

* **Duplicated construction.** The `ExistingDistributionDto` build is copy-pasted at two sites in `DistributionService.GetItemSummaryAsync` — which is *why* the bug existed in exactly two places. Extract one local factory so the next change has a single site.
* **Dead fallback. **`divisionNameById.GetValueOrDefault(d.DivisionId, d.DivisionId.ToString())` — `DivisionId` is an FK, so the fallback is unreachable; if it ever were reached it would silently reproduce the original bug with no log. Drop it, or `LogWarning` per the CLAUDE.md logging rules.
* **Root shape.** The repository breakdown rows (`DistributionBreakdownRow`, `DeliveryItemBreakdownRow`) carry `DivisionId` but not the name, forcing every consumer to re-resolve it. Projecting the name in SQL would make the bug class unconstructible.
* **Test gap.** The two [RAL-236](https://linear.app/ralphoksiprojects/issue/RAL-236/distribution-all-distributions-for-stockno-table-shows-numeric) regression tests were never mutation-checked — confirm they fail against the unfixed code, otherwise they pin nothing.
