# RAL-230 — Stop office users fetching the PPDO-scoped Budget Planning dashboard

🔴 Critical — PPDO's budget ceilings, per-division allocations, and per-division WFP status are fetched into an office user's browser on every Budget Planning page load.

## Context — read first

* `docs/v1.8/Office_User_Path_Findings.md` §3.2 (this bug) and §2 (what already works for office users)
* `frontend/src/app/(portal)/budget-planning/page.tsx` — the page; note it already has a correct `isPpdo` branch that the data-load effect simply does not use
* `backend/PPDO.Application/Services/BudgetPlanningDashboardService.cs` — `GetDashboardAsync`, hardcoded to PPDO
* `backend/PPDO.Functions/Functions/BudgetPlanningDashboardFunctions.cs` — `GetDashboard`
* `CLAUDE.md`, `docs/DESIGN_SYSTEM.md`, `docs/TEST_CONVENTIONS.md`

## Problem

`GetDashboardAsync` is permanently scoped to the PPDO office by design (v1.4.5, [RAL-161](https://linear.app/ralphoksiprojects/issue/RAL-161/budget-planning-dashboard-rework-ppdo-scoped-queries-per-divisionfund)):

```csharp
private const string PpdoOfficeCode = "PPDO";
Office ppdo = await _officeRepo.GetByCodeAsync(PpdoOfficeCode, ct)
    ?? throw new InvalidOperationException($"Office '{PpdoOfficeCode}' is not seeded.");
```

That was correct when Budget Planning was PPDO-only. But the page calls it **unconditionally**:

```tsx
useEffect(() => {
  loadDashboard();          // → GET /budget-planning/dashboard  (always PPDO)
}, [loadDashboard]);
```

There is no `isPpdo` guard on the effect, even though the page computes `isPpdo` a few lines below and correctly uses it to gate *rendering* (`{isPpdo && dashboard && ...}`). So an office user never *sees* the PPDO panels — but the response is fetched, sits in memory, and is plainly visible in devtools. The page also seeds `fiscalYear` from that response, so the fetch is currently load-bearing for office users even though its payload is not theirs.

Both layers need fixing. Gating only the frontend leaves the endpoint open to a direct call; gating only the backend breaks the office user's fiscal-year bootstrap.

## Working branch

Branch off `release/1.8.0`, named `fix/v1.8.0-<ral>-ppdo-dashboard-office-user-fetch`. PR targets `release/1.8.0` (**not **`main`).

**Depends on the** `OfficeScope` **ticket** for the backend guard.

## Product decision needed before starting

**What should an office user see at** `/budget-planning`**?** The page is currently a PPDO-shaped dashboard with an office-readiness hub bolted on. Options, roughly ascending in effort:

1. Office users get only the office-readiness hub (the `getOfficeDashboard` section they already see) — smallest change, and the page already renders this correctly today.
2. Office users get a purpose-built landing view for their own office.
3. Office users are redirected away from `/budget-planning` to their first real page.

Recommendation is (1) for this ticket — it is the minimum that closes the leak without prejudging the dashboard redesign. Confirm with Ralph before building anything larger; a fuller office-user dashboard likely belongs with the redesign track, not here.

## Steps

1. **Backend — deny non-PPDO callers. **`GetDashboard` should 403 an office user rather than serving PPDO's data. Use the `OfficeScope` helper. Keep the message generic; do not leak whether PPDO data exists.
2. **Frontend — stop calling it.** Guard the load effect on `isPpdo`. Note the ordering problem: `user` comes from `useMe()` and is null on first render, so the effect must wait for `user` to resolve rather than firing on mount — the existing `getRecentActivity` effect at the same level already handles this correctly with an early `if (!user) return;`. Follow that.
3. **Fix the fiscal-year bootstrap. **`fiscalYear` is currently seeded from the PPDO dashboard response (`if (fy == null) setFiscalYear(data.fiscalYear)`). Office users will no longer have that. Source it from somewhere legitimately theirs — the office dashboard response is the obvious candidate, but check the load ordering: `getOfficeDashboard` is currently gated on `fiscalYear != null`, so naively swapping the source creates a deadlock where each waits for the other. Resolve this deliberately rather than by trial and error.
4. **Verify the office-user path end-to-end in the browser**, not just via tests. Per `CLAUDE.md`'s local dev setup, create an office user against the local dev DB and load `/budget-planning` as them. Confirm: no `GET /budget-planning/dashboard` request in the network tab, the office readiness hub still renders, the fiscal-year selector works, and there is no infinite redirect (the page's `useMe` fallback deliberately sends office users to `/account` — see the comment at `page.tsx:440`).
5. **Preserve layout during loading** — per `CLAUDE.md`'s CLS rule, the office-user view must not gate the whole page on a spinner that is then replaced by full-height content.
6. **Tests**: backend — office user gets 403 from `GetDashboard`, PPDO user unchanged. Frontend — no equivalent test harness exists for this page, so the browser verification in step 4 is the acceptance evidence; state explicitly in the PR what was checked.
