# RAL-232 — Price index: slim the list payload (1.57 MB) and stop the Config dashboard downloading it just to count rows

Follow-up to [RAL-231](https://linear.app/ralphoksiprojects/issue/RAL-231/wfp-entry-158-mb-price-index-fetch-blocks-the-aipoffice-selectors-on), which took the price-index fetch off `wfp/entry`'s critical path but left the payload itself untouched. This is the deeper fix and it helps **every** consumer, not just that page.

## Context — read first

* `docs/PERFORMANCE_GUIDELINES.md` — the "slim DTOs for list endpoints" rule this applies
* `backend/PPDO.Application/DTOs/Config/PriceIndexItemDto.cs`
* `backend/PPDO.Application/Services/PriceIndexService.cs` — `GetFilteredAsync` path added by `f841184`
* `frontend/src/lib/config.ts` — `listPriceIndex`
* `CLAUDE.md`, `docs/TEST_CONVENTIONS.md`

## Measured (local dev, 6,397 active rows)

`GET /api/config/price-index?active=true` returns **1,606,522 bytes (1,569 KB)**.

The WFP item picker reads exactly five fields — `id`, `name`, `unit`, `unitPrice`, `daysEnabled`. Re-encoding the real response with only those:

|  | Bytes |  |
| -- | -- | -- |
| Full | 1,606,522 | 1,569 KB |
| Slim (5 fields) | 702,868 | 686 KB |
| **Saving** | **903,654** | **56% smaller** |

Cost of the four fields that picker never reads:

| Field | Bytes |  |
| -- | -- | -- |
| `category` | 322,175 | 315 KB |
| `priceUpdatedAt` | 275,197 | 269 KB |
| `stockCardNo` | 203,930 | 199 KB |
| `isActive` | 102,352 | 100 KB |

`priceUpdatedAt` is a full ISO timestamp per row; `isActive` is redundant on a response already filtered by `active=true`.

## ⚠️ Second, worse problem found while scoping this

`frontend/src/app/(portal)/config/page.tsx:72`:

```ts
load: async () => (await listPriceIndex({ active: "true" })).length,
```

**The Config dashboard downloads 1.57 MB to render a row count.** That is the single worst instance and the cheapest to fix — it needs a count, not a list. Fix it in this ticket.

## The constraint that shapes the design

There are four consumers with genuinely different needs, so **do not just narrow the shared DTO** — the management grid needs the full record:

| Consumer | Needs |
| -- | -- |
| `wfp/entry` (item picker) | 5 fields |
| `config/procurement-presets` | verify — likely the same 5 |
| `config/price-index` (management grid) | **all 9** — do not break this |
| `config/page.tsx` (dashboard tile) | a count only |

## Suggested approach

1. **Count endpoint** for the Config dashboard tile — `GET /api/config/price-index/count?active=true`, backed by `CountAsync` (per CLAUDE.md: "Counts → `CountAsync`"). Point `config/page.tsx:72` at it. Biggest win for the least risk; consider doing this first as its own commit.
2. **Slim list variant** for pickers — either `?fields=slim` on the existing route or a separate `PriceIndexItemPickerDto`. Prefer whichever matches existing precedent in this codebase; check how other slim list DTOs were introduced before inventing a shape.
3. Point `wfp/entry` and `procurement-presets` at the slim variant. **Confirm first** that `procurement-presets` really only needs those five — read it, don't assume.
4. Leave `config/price-index`'s management grid on the full DTO.

Server-side pagination for the management grid is a *separate* concern — `docs/PERFORMANCE_GUIDELINES.md` recommends it for tables that grow, and 6,397 rows qualifies. Out of scope here unless it falls out naturally; raise it separately if you think it is warranted.

## Acceptance

* Config dashboard tile issues no multi-hundred-KB request.
* `wfp/entry`'s catalogue fetch drops to roughly the 686 KB figure above (verify the real number; don't restate this estimate).
* The price-index management page is unchanged — all 9 fields, editing intact.
* Procurement presets still resolve item name/unit/price correctly.
* Backend tests for the new count and slim paths per `docs/TEST_CONVENTIONS.md`.
