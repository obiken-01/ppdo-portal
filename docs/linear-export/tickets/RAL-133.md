# RAL-133 — A11y: darken light-gray label/secondary text site-wide for low-vision readability

> 🌿 **Working branch: **`release/1.4.0`. Create a feature branch off `release/1.4.0` and open the PR against `release/1.4.0` (NOT `main`) — implemented as part of the v1.4 release train per Ralph's call, even though it's a standalone site-wide fix unrelated to the WFP Rework epic scope itself.
> 📌 Frontend-only. No backend, no migration.

## Why

Ralph flagged that several labels and secondary text across the portal use gray shades that are too light to read comfortably, especially for older users or users with low vision. Scope confirmed with Ralph: **text color only** for this ticket (font size, button/badge contrast, and focus-ring visibility are explicitly out of scope — separate follow-ups if needed).

## Root cause (confirmed by codebase audit)

The codebase never uses Tailwind's default `gray-*` palette — everything routes through a custom `slate-*` token defined in `tailwind.config.ts`, which deep-merges with Tailwind's defaults. Only **6 of 11** slate shades are actually PPDO-reviewed:

| Token | Hex | Intended use |
| -- | -- | -- |
| `slate-800` | `#343A40` | footer |
| `slate-600` | `#6C757D` | **body text / labels** (already the "correct" token for this!) |
| `slate-400` | `#ADB5BD` | disabled / muted |
| `slate-200` | `#E9ECEF` | input borders |
| `slate-100` | `#F1F3F5` | page background |
| `slate-50` | `#F8F9FA` | zebra rows |

`slate-300`, `slate-500`, `slate-700`, `slate-900`, `slate-950` are **not** overridden, so any component using `text-slate-300` or `text-slate-500` silently falls back to **stock Tailwind slate** (`#cbd5e1` and `#64748b` respectively) — never reviewed for contrast, and in `slate-300`'s case, barely visible (~1.5:1 contrast on white, WCAG AA requires 4.5:1 for normal text).

On top of that, many components use `text-slate-400` (`#ADB5BD`, ~2.5:1 contrast — fine for genuinely disabled controls, which WCAG exempts) for things that are **not** disabled: real field labels, table headers, helper text. The design system already has a properly-reviewed darker token for exactly this (`slate-600`, "body text/labels") — it's just not being used consistently.

**Usage audit** (frontend/src, `.tsx` only):

* `text-slate-400`: 47 files, 246 occurrences (mix of genuinely-disabled AND mislabeled active text — needs per-site judgment call)
* `text-slate-500`: 50 files, 261 occurrences (almost all active labels/headers/helper/timestamp text — the main offender)
* `text-slate-300`: 23 files, 28 occurrences (breadcrumb separators — decorative, OK to stay light; but also zero-value table cells and empty-placeholder dashes like `config/accounts/page.tsx:407` and `inventory/pr-report/page.tsx:535` — these ARE meaningful data and should not be near-invisible)
* `globals.css`: 4 hardcoded hex values bypassing the token system entirely (`color: #64748b` on `.tiptap-editor blockquote` / `.announcement-content blockquote`, lines ~133/150; `border-left: 3px solid #e2e8f0` on the same selectors, lines ~131/148) — despite the file's own comment "DO NOT hardcode hex values in components — use Tailwind classes only"

No shared `<Label>` component exists — the label pattern `className="block text-xs font-medium text-slate-500 uppercase tracking-wide mb-1"` is copy-pasted inline in 20+ places (e.g. `WfpFrequencyGrid.tsx:130`, `WfpProcurementItemTable.tsx:246`, `budget-planning/wfp/entry/page.tsx` ×12, `budget-planning/report/page.tsx:397,412,430`, `inventory/receive-delivery/page.tsx:80`, `inventory/create-pr/page.tsx:192`, `inventory/pr-register/page.tsx:257,715`, `inventory/distribution/page.tsx:574,585,593`, `config/accounts/page.tsx:479`).

`frontend/src/components/ui/DataTable.tsx` is the single shared table component reused across ~14+ list/report pages — its header row (line ~200, `text-xs text-slate-500 uppercase tracking-wide`), empty-state (line ~186, `text-slate-400`), and loading-skeleton header (line ~145, `text-slate-400`) are each defined once, so fixing those 3 lines fixes table headers/empty-states everywhere `DataTable` is used.

## Files to read before writing code

* `frontend/tailwind.config.ts` — the `slate-*` token block under `theme.extend.colors`; this is where `slate-300`/`slate-500` get proper PPDO values instead of falling back to stock Tailwind.
* `frontend/src/app/globals.css` — the 4 hardcoded hex values (`.tiptap-editor blockquote`, `.announcement-content blockquote`) and the shadcn `--muted-foreground` etc. CSS-variable mappings, to check nothing else needs updating in parallel.
* `frontend/src/components/ui/DataTable.tsx` — centralized table header/empty-state/skeleton fix (lines ~145, ~186, ~200).
* One or two representative pages using the copy-pasted label pattern, e.g. `frontend/src/components/wfp/WfpFrequencyGrid.tsx:130` and `frontend/src/app/(portal)/budget-planning/wfp/entry/page.tsx`, to confirm the literal className string to search-and-replace.

## Steps

1. **Token fix (covers the bulk of occurrences in one place):**
   * Define `slate-500` in `tailwind.config.ts` with a properly dark, WCAG-AA-compliant value (target ≥4.5:1 contrast on white — check against a contrast tool during implementation; something in the neighborhood of the existing `slate-600 #6C757D` since that's already the "body text/labels" token, or slightly lighter to keep a visible two-step scale between 400 and 600).
   * Define `slate-300` with a value darker than the current stock Tailwind fallback (`#cbd5e1`) but still visibly lighter than `slate-400` — this token is legitimately used for decorative elements (breadcrumb chevrons) as well as some data values that need to stay legible; check both use cases don't regress.
2. **Redirect mislabeled **`slate-400` **usages:** for each `text-slate-400` site that is NOT a genuinely disabled/inactive control (disabled inputs, disabled tabs), change to `text-slate-600` — the token the design system already reserves for "body text/labels". Leave true disabled-state usages (e.g. `account/page.tsx:132`, `budget-planning/aip/new/page.tsx:108`) on `slate-400` — WCAG's contrast requirement doesn't apply to disabled controls, and darkening those risks making them look interactive.
3. `DataTable.tsx`**:** update the header row, empty-state, and skeleton-header classes (verify final values read comfortably against the design's white/zebra backgrounds).
4. `globals.css`**:** replace the 4 hardcoded hex values with the new token values (or a `var(--slate-500)`-equivalent) so blockquote styling in the rich-text editor/announcements stays in sync with the rest of the app instead of hardcoding a color that'll drift out of sync again.
5. **Spot-check** the ~20 copy-pasted label sites and the `text-slate-300` data-value sites (zero-value cells, `—` placeholders) after the token change — confirm nothing needs an individual override once `slate-300`/`slate-500` are darker, and fix any remaining outliers you find that the token change alone doesn't cover (e.g. a component using an inline hex instead of a class).
6. Manually verify in the browser: at least one page from each major section (Dashboard, Inventory, Budget Planning, Config, Account, public landing page) to confirm labels/table headers/helper text read clearly, and that genuinely-disabled controls still look visually distinct from active ones.

## Out of scope

Do NOT touch font sizes, button/badge color contrast, focus-ring visibility, or any non-text-color accessibility concern — those are candidates for separate follow-up tickets if Ralph wants them. Do NOT change the PPDO brand `green-*` scale or status colors (`amber-*`, `danger-*`, `info-*`). Do NOT introduce a new shared `<Label>` component as part of this ticket unless it's a trivial byproduct of the search-and-replace — that's a nice-to-have refactor, not what this ticket is asking for.
