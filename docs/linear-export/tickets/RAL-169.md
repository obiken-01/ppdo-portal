# RAL-169 — Eliminate N+1 queries on Dashboard, Report, Allocation, and WFP entry (backend)

> 🌿 Branch `fix/v1.4.6-budget-planning-query-perf` off `main` (post-v1.4.5). PR targeted `main` directly. **MERGED**, PR [obiken-01/ppdo-portal#159](https://linear.app/ralphoksiprojects/review/fixbudget-planning-eliminate-n1-queries-on-dashboard-report-allocation-e9d008d9e177), commit `95b92c5`. Child of epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> 📌 Backend + small frontend wiring. Found live via Application Insights Live Metrics after v1.4.5 shipped — a second wave of the same N+1 bug class that [RAL-163](https://linear.app/ralphoksiprojects/issue/RAL-163/allocationservice-eliminate-repeated-full-table-ceilingallocation)–165 fixed in v1.4.5, on call paths that audit round didn't cover.

## Why

v1.4.5 shipped with the Budget Planning Dashboard, Report page, Allocation page, and WFP Entry Wizard all still noticeably slow in production — confirmed via repeated ~195ms `DbCommand`s and CPU/dependency-rate spikes in Live Metrics.

## What shipped

* **Dashboard** (`BudgetPlanningDashboardService.GetDashboardAsync`): `GetAllocationsAsync` was called once per division *per* fund, even though a single call already returns every division's amount for that fund — ~60 sequential `DbCommand`s for a 6-division, 4-fund office. Now fetches active funds + their allocations once per fund and reuses the result across the WFP-by-division and ceiling-by-fund panels.
* **Report page**: first load hit the full `GET /budget-planning/dashboard` endpoint (LDIP + AIP + WFP-by-division + ceiling-by-fund) purely to read `availableFiscalYears` for a dropdown. Added a lightweight `GET /budget-planning/fiscal-years` endpoint and pointed the Report page at it.
* **Allocation page**: fired one `GET .../allocation/divisions` call per active fund in parallel (`Promise.all`) — N funds meant N concurrent Function invocations, the actual burst visible in Live Metrics. Added `IAllocationService.GetAllocationsForAllFundsAsync`, backed by a new `IDivisionAllocationRepository` overload that fetches every fund's allocation rows for an office+FY in one query (same shape as the existing batched `GetCeilingsAsync`). Wired up as `GET /budget-planning/allocation/divisions/all-funds`, same auth gate + per-caller division clamp as the original endpoint. Allocation page now fires one call and groups the result by `fundingSourceId` client-side.
* **WFP Entry Wizard** (`WfpExpenditureService.GetByActivityIdAsync`): fires on every Activity click during live data entry — the most-used path of all four. Still had the old per-expenditure loop (2 extra queries per expenditure row) even though its sibling `GetByActivityIdsAsync` (used by the WFP Report) was already fixed under [RAL-158](https://linear.app/ralphoksiprojects/issue/RAL-158/wfp-report-fix-n1-queries-in-report-generation-30s-load-100percent-cpu) with the batched repo methods already in place. Rewired to reuse `GetPeriodsByExpenditureIdsAsync` / `GetProcurementItemsByExpenditureIdsAsync` — 3 queries total regardless of expenditure count.
* `APP_VERSION` bumped to `v1.4.6` (patch, no new features) per the version-bump-timing convention.

## Verification

* `dotnet test` — 696/696 backend tests pass, including new N+1 regression guards and a byte-for-byte parity test between the fixed singular path and its already-correct batched sibling.
* `npx tsc --noEmit` — clean.
* Verified live against local dev DB: Dashboard totals unchanged after the refactor, Report page network log confirms it now calls `fiscal-years` instead of `dashboard`, Allocation page shows exactly one `divisions/all-funds` call with correctly-grouped per-division amounts, WFP Entry Wizard returns correctly-scoped expenditures per activity with zero cross-contamination, no console errors.

Frontend loading-state UX for the WFP Entry Wizard's price-index fetch — see RAL-170/RAL-171.
