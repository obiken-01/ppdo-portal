# RAL-206 — Formalise and document the PPDO design system

> **UPDATE 2026-08-07 — the documentation half is DONE. **`docs/DESIGN_SYSTEM.md` created in PR [obiken-01/ppdo-portal#213](https://linear.app/ralphoksiprojects/review/docsdesign-add-design-systemmd-reference-record-style-divergences-ral-23e161b64387), branch `docs/v1.7.1-ral-206-design-system` off `main`. Docs only, no styling changed. The audit findings below were confirmed against the real code and the divergence table now lives in the doc's §7. **Remaining in this ticket: the code migration to actually make the pages uniform** — see "Migration status" at the bottom.

Placeholder ticket — Ralph plans to bring a reference post to shape the scope. Scope below is what an audit of the current frontend suggests; **confirm with Ralph before starting**.

## Framing

We do **not** need to build a design system from scratch. One already exists de facto — it's just undocumented and unevenly applied. This ticket is about making it explicit and enforceable.

## What already exists

* **Design tokens** — `frontend/tailwind.config.ts` is genuinely good: full PPDO green ramp (950→25), slate neutrals with documented accessibility reasoning ([RAL-133](https://linear.app/ralphoksiprojects/issue/RAL-133/a11y-darken-light-gray-labelsecondary-text-site-wide-for-low-vision) — which slate shade is AA-safe for body text vs disabled vs decorative), status colours, stat-card and Excel-cell palettes, `Segoe UI` font stack, `slide-in`/`toast-progress` keyframes.
* **Primitives** — Radix (`dialog`, `dropdown-menu`, `select`, `tooltip`, `avatar`, `label`, `separator`, `slot`, `toast`), `class-variance-authority`, `clsx`, `tailwind-merge`, `lucide-react` icons. The shadcn/ui foundation is in place.
* **Shared components** — `Toast.tsx` (complete: 4 variants, slide-in, auto-dismiss, progress bar), `DataTable.tsx`, `TableSkeleton.tsx`, `LoadingState.tsx`, `ConfigPageHeader.tsx`.
* **Written conventions** — `docs/NAMING_CONVENTIONS.md`, `docs/PERFORMANCE_GUIDELINES.md` §6-7, CLAUDE.md's frontend rules.

## The actual gaps

1. **No single design-system doc.** The rules are scattered across `CLAUDE.md`, three `docs/` files, and inline comments in `tailwind.config.ts` and `LoadingState.tsx`. There's no one page a contributor reads to know how to build a page that looks like the rest of the app.
2. **No component inventory.** Nobody can tell what shared components exist without grepping — which is exactly how [RAL-201](https://linear.app/ralphoksiprojects/issue/RAL-201/mobile-layout-fixes-across-configuration-pages) ended up finding the same header markup duplicated across six config pages, and how [RAL-192](https://linear.app/ralphoksiprojects/issue/RAL-192/inventoryservice-scoped-queries-list-pagination)'s skeleton sweep nearly misused `LoadingState` for a case its own doc comment excludes.
3. **No visual reference.** No Storybook or equivalent; components are only viewable by navigating to a page that happens to use them.
4. **Spacing and radius aren't tokenised** the way colour is. `borderRadius` maps to a `--radius` var, but the app is deliberately flat ("no rounded edges", per CLAUDE.md's v1.1 table) — worth recording as an explicit decision rather than leaving it implicit.
5. **Uneven adoption.** Not all pages use the shared components; one-off skeletons exist in `pr-report` and `distribution` (justified at the time, but undocumented as exceptions).

## Suggested scope

* `docs/DESIGN_SYSTEM.md` — tokens and when to use each, the flat-design decision, component inventory with "use this for X, don't use it for Y", the toast-vs-inline-error rule (currently only in `Toast.tsx`'s header comment), accessibility rules (the [RAL-133](https://linear.app/ralphoksiprojects/issue/RAL-133/a11y-darken-light-gray-labelsecondary-text-site-wide-for-low-vision) slate guidance belongs here).
* Audit shared components for duplication — the [RAL-201](https://linear.app/ralphoksiprojects/issue/RAL-201/mobile-layout-fixes-across-configuration-pages) pattern (same markup in 6 files) likely exists elsewhere.
* **Decide on Storybook explicitly.** It's real ongoing maintenance for a single-developer project; the honest answer may be no. Record the decision either way.

## Explicitly not in scope

A visual redesign. The current look is deliberate and reviewed (flat by decision, contrast-audited per [RAL-133](https://linear.app/ralphoksiprojects/issue/RAL-133/a11y-darken-light-gray-labelsecondary-text-site-wide-for-low-vision)). This is about documenting and consistently applying it, not changing it.

## Note on ticket references

CLAUDE.md's v1.1 implementation table lists `RAL-69` as "UI: flat design (no rounded edges)", but Linear's actual [RAL-69](https://linear.app/ralphoksiprojects/issue/RAL-69/db-config-tables-migration-accounts-offices-funding-sources) is "DB config tables migration — accounts, offices, funding sources".
