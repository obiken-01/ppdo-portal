# RAL-93 — Perf: scope AIP/WFP hierarchy queries — stop loading whole tables in memory

## Context

Scalability audit (2026-06-22). The AIP and WFP services load **entire tables** and filter in memory rather than querying scoped rows from the database. Not painful today (small data), but it scales poorly: every detail/save request pulls every row of several tables across all fiscal years and offices, then filters with LINQ-to-objects in C#.

> 🌿 **Working branch:** create feature branch off `hotfix/1.1.1` — PR targets `hotfix/1.1.1` (NOT main)

This is the **query-efficiency** follow-up referenced in [RAL-89](https://linear.app/ralphoksiprojects/issue/RAL-89/perf-slim-aip-detail-payload-for-the-wfp-grid-12-mb-minimal). [RAL-89](https://linear.app/ralphoksiprojects/issue/RAL-89/perf-slim-aip-detail-payload-for-the-wfp-grid-12-mb-minimal) slims the AIP detail *payload* (what goes over the wire); this ticket fixes the *query* (what's loaded from the DB). They're complementary and can land independently.

### Root cause

The base `Repository<T>` exposes an efficient `IQueryable Query()` method, but **no Application service uses it** — they all call `GetAllAsync()` (= `ToListAsync()`, whole table) then filter in memory. Examples:

`AipService.GetByIdAsync` (`AipService.cs:77`) loads **all five levels**:

```csharp
(await _officeRepo.GetAllAsync(ct)).Where(o => o.AipRecordId == id)       // ALL offices
(await _programRepo.GetAllAsync(ct)).Where(p => officeIds.Contains(...))  // ALL programs
(await _projectRepo.GetAllAsync(ct)).Where(j => ...)                      // ALL projects
(await _actRepo.GetAllAsync(ct)).Where(a => ...)                          // ALL activities  ← biggest table
```

`WfpService` has **13 **`GetAllAsync` calls in the same shape (`WfpService.cs:72, 76-80, 96, 142, 234, 254, 302` …), e.g. loading all `WfpActivity` / `WfpExpenditureLine` rows then filtering by `WfpId` in memory.

The activities/expenditure-line tables grow with each fiscal year × office × program × project, so these are the ones that will hurt first.

### The good pattern already exists

`PurchaseRequestRepository.GetByDivisionAsync`, `ItemMasterRepository`, `DeliveryRepository`, `CalendarEventRepository`, `UserRepository` all do server-side `.Where(...).ToListAsync(...)`. Replicate that shape for the AIP/WFP hierarchy via feature repositories — keeping `Include` depth ≤ 2 per CLAUDE.md (load the levels in a few scoped queries rather than one deep chain).

## Backend — no migration

1. **AIP hierarchy reads** (`AipService.GetByIdAsync`, and the slim `GetSummaryByIdAsync` from [RAL-89](https://linear.app/ralphoksiprojects/issue/RAL-89/perf-slim-aip-detail-payload-for-the-wfp-grid-12-mb-minimal) if merged): replace the five `GetAllAsync` calls with scoped queries — `WHERE AipRecordId = @id` for offices, `WHERE OfficeId IN (@ids)` for programs, etc. Add the needed methods to a feature repository (`IAipOfficeRepository`/etc. or extend existing) rather than the generic repo. Same nested result, far fewer rows scanned.
2. **WFP reads** (`WfpService.GetByIdAsync`, save lookups, finalize/unlock): scope `WfpActivity` by `WfpId`, `WfpExpenditureLine` by activity ids, and the existing-WFP lookup by `(AipRecordId, OfficeId)` server-side instead of `GetAllAsync().FirstOrDefault(...)`.
3. **Status-transition methods** (`FinalizeAsync`/`UnlockAsync`/`ArchiveAsync` in both services) currently do `(await GetAllAsync()).FirstOrDefault(r => r.Id == id)` — replace with a by-id query (the entities use int keys; add a typed `GetByIntIdAsync` or a feature-repo method since the generic `GetByIdAsync` is Guid-based).

> ⚠️ Behaviour must stay identical — this is an internal query refactor, not a contract change. The DTOs, routes, and JSON shapes are untouched.
