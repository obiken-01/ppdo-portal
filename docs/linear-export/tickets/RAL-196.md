# RAL-196 — Create PR: import the GSO PR export to prefill the form

Full spec: `docs/v1.7/GSO_PR_Import_Findings.md` — read FULLY, it has the exact row/column layout verified against real sample files (not guessed).

## Problem

`ExcelService.ParsePRImport` only reads our own generated template (`GeneratePRTemplate`'s fixed row layout: Division at row 5, RequestedBy at row 7, etc.). Real PRs are increasingly created first in the external GSO system, which exports a completely different, flatter `.xlsx` layout with no Division/RequestedBy/Position/ApprovedBy fields at all (see findings doc for the exact cell map — single `PR` sheet, label/value pairs rows 1–8, Program/Project/Activity/Account No. embedded as description-only rows immediately above the item rows). Right now the only way to get one of these already-approved PRs into the portal is to retype every header field and item by hand.

## Scope

1. `IAccountService`/`AccountService` already exposes `GetAllAsync(search, accountType, active)` — `search` does `Contains` on both `AccountNumber` and `AccountTitle`, open to any authenticated user. No new backend endpoint needed for lookup; reuse it.
2. `ExcelService`: new `ParseGsoPRImport(Stream stream)` — parses the single `PR` sheet per the findings doc's exact cell map. Real item rows are identified by a positive integer in column A; hierarchy rows (Program/Project/Activity/Account No.) are description-only rows immediately above the first item row, distinguished from each other by whether they contain `" - "` (Program/Project/Activity do; Account No. doesn't). Resolve AccountTitle server-side via `IAccountService.GetAllAsync(search: accountNo, ...)`, exact match on `AccountNumber`.
3. New preview-only endpoint `POST /api/purchase-requests/import/gso-preview` — parses and returns one prefill payload (header fields + items). No PR is created by this endpoint — read-only besides the account/item lookups. Protected (JWT), same permission gate as the existing Create PR flow.
4. Frontend (`inventory/create-pr/page.tsx`): new upload action next to the existing "Upload PR Excel" button — distinct label so there's no ambiguity about which format is expected (this one is single-PR, prefill-only; the existing one is our own template, bulk, direct-create). On upload, populate the existing form state (header + items grid — items go through the same Stock No lookup manual entry already uses) exactly as if typed by hand. Division, Requested By, Position, Approved By, Approving Position, SAI No., ALOBS No. stay blank for the user to fill in — Submit validation is unchanged.
5. Manual Create PR form: replace the two free-text Account No. / Account Title inputs with a bidirectional lookup against `GET /api/config/accounts?search=`, same interaction pattern as the existing Stock No ↔ Description lookup.

## Do NOT

Do not change the existing `POST /api/purchase-requests/import` (our own template, bulk, direct-create) path — this is a new, separate, additive endpoint. Do not add PDF upload/parsing or any file-attachment storage — confirmed out of scope (Ralph, 2026-07-31: the PDF is reference-only). Do not attempt to derive Division from the file under any circumstance; it is not derivable (the file only has PPDO's own office name, not an internal division) and must stay a required manual field.
