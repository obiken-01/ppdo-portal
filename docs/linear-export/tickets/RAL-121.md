# RAL-121 — WFP: reserve rule wiring (10% hard cap, default-only prefill)

> 🌿 **Working branch: **`release/1.4.0`. PRs target it, **not **`main`.
> 📌 Read the epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14) first, then `docs/v1.4/WFP_Rework_Requirements_Draft.md` §6 FULLY. Depends on [RAL-117](https://linear.app/ralphoksiprojects/issue/RAL-117/config-chart-of-accounts-rework-expense-class-default-nature-default) (`accounts.default_apply_reserve`) and [RAL-120](https://linear.app/ralphoksiprojects/issue/RAL-120/wfp-expenditure-schema-rework-periods-procurement-items-computation) (`wfp_expenditures.apply_reserve`/`reserve_amount` columns) — both must merge first.
> ✔ **Updated 2026-07-07 (Ralph's answers to open questions #4, #5, #11):** the reserve rate is confirmed **10%** (not the draft's "19%" typo), computed against **the expenditure line's own Total**, enforced as a **hard cap**. Eligibility is now **default-only, not a gate** ([RAL-117](https://linear.app/ralphoksiprojects/issue/RAL-117/config-chart-of-accounts-rework-expense-class-default-nature-default)'s `default_apply_reserve`) — **any account may reserve**; there is no eligibility restriction to enforce here.

## Why

The new WFP form reserves up to **10%** of an expenditure line's appropriation.

## Scope

1. **Reserve rate as config, not hard-coded.** Add a single configurable rate (10% today) — simplest approach: an app-setting/constant surfaced through a small config endpoint, OR a dedicated single-row config table if PPDO is likely to change it seasonally. Default to a constant with a clearly-named location (e.g. `WfpReserveDefaults.RatePercent = 0.10m`) unless you judge the config-table route is barely more work — your call, document which you picked and why in the PR.
2. **No eligibility gate — any account may reserve. **`RAL-117`'s `default_apply_reserve` is a **UI pre-fill only** (checked/unchecked default when the account is picked) — do **not** reject `apply_reserve=true` for any account. There is no "ineligible account" case.
3. **Default amount on toggle:** when `apply_reserve` is set and `reserve_amount` is not explicitly provided, default it to `RatePercent × Total` (the expenditure line's own computed Total — confirmed calculation base, per Ralph 2026-07-07). User can edit it downward. **Validate** `reserve_amount <= RatePercent × Total` **as a hard cap** (confirmed, Ralph 2026-07-07) — reject anything higher server-side, on every account.
4. **Reserved is excluded from the quarterly release plan** (already noted in [RAL-120](https://linear.app/ralphoksiprojects/issue/RAL-120/wfp-expenditure-schema-rework-periods-procurement-items-computation)'s computation pipeline: `Total = Net + Reserved`) — this ticket's job is specifically the reserve VALUE/cap logic; the pipeline wiring itself is [RAL-120](https://linear.app/ralphoksiprojects/issue/RAL-120/wfp-expenditure-schema-rework-periods-procurement-items-computation)'s.

## Acceptance Criteria

- [ ] Reserve rate lives in one named, documented location — not scattered as magic numbers
- [ ] Server does **NOT** reject `apply_reserve=true` based on the account's `default_apply_reserve` value — every account may reserve
- [ ] Server rejects `reserve_amount` exceeding `RatePercent × Total` (the line's own Total) — hard cap, no override
- [ ] Default `reserve_amount` auto-fills to `RatePercent × Total` when the toggle is turned on without an explicit amount
- [ ] Unit tests cover: toggle-on with default account (default_apply_reserve=false) still succeeds, over-cap amount rejected regardless of account, explicit valid amount respected (not overridden), default-fill math
