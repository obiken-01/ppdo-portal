# RAL-226 — Create PR: align item Description length with Price Index (300 chars), add friendly validation

## Ask (Ralph, live)

Adjust the field length for the Create PR line item **Description** column (`backend/PPDO.Domain/Entities/PRItem.cs:29`, bound via `CreatePRItemDto.Description`) — use Price Index's item description length as the reference.

## Current state (checked by code read)

* `PRItem.Description`: `nvarchar(500)` (`PRItemConfiguration.cs:19-21`)
* `ItemMaster.Description`: `nvarchar(500)` (`ItemMasterConfiguration.cs:19-21`) — the catalog description that auto-fills `PRItem.Description` via the bidirectional StockNo↔Description lookup, and the value copied in when a PR references an unknown StockNo (`IsNewItem = true`, `PurchaseRequestService.BuildItemsAsync`)
* `PriceIndexItem.Name` (the reference field Ralph named): `nvarchar(300)` (`PriceIndexItemConfiguration.cs:16-19`)
* Everything already downstream of Price Index already matches its 300 exactly: `WfpProcurementItem.Name` and `ProcurementPresetItem.Name` are both `nvarchar(300)`.

So PRItem/ItemMaster are the two outliers still at 500 instead of the established 300 convention.

## Fix — scope decision (Ralph, 2026-08-12): validation only, DB stays at 500

Added a 300-char business-rule check (matching `PriceIndexItem.Name`) with a clear `BadRequest` message — same "no unhandled DB exception" principle as [RAL-224](https://linear.app/ralphoksiprojects/issue/RAL-224/create-pr-clear-pr-no-already-exists-error-instead-of-generic-failure):

* `PurchaseRequestService.ValidateItemLengths` — checked in both `CreatePRInternalAsync` and `UpdateAsync`'s item-replace path, message `"Row {n}: Description must be 300 characters or fewer (got {len})."`
* `ItemService.CreateAsync`/`UpdateAsync` — same 300-char check on `ItemMaster.Description`.

**Deliberately did NOT narrow the DB columns. **`PRItem.Description`/`ItemMaster.Description` stay `nvarchar(500)` — narrowing 500→300 is a lossy `ALTER COLUMN` that SQL Server would refuse if any existing prod row already exceeds 300 chars, and that can't be checked from this environment. The application-level validation alone already enforces the 300-char rule on every new/edited value going forward; the wider DB column is harmless unused slack, not a bug. Revisit narrowing later only if there's a concrete reason (e.g. confirmed no prod row exceeds 300).

## Implementation (as built)

1. `backend/PPDO.Application/Services/PurchaseRequestService.cs` — new `ValidateItemLengths(IReadOnlyList<CreatePRItemDto>)` helper (reuses the existing `ValidateFieldLength` helper), called from both `CreatePRInternalAsync` (after the empty-items check) and `UpdateAsync`'s `if (dto.Items is not null)` block (after its own empty-items check).
2. `backend/PPDO.Application/Services/ItemService.cs` — inline 300-char check in `CreateAsync` (after the required-Description check) and `UpdateAsync` (after the NotFound check, before applying any tracked field changes).
3. Tests: `PurchaseRequestServiceTests.CreateAsync_ItemDescriptionExceeds300Chars_ReturnsBadRequest_NeverHitsRepository`, `UpdateAsync_ItemDescriptionExceeds300Chars_ReturnsBadRequest_NeverSaves`; `ItemServiceTests.CreateAsync_DescriptionExceeds300Chars_ReturnsBadRequest`, `UpdateAsync_DescriptionExceeds300Chars_ReturnsBadRequest`. Full suite: 1061/1061 passing, no regressions.
4. No EF migration — no schema change in this ticket.

## Out of scope

Not touching `PriceIndexItem.Name`, `WfpProcurementItem.Name`, or `ProcurementPresetItem.Name` — they're already at 300 and are the reference, not the target. Not narrowing the DB columns (see scope decision above) — a future ticket if ever needed, gated on a prod data check.
