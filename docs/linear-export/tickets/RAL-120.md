## Why

The current `WfpExpenditureLine` stores only the final Q1–Q4/Net/Total numbers — there's no record of the frequency (Monthly/Quarterly/Bi-annual/Annual) or the individual period amounts the user actually typed, and no support for procurement items. This is the core schema + math rework everything else in the epic builds on.

## Scope — read §9 of the requirements draft for the full sketch; summary:

1. **New tables** (additive alongside the existing `WfpExpenditureLine`, or replacing it — your call on migration approach, but existing Draft-status WFP data should not be silently corrupted; Final/Archived data can stay on the old shape since it's locked):
   * `wfp_expenditures`: the per-line record — `wfp_activity_id`, `account_id` + snapshots, `nature` (Procurement/Non-Procurement/Combined — inherits `accounts.default_nature` as a UI pre-fill only, per [RAL-117](https://linear.app/ralphoksiprojects/issue/RAL-117/config-chart-of-accounts-rework-expense-class-default-nature-default); never enforced), `frequency` (M/Q/B/A), `funding_source_id` + snapshots (defaulted from the AIP activity's funding source, overridable), `apply_reserve` (pre-filled from `accounts.default_apply_reserve`, [RAL-117](https://linear.app/ralphoksiprojects/issue/RAL-117/config-chart-of-accounts-rework-expense-class-default-nature-default) — never restricted; every account may set this), `reserve_amount`, `annual_quarter_choice` (nullable, only meaningful when frequency=A — which quarter an annual amount charges to, default Q1). `q1..q4`, `net_appropriation`, `total_appropriation` are **computed columns populated by the service on save**, never trusted from the client.
   * `wfp_expenditure_periods`: `expenditure_id`, `period_no` (1–12 for M, 1–4 for Q, 1–2 for B, 1 for A), `amount`. This is the NEW thing — captures exactly what the user typed, at whatever grain they typed it, so re-opening an entry doesn't lose the original monthly/bi-annual breakdown.
   * `wfp_procurement_items`: `expenditure_id`, `period_no` (items can differ per period — carry-forward is a UI convenience, ticket #11, not a schema constraint), `price_index_item_id` (nullable), `name`/`unit`/`unit_price` (snapshot), `qty`. `line_total = qty × unit_price` computed.
2. **One computation pipeline, one code path**, used by both the entry save (this ticket) and the report generator (later, blocked ticket): `period amounts (or Σ items per period for procurement) → quarter roll-up (§2's M/Q/B/A rules) → Net = ΣQ1..Q4 → Total = Net + Reserved → expense-class sub-totals`. Do not let the frontend or a second backend code path recompute any of this independently.
3. **Frequency roll-up rules (§2)**, implement exactly:
   * M: 12 periods → Q1=Jan+Feb+Mar, Q2=Apr+May+Jun, Q3=Jul+Aug+Sep, Q4=Oct+Nov+Dec
   * Q: 4 periods → direct
   * B: 2 periods (1st Half, 2nd Half) → 1st Half→Q1, 2nd Half→Q3
   * A: 1 period → charges to `annual_quarter_choice` (default Q1, user-overridable per §2's ★REC)

## Acceptance Criteria

- [ ] All 3 new tables exist with correct FKs; migration additive, doesn't touch existing `WfpExpenditureLine` rows
- [ ] Frequency roll-up matches §2 exactly for all 4 frequency types (TDD: one test per frequency type minimum)
- [ ] `Net`/`Total`/quarter values are always server-computed on save — never accepted as client input
- [ ] Procurement `line_total` and expenditure total are computed from `wfp_procurement_items`, not entered directly
- [ ] Reserve is excluded from the quarterly release plan (Total = Net + Reserved, not Net = Total − Reserved as a display trick — Net is what the periods sum to)
- [ ] Fund source defaults from the AIP activity's funding source when the expenditure is created, but is stored (not just referenced) so it's independently overridable
- [ ] `apply_reserve` is NEVER restricted based on the account — every account can set it ([RAL-117](https://linear.app/ralphoksiprojects/issue/RAL-117/config-chart-of-accounts-rework-expense-class-default-nature-default)/[RAL-121](https://linear.app/ralphoksiprojects/issue/RAL-121/wfp-reserve-rule-wiring-10percent-hard-cap-default-only-prefill)'s default-only design)
- [ ] The save method is a single, clearly-named entry point (e.g. `SaveExpenditureAsync`) so [RAL-122](https://linear.app/ralphoksiprojects/issue/RAL-122/wfp-division-allocation-ledger-aip-budgetallocation-ceiling-blocking) can add its ceiling-check rejection there
