# RAL-262 — Permission-aware landing selector — user form, division config, office config, /account

**V18-20** — plan: `docs/v1.8/Phase_Plan.md` §3.3. Depends on V18-16 ([RAL-251](https://linear.app/ralphoksiprojects/issue/RAL-251/landing-page-schema-resolution-chain-user-division-office-fallback)).

One shared selector component for choosing a landing page, used in four places:

* **User Management** — an admin setting it for someone else.
* **Division config** (V18-13) and **Office config** (V18-12) — the two default levels.
* `/account` — the user's own preference, self-service.

⚠️ **The options list must be filtered by what the target can actually reach**, and validated again on the backend — the UI filter is a convenience, not the guard. Saving "Inventory Dashboard" for a user without `CanAccessInventory` does not produce an error; it produces a **redirect loop** at login, or a 403 landing page. The office-user gate in `(portal)/layout.tsx:208-217` makes this concrete: an office user with "Main Dashboard" saved would ping-pong between the gate and their preference.

Note the filter subject differs per site: for the user form it is that **user's** effective permissions; for division/office config it is that **division's / office's** flags, not the editing admin's.

**Done when:** an impossible combination cannot be saved from any of the four surfaces, the backend rejects it independently, and a test covers the office-user + Main Dashboard case.
