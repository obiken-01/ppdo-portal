## Why

[RAL-170](https://linear.app/ralphoksiprojects/issue/RAL-170/scope-priceindexservice-query-to-sql-memoize-allocationservice-lookups)'s `resourcesLoading` notice on the WFP Entry Wizard was a one-off inline skeleton, built to unblock that ticket. Worth promoting to a reusable component now that a second "content area with no known final shape to skeleton against" case is likely to come up elsewhere in Budget Planning/Config.

## What shipped

New `frontend/src/components/ui/LoadingState.tsx` — a centered spinner with a message below it, reusing the same spinner style already established by `app/(portal)/loading.tsx` (the route-transition fallback) so both feel like one system. Takes a `minHeightClassName` prop so callers can size the container to roughly match the content it's replacing, avoiding a layout jump when the real content swaps in.

Swapped the WFP Entry Wizard's ad-hoc skeleton bars (from [RAL-170](https://linear.app/ralphoksiprojects/issue/RAL-170/scope-priceindexservice-query-to-sql-memoize-allocationservice-lookups)) for this component while `resourcesLoading` is true (AIP/office list, reserve rate, and price index are still loading).

**Deliberately not a general replacement** for the page's other skeletons — Effect B's ceiling-header + context-picker skeleton (from [RAL-166](https://linear.app/ralphoksiprojects/issue/RAL-166/fix-cls-wfp-entry-allocation-report-page-loading-spinners-frontend), which sizes itself to the real final layout) stays as-is. `LoadingState` is for content areas with no known final shape to skeleton against, not a swap-in for every loading state in the app.
