# RAL-139 — WFP entry: make the "Apply reserve" checkbox read-only, driven by the selected account

> 🌿 Working branch: `release/1.4.2` (off `main`). PR targets `release/1.4.2`. Child of epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> 📌 Frontend-only, small.

## Why

The 10% reserve should not be a free user choice — whether an expenditure applies the reserve is a property of the selected account (`Account.default_apply_reserve`, seeded/reseeded in [RAL-130](https://linear.app/ralphoksiprojects/issue/RAL-130/config-audit-chart-of-accounts-reseed-reserve-eligibility-semi)). The "Apply reserve" checkbox in the expenditure wizard should reflect the account's default and be **disabled** (read-only), so users can't diverge from policy.

## Current behavior

`frontend/src/app/(portal)/budget-planning/wfp/entry/page.tsx` — the `ExpenditureWizard` checkbox at ~line 507-516 (`id="applyReserve"`) is fully user-editable; `applyReserve` state (~line 249) defaults from `editingExpenditure?.applyReserve ?? false`, NOT from the account. Ralph notes the "value depends on the account" wiring is partly in place already — this ticket finishes it.

## Scope

1. When an account is selected in the wizard, set `applyReserve` from that account's `defaultApplyReserve` flag (and re-derive `reserveAmount` accordingly).
2. Add `disabled` to the checkbox input so it's read-only; keep it visually clear it's account-driven (e.g. helper text "Set by the selected account").
3. Confirm the saved value still round-trips on edit (`editingExpenditure`) — editing an existing expenditure should show the account-driven state, not a stale stored bool that contradicts the account.

## Out of scope

The reserve amount math / rate (already correct). Backend changes — `default_apply_reserve` already exists on `Account`.
