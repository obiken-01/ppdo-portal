# RAL-114 — LDIP: no way to correct an uploaded multi-office record

> 🌿 **Working branch:** confirm the current v1.3 integration branch (`release/1.3.0` if open, else `main`) before starting; PRs target that branch, **not **`main` directly.
> 📌 Found while live-testing [RAL-113](https://linear.app/ralphoksiprojects/issue/RAL-113/ldip-file-upload-activity-level-fields-mirror-aip-upload) (LDIP file upload) — confirmed by uploading the real reference workbook against a local dev DB.
> ✅ **Scope confirmed: this ticket implements Option A only** (re-upload replaces the whole record). The finer-grained alternative (inline per-program editing) is intentionally split out to [RAL-115](https://linear.app/ralphoksiprojects/issue/RAL-115/ldip-inline-per-program-editing-for-uploaded-records-option-b-follow), sequenced to start only after this one ships — re-upload alone already covers every correction case, so it's the higher-leverage fix to land first.

## 0. Why this exists

[RAL-113](https://linear.app/ralphoksiprojects/issue/RAL-113/ldip-file-upload-activity-level-fields-mirror-aip-upload) shipped LDIP upload creating **one** Draft record spanning every office in the file (`OfficeId = null`, `EntryMode = "Upload"`), mirroring AIP. To make that safe, `LdipForm` was deliberately forced **read-only for these records regardless of status** — the existing form is built around ONE office (Section 2's "+ Add Program" mini-form computes its AIP ref-code preview from a single selected office's `officeRefCode`; that doesn't generalize when a document's groups belong to many different real offices).

The result: once a file is uploaded, **there is no way to correct it** — no fixing a typo in a program name, no adjusting a budget, no correcting an unmatched funding source, no adding/removing a program. The only actions available are View (read-only), Finalize, and Archive (both list-page-only). If PPDO finds a mistake after uploading — which is likely, given the reference file alone needed two parser bug fixes to import cleanly — their only option today is to Archive the whole record and re-upload from scratch as a brand-new document (different Id/RefCode, loses any audit trail continuity).

## 1. Current architecture (what's blocking this)

* `frontend/src/app/(portal)/budget-planning/ldip/LdipForm.tsx`: `isMultiOffice = isEdit && record.officeId == null && record.entryMode === "Upload"` forces `isReadOnly = true` unconditionally. Section 2 (manual "+ Add Program") is hidden whenever `isReadOnly`, and even if shown, its ref-code preview (`groupRefCode`/`programRefPreview`) is computed from ONE `officeId` in local state — meaningless for a multi-office document.
* `backend/PPDO.Application/Services/LdipService.cs`: `UpdateAsync` resolves exactly ONE office (`ResolveOfficeAsync(dto.OfficeId ?? rec.OfficeId, ct)`) and calls the single-office `BuildHierarchy(groups, office, fsLookup)` overload — no path exists for updating a record whose groups span multiple offices via a per-group office (the overload [RAL-113](https://linear.app/ralphoksiprojects/issue/RAL-113/ldip-file-upload-activity-level-fields-mirror-aip-upload) added for `ConfirmImportAsync` — `BuildHierarchy(IEnumerable<(Office, SaveLdipGroupDto)>, ...)` — is only ever called from `ConfirmImportAsync` today).
* `ConfirmImportAsync` always **creates a new **`LdipRecord` — there is no "re-import into an existing record" path. Re-uploading a corrected file just produces a second, separate record; it doesn't fix the first one.

## 2. Implementation — Option A: re-upload replaces the existing record's hierarchy

Add a "Re-upload" action (Draft + `EntryMode == "Upload"` records only — Final ones need admin Unlock first, matching the existing status guard convention) that runs the SAME upload → preview → confirm flow, but confirm targets the existing record instead of creating a new one:

* Extend `LdipImportConfirmDto` with an optional `TargetRecordId` (int?). When present, `ConfirmImportAsync`:
  1. Loads the target record, verifies it exists, `Status == Draft`, `EntryMode == "Upload"`.
  2. Full-replaces its hierarchy using the SAME two-round delete-then-reinsert pattern `UpdateAsync` already uses (so the unique `(ldip_office_id, ref_code)` index never sees old+new side by side), driven by the freshly-parsed multi-office `BuildHierarchy` overload instead of insert-only.
  3. Bumps `UpdatedAt`; keeps `RefCode`/`Id`/`CreatedById`/`CreatedAt` unchanged — same document, corrected content, full audit trail preserved.
  4. When `TargetRecordId` is absent, behaves exactly as today (create new record) — fully backward compatible.
* No new HTTP routes needed — reuses `POST /budget-planning/ldip/upload` (stateless parse, already id-agnostic) and `POST /budget-planning/ldip/confirm` (extend the body).
* Frontend: add a "Re-upload" entry point on the read-only edit view (`ldip/edit?id=X`, shown only when Draft + Upload) that routes to the existing `ldip/new` Upload tab with a `?replaceId=X` query param; `ldip/import-preview` threads that id through to `confirmLdipImport({ ..., targetRecordId })`; on success, redirect back to `ldip/edit?id=X` (same id, not a new one).

**See** [RAL-115](https://linear.app/ralphoksiprojects/issue/RAL-115/ldip-inline-per-program-editing-for-uploaded-records-option-b-follow) **for the finer-grained follow-up** (inline per-program field editing without a file round-trip) — deliberately not in this ticket's scope.

## Acceptance Criteria

- [ ] `LdipImportConfirmDto.TargetRecordId` (optional) — when set, `ConfirmImportAsync` full-replaces that record's hierarchy instead of creating a new one
- [ ] Guard: target record must be `Status == Draft` and `EntryMode == "Upload"`; otherwise BadRequest naming why
- [ ] RefCode/Id/CreatedById/CreatedAt unchanged on replace; UpdatedAt bumped; audit log entry recorded (Update action, not Create)
- [ ] "Re-upload" entry point on `ldip/edit?id=X` for Draft + Upload-entry-mode records, reusing the existing upload/preview UI
- [ ] Confirming a re-upload redirects back to the SAME record's edit page, not a new one
- [ ] Existing "create new record" upload flow (no target id) is unaffected
