# RAL-88 — User profile page: edit profile + change password

## Context

Part of v1.1.1 — User Profile page. All authenticated users (any role) get a self-service `/account` page where they can edit their own profile details **and** change their password — no admin involvement.

> 🌿 **Working branch:** create feature branch off `hotfix/1.1.1` — PR targets `hotfix/1.1.1`

See full spec: `docs/v1.1.1/v1.1.1_Requirements.md` §1.

### Editable vs. restricted fields

The `users` table (`PPDO.Domain/Entities/User.cs`) already has every column needed — **no migration required**.

| Field on `User` | Self-editable on `/account`? | Notes |
| -- | -- | -- |
| `FullName` | ✅ | required, max 100 |
| `Position` | ✅ | optional, max 100 |
| `Username` | ✅ | required, unique, max 50 — login identifier |
| `Email` | ✅ | optional, unique when set, max 256 |
| `ContactNo` | ✅ | optional |
| Password | ✅ | via separate Security tab (see below) |
| `Role` | ❌ | **User Management page only** |
| `Division` | ❌ | **User Management page only** |
| `OfficeId`, override flags, `IsActive` | ❌ | admin-controlled only |

## Backend — no migration required

### A) Update own profile

**Add to **`IUserService` **/ **`UserService`**:**

```csharp
Task<ServiceResult<UserDto>> UpdateOwnProfileAsync(CallerContext caller, UpdateOwnProfileDto dto, CancellationToken ct);
```

`UpdateOwnProfileDto`:

```csharp
public sealed record UpdateOwnProfileDto(
    string FullName,
    string? Position,
    string Username,
    string? Email,
    string? ContactNo);
```

Logic:

1. Load user by `caller.UserId` → `ServiceResult.NotFound` if missing.
2. **Never touch **`Role`**, **`Division`**, **`OfficeId`**, permission overrides, or **`IsActive` — even if a crafted payload includes them (the DTO simply doesn't carry them).
3. Validate `FullName` non-empty (≤100).
4. Validate `Username` non-empty (≤50) and **unique** across other users (exclude self) → `ServiceResult.Validation("Username is already taken")`.
5. If `Email` provided: validate format and **unique** when set (exclude self) → `ServiceResult.Validation("Email is already in use")`. Email may be cleared to null (it's optional).
6. Assign the five fields, set `UpdatedAt = DateTime.UtcNow`, `SaveChangesAsync`.
7. Audit the change via `IAuditService` (matching the config-service pattern).
8. Return `ServiceResult.Success(updatedUserDto)`.

### B) Change own password (unchanged from original scope)

**Add to **`IUserService` **/ **`UserService`**:**

```csharp
Task<ServiceResult> ChangePasswordAsync(CallerContext caller, ChangePasswordDto dto, CancellationToken ct);
```

`ChangePasswordDto`:

```csharp
public sealed record ChangePasswordDto(
    string CurrentPassword,
    string NewPassword,
    string ConfirmPassword);
```

Logic:

1. Load user by `caller.UserId`.
2. Verify `CurrentPassword` against stored hash → `ServiceResult.Validation("Current password is incorrect")` on mismatch.
3. Validate `NewPassword == ConfirmPassword` → `ServiceResult.Validation("Passwords do not match")`.
4. Validate password policy (min 8 chars, ≥1 uppercase, ≥1 digit).
5. Hash `NewPassword`, save.
6. Return `ServiceResult.Success()`.

### Endpoints (`UserFunctions.cs`, or a new `ProfileFunctions.cs`)

| Method | Route | Auth | Body | Success |
| -- | -- | -- | -- | -- |
| GET | `/api/users/me` | JWT (any user) | — | `200` current profile (`UserDto`, no hash) |
| PUT | `/api/users/me` | JWT (any user) | `UpdateOwnProfileDto` | `200` updated `UserDto` |
| PUT | `/api/users/me/password` | JWT (any user) | `ChangePasswordDto` | `204 No Content` |

Use the `ApiResponse<T>` envelope for error responses (matching config endpoints pattern).

## Frontend — new page `/account`

**Route: **`src/app/(portal)/account/page.tsx`

**Sidebar entry:**

* Position: bottom of sidebar, near the logout / user avatar area
* Icon: `UserCircle` (Lucide)
* Label: "My Account"
* Visible to **all** authenticated users

**Page layout:** heading "My Account" + a tab group with two tabs:

### Tab 1 — Profile

Form pre-filled from `GET /api/users/me`:

```
Full Name        [text input]   (required)
Position         [text input]
Username         [text input]   (required)
Email            [email input]
Contact Number   [text input]
                 [Save Changes button]
```

* Role and Division are **not shown here** (or shown read-only/disabled with a hint "Managed by an administrator") — they are edited only on the User Management page.
* Client-side validation: Full Name + Username required; Email format if provided.
* On success: success Toast "Profile updated." and refresh the displayed values. If the username changed, keep the session working (JWT is id-based) — no forced re-login.
* On API error (e.g. username/email taken): inline error message below the form (red text).

### Tab 2 — Security

"Change Password" section:

```
Current Password    [password input]
New Password        [password input]
Confirm Password    [password input]
                    [Save Changes button]
```

* All fields required; client-side: New ≠ Current, Confirm matches New, min 8 chars / 1 uppercase / 1 digit.
* On success: clear fields + success Toast "Password updated successfully."
* On API error (wrong current password): inline error below the form (not a toast).
* Save button shows loading state; disabled until all fields non-empty.

**API helpers in **`lib/account.ts` **(or **`lib/users.ts`**):**

```ts
getMyProfile(): Promise<UserProfile>
updateMyProfile(dto: { fullName: string; position?: string; username: string; email?: string; contactNo?: string }): Promise<UserProfile>
changePassword(dto: { currentPassword: string; newPassword: string; confirmPassword: string }): Promise<void>
```

## TDD Requirements

Write tests BEFORE implementing the service methods.

`UpdateOwnProfileAsync`**:**

* Success: all five fields update; `UpdatedAt` bumped
* `Role` / `Division` / `OfficeId` are **unchanged** after update (guard against privilege escalation)
* Duplicate username (another user) → `ServiceResult.Validation`
* Duplicate email (another user) → `ServiceResult.Validation`
* Email cleared to null → succeeds
* Empty `FullName` / `Username` → `ServiceResult.Validation`
* Non-existent caller id → `ServiceResult.NotFound`

`ChangePasswordAsync`**:**

* Success: correct current + valid new → hash updated
* Wrong current password → `ServiceResult.Validation`
* Mismatched new/confirm → `ServiceResult.Validation`
* Policy failure (too short / no uppercase / no digit) → `ServiceResult.Validation`
* Non-existent caller id → `ServiceResult.NotFound`
