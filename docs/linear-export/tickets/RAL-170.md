## What shipped

* `PriceIndexService.GetAllAsync`: loaded the entire `price_index_items` table into memory before filtering by active flag/search term. The 2026-07-16 perf audit (`docs/Performance_Audit_2026-07-16.md`) carved this out as "low severity... genuinely small (tens to a few hundred rows)" — it actually runs to **~6,400 rows** in this environment, and is the WFP Entry Wizard's slowest mount-time fetch (`GET /config/price-index?active=true`). Added `IPriceIndexItemRepository.GetFilteredAsync`, pushing the `IsActive`/search `WHERE` and `ORDER BY` to SQL (mirrors the existing `GetByIdsAsync` on the same repo, [RAL-164](https://linear.app/ralphoksiprojects/issue/RAL-164/procurementpresetservice-scope-price-index-items-lookup-instead-of)). Every other `PriceIndexService` method (Create/Update/Delete uniqueness checks, CSV import/export) still legitimately needs the full table and is untouched.
* **Dashboard reuses the batched all-funds allocation read**: `GetAllocationsByFundAsync` still called `GetAllocationsAsync` once per active fund, and that method re-resolves every division and funding source from scratch each call — 3N queries just for allocations on a Dashboard load. Swapped to `GetAllocationsForAllFundsAsync` (built for [RAL-169](https://linear.app/ralphoksiprojects/issue/RAL-169/eliminate-n1-queries-on-dashboard-report-allocation-and-wfp-entry)'s Allocation-page batch endpoint), resolving divisions/funds once and reading every fund's allocations in a single query; Dashboard now groups the flat result by `FundingSourceId` in memory. Also added local-only EF Core command logging (`Program.cs`, gated on a blank `APPLICATIONINSIGHTS_CONNECTION_STRING`) so "Executed DbCommand" traces surface in the local `func` host console — used to measure a full Dashboard load at 85 SQL commands locally (each 1-20ms), confirming the ~195ms/command seen in prod is Azure SQL network round-trip latency, not query cost.
* `AllocationService` **memoization**: it re-fetched the entire divisions/funding-sources/offices/AIP-records tables from scratch on every internal call, even across multiple of its own methods invoked back-to-back within one request (e.g. the Dashboard's `GetOfficeDashboard` chain: `GetGeneralFundIdAsync` → `GetCeilingAsync` → `GetAllocationsAsync` → `GetProgramAssignmentsAsync`). Since `AllocationService` is registered Scoped (one instance per request), added a private nullable-field cache per table, populated lazily via `??=` — same per-request lifetime `CallerContext` already uses, applied to reference-data lookups. No behavior change, just fetched once per request instead of once per call.
* **WFP Entry Wizard loading UX**: the mount effect batched `listAip`/`listOffices`/`getReserveRate` with `listPriceIndex` in one `Promise.all`, so the AIP/Office dropdowns didn't render until the price-index fetch finished too, even though nothing on that screen needs it until the expenditure wizard opens for a Procurement/Combined entry. Per Ralph's direction: keep loading everything up front (so the rest of the session never waits on a fetch again), but communicate the wait instead of leaving dropdowns silently empty — added a `resourcesLoading`-gated skeleton + "Loading resources…" notice, matching the layout-preserving skeleton convention already used elsewhere on this page ([RAL-166](https://linear.app/ralphoksiprojects/issue/RAL-166/fix-cls-wfp-entry-allocation-report-page-loading-spinners-frontend)). Flagged as a gap for this exact page by the 2026-07-16 audit.
* **Auto-select single AIP**: when exactly one AIP is available, it's now auto-selected instead of requiring a click into a single-option dropdown.
