# RAL-144 — [bug] AIP activity Total blank/zero when source Excel cell is blank — blocks WFP entry against real budget

> 🌿 Working branch: off `main`. PR now retargeted to `release/1.4.1` (2026-07-13, per Ralph) so this and [RAL-145](https://linear.app/ralphoksiprojects/issue/RAL-145/bug-function-band-default-core-never-persists-unless-the-dropdown-is)/146 merge to `main` together in one consolidating PR, instead of two separate direct merges. Child of epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> 📌 Found live 2026-07-13 by Ralph: activity `1000-000-1-01-010-001-001-003` ("Hiring of additional manpower...") shows a blank Total in the AIP document despite having a real MOOE budget.

## Root cause

`backend/PPDO.Infrastructure/Services/AipXlsmParser.cs` (~line 172-175) reads an AIP activity's `Total` from the source Excel's own Total column (column O) **independently** of PS/MOOE/CO (columns L/M/N) — it never computes `Total = Ps + Mooe + Co`. `AipActivity.Total`'s own doc comment already says *"Auto-computed: Ps + Mooe + Co"* — that was the original design intent, never actually implemented.

`ParseDecimal` returns `null` for a blank cell and `0m` for a literal zero — so depending on how the source cell was left blank, an activity ends up with `Total = NULL` or `Total = 0.00` despite PS/MOOE/CO holding real values. No validation catches this (`AipService.ParsePreviewAsync`/`ConfirmImportAsync` only warns on unmatched funding-source codes) — it silently passes straight through import into production.

## Real functional impact (not cosmetic)

`WfpCeilingService` computes the WFP entry wizard's "AIP budget" display **and** its save/finalize guard as `(activity.Total ?? 0m) * 1000m`:

* `GetStatusAsync` (~line 52) — the figure shown to the user as "AIP budget: ₱0.00".
* `ValidateExpenditureSaveAsync` (~line 77) and `ValidateRecordForFinalizeAsync` (~line 161) — reject any real WFP expenditure entry against the activity, since `wouldBeUsed > 0` trivially exceeds an `aipBudget` of 0.

So this doesn't just display wrong — it **actively blocks entering a legitimate WFP expenditure** against any activity it affects.

## Scope of existing bad data (searched, 2026-07-13)

14 of 2,375 `aip_activities` rows affected (`Total` NULL/0 despite PS+MOOE+CO > 0):

| Office | Count |
| -- | -- |
| PPDO | 1 (the reported one) |
| General Services Office | 11 |
| Prov. Administrator - LEDIPO | 2 |

**Data fix status (2026-07-13): NOT YET APPLIED TO PRODUCTION.** Fixed in local dev DB only (scoped `UPDATE` by `ref_code`). A production-ready script (`fix-ppdo-blank-total-generic.sql`, PPDO-scoped, reusable) is prepared and handed to Ralph to run — pending execution. GSO/LEDIPO rows remain deliberately out of scope for now (Ralph's call) — revisit once PPDO is confirmed working end-to-end.

## Fix

`AipXlsmParser.cs`: stop reading `Total` from the source column entirely — compute `Total = Ps + Mooe + Co` server-side during parse, matching the field's own original documented intent. (Column O's raw value can still be read into a preview/debug field if useful for spotting source-spreadsheet arithmetic errors, but it must not be what gets persisted as `AipActivity.Total`.)

Since `WfpActivity.AipActivityId` is a hard FK to the current `AipActivity.Id` and `ConfirmImportAsync` has no per-activity upsert (re-importing an AIP creates a whole new hierarchy with new IDs, orphaning any existing WFP entries), **this fix only prevents new bad imports** — it does not retroactively touch already-imported activities. Existing bad rows need the SQL backfill above (or a future admin tool) on a case-by-case basis.

## Test plan

* Unit test: `AipXlsmParser` (or its test double) parsing a row with a blank/zero source Total cell and non-zero PS/MOOE/CO produces `Total = Ps + Mooe + Co`.
* Regression: parsing a row where the source Total already matches PS+MOOE+CO still works identically.
* Manual: re-import a small test AIP with a deliberately blank Total cell, confirm the resulting `aip_activities.total` is computed correctly and the WFP entry wizard shows the real AIP budget for that activity.

## Out of scope

Backfilling the 11 GSO / 2 LEDIPO rows (deliberately deferred). A general "AIP data quality audit" admin tool (this ticket is the targeted parser fix only).
