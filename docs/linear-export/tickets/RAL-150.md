# RAL-150 — WFP Report: sort Program/Project/Activity by ref-code sequence within each grouping

> 🌿 Working branch: `release/1.4.2` (off `main`). PR targets `release/1.4.2`. Child of epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> 📌 Backend-only, small. Ralph raised this in chat yesterday (2026-07-13).

## Why

Inside a fund-source's function-band section, Programs/Projects/Activities should always display in ref-code sequence (the one ending `-001` first, then `-002`, etc.) regardless of the order a user happened to enter WFP expenditures in. Today the entry wizard lets a user open and save any activity in any order (e.g. activity `-003` before `-001`) — the report must not let that entry order leak into the printed/exported hierarchy; it should always read top-to-bottom in the AIP's own numbering.

## Current behavior

`WfpReportService.BuildSections` (`backend/PPDO.Application/Services/WfpReportService.cs`) already calls `.OrderBy(p => p.RefCode)` / `.OrderBy(a => a.RefCode)` for programs, projects, and activities — a plain string sort on the *full* ref code (e.g. `1000-000-1-01-010-002-001-001`). This happens to produce the right order today because every segment is consistently zero-padded to 3 digits, but it's an implicit side effect of string comparison, not a deliberate "sort by sequence number" — it would silently break for any future ref code whose last segment isn't 3-digit padded, and it's not obvious from reading the code that this is what it's guaranteeing.

## Scope

1. Add an explicit helper that extracts and parses the **last dash-separated segment** of a Program/Project/Activity ref code as an integer, and sort each level (Programs within a function-band section, Projects within a program, Activities within a project) by that parsed sequence number ascending — not by the raw ref-code string.
2. Fall back to the existing full-string comparison as a tie-break (defensive only; two siblings should never share a last segment) and as a safety net if a ref code doesn't parse (e.g. non-numeric suffix) so a malformed code doesn't crash the report, just sorts last.
3. Cover with a backend test: build a report where activities were entered/saved out of numeric order (e.g. `-003` before `-001`) and assert the returned `WfpReportActivityDto` list is still in `-001, -002, -003` order.

## Out of scope

Any change to how expenditures are entered or saved (the entry wizard itself is untouched — users can still add expenditures to activities in any order they like, that's the whole point). Sorting of anything below the Activity level (accounts/expense-class rows within an activity — already grouped by a fixed PS/MOOE/CO order, not ref-code, and not part of this ask).
