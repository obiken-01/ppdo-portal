# RAL-89 — Perf: slim AIP detail payload for the WFP grid (1.2 MB → minimal)

## Context

Lighthouse + API-timing audit of v1.1.0 in prod (2026-06-22) found this is the **single worst performance issue** in the portal. `GET /api/budget-planning/aip/{id}` returns **~1,217 KB** and averages **6.7 s** warm. It is the sole cause of the WFP page's 3.3 s LCP and Lighthouse score of 73 (every other page scores 87–98).

> 🌿 **Working branch:** create feature branch off `hotfix/1.1.1` — PR targets `hotfix/1.1.1` (NOT main)

See findings: `docs/v1.1.1/v1.1.1_Requirements.md` (Performance section — add if missing) and the audit summary in this ticket.

### Root cause

`AipService.GetByIdAsync` (`backend/PPDO.Application/Services/AipService.cs:77`) returns the **entire** AIP hierarchy via `AipRecordDetailDto` → `AipOfficeDto` → `AipProgramDto` → `AipProjectDto` → `AipActivityDto`. The leaf `AipActivityDto` carries **18 fields per activity**, including heavy free-text/rarely-used columns: `ExpectedOutputs`, `EsreCode`, `ImplementingOffice`, `StartDate`, `EndDate`, `CcAdaptation`, `CcMitigation`, `CcTypologyCode`.

The WFP grid (`frontend/src/app/(portal)/budget-planning/wfp/page.tsx`) only needs, per activity: `RefCode`, `Name`, `Total` (AIP budget), `Ps`/`Mooe`/`Co`, and `FundingSourceId`/`FundingSourceSnapshot` (to resolve the default funding source). Everything else is dead weight on the wire.

> ⚠️ The full detail payload **is** still used by the AIP detail view (`budget-planning/aip/detail/page.tsx`). Do not change that endpoint's shape — add a separate slim path so both consumers are served.

### Approach

Add a **slim summary endpoint** dedicated to the WFP grid, leaving the existing full-detail endpoint untouched.

---

## Backend — no migration

1. **New DTO** in `AipDtos.cs` — a slim parallel hierarchy:
   * `AipActivitySummaryDto(int Id, int ProjectId, string RefCode, string Name, int? FundingSourceId, string? FundingSourceSnapshot, decimal? Ps, decimal? Mooe, decimal? Co, decimal? Total)`
   * `AipProjectSummaryDto`, `AipProgramSummaryDto`, `AipOfficeSummaryDto`, `AipRecordSummaryDto` mirroring the nesting but using the slim activity DTO.
   * **Confirm exact field needs** by reading `wfp/page.tsx` before finalizing — only include what the grid + expenditure popup actually read.
2. `IAipService` **/** `AipService`: add `Task<ServiceResult<AipRecordSummaryDto>> GetSummaryByIdAsync(int id, CancellationToken ct)`. Same hierarchy-loading logic as `GetByIdAsync` but projecting to the slim DTOs. **Bonus:** while here, the current method loads ALL rows of every level table then filters in memory — keep behaviour identical for now (a broader fix is tracked separately), just project fewer columns into the response.
3. `AipFunctions.cs`: new route `GET /api/budget-planning/aip/{id}/summary`, JWT-protected, `canAccessBudgetPlanning` gate (same as the existing detail endpoint), `ApiResponse<T>` envelope.

## Frontend

4. `lib/aip.ts`: add `getAipSummary(id: number)` calling the new endpoint; add matching `AipRecordSummary` / `AipActivitySummary` types in `types/`.
5. `wfp/page.tsx`: replace the `getAipById(...)` call with `getAipSummary(...)`. Verify the grid, collapse keys, AIP-budget column (`total * 1000`), and the expenditure popup's default-funding-source resolution all still work against the slim shape.

## TDD

Extend `AipServiceTests` first: `GetSummaryByIdAsync` returns the correct nested counts and slim fields for a known record; returns `NotFound` for a missing id; the slim DTO does **not** carry the dropped fields.
