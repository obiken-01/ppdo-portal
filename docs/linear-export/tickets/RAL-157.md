# RAL-157 — Funding source config: add aliases/other-names column + AIP fund-source matching

> Part of **v1.4.3 — Other Fund Source Ceiling & Allocation**. Child of the WFP Rework epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> Blocked by [RAL-154](https://linear.app/ralphoksiprojects/issue/RAL-154/fund-source-scoped-ceiling-allocation-and-wfp-check-backend) (shares the v1.4.3 backend line); **blocks** [RAL-156](https://linear.app/ralphoksiprojects/issue/RAL-156/wfp-entry-fund-source-default-hints-and-per-fund-allocation-bars) (its WFP-entry resolver consumes these aliases).
> Working branch: `release/1.4.3`. Feature branch off `release/1.4.3`; PR targets `release/1.4.3` (NOT `main`).

## Why

AIP activities record their fund source as **free text with no controlled vocabulary**. Analysis of `AIP_2027_PGOM_Test.xlsm` (column K "Funding Source (7)", all 4 sectoral sheets) shows the same fund written many ways — e.g. General Fund appears as `GF`, `General Fund`, `General fund`, `Gen Fund`; the 5% GAD Fund as `GAD FUND`, `GAD Fund`, `5% GAD`, `5% GAD Fund`, `GAD`; 20% DF as `20% DF`, `20 % DF`, `20%DF`; LDRRMF as `LDRRMF`, `LDRRM Fund`, `5% LDRRMF`.

Today the WFP entry resolver only matches the AIP snapshot against a fund source's Code/Name, so a valid GAD activity spelled `GAD FUND` fails to match and falls back to General Fund — silently mis-attributing the expenditure to the wrong ceiling. This ticket adds an **aliases** column to `funding_sources` so those variants map to the correct canonical fund source.

Note: many AIP rows list **multiple** funds separated by `/` (e.g. `GF/20% DF`, `TF/DOH/NGAs/20% DF`). Those stay ambiguous → unselected (decision D5) and are explicitly NOT resolved by aliases.

## Steps

1. Migration `AddFundingSourceAliases`: add nullable `aliases` column to `funding_sources`.
2. Domain + EF: `FundingSource.Aliases` (string?); map column in `FundingSourceConfiguration`.
3. DTOs: add `Aliases` to `FundingSourceDto` + `UpsertFundingSourceDto`.
4. Service: add `aliases` to `CsvHeaders`; round-trip in Export/Import; map in create/update.
5. Config UI: add an Aliases input (pipe-delimited; show a hint that `/`-combinations aren't aliased) + list column.
6. Seed the alias data from `docs/v1.4.3/Funding_Source_Aliases.md` §3 (align Codes with the reconciled config per O2 — confirm the GAD Code/Name, and whether Calamity/Trust stay active).
7. **Matching contract for** [RAL-156](https://linear.app/ralphoksiprojects/issue/RAL-156/wfp-entry-fund-source-default-hints-and-per-fund-allocation-bars) (this ticket only exposes aliases in the funding-source list DTO the frontend already loads): the resolver in [RAL-156](https://linear.app/ralphoksiprojects/issue/RAL-156/wfp-entry-fund-source-default-hints-and-per-fund-allocation-bars) must normalize (trim, collapse whitespace/newlines, case-insensitive, spaces-around-% ignored), bail to unselected on `/ , newline` combinations, then match the single token against Code/Name/aliases; blank → General Fund.

## Out of scope / do NOT

* Do NOT attempt to resolve multi-fund (`/`-separated) AIP values — they stay unselected.
* Do NOT alias external labels (DOH, NGAs, NGA (ER 1-94), TIEZA, TESDA, NDRRMC, DA-BAFE, PHILMEC, Brgy. Aid, Outsource) to any PPDO fund — they stay unmatched.
* Do NOT touch the Purchase Requests module.
