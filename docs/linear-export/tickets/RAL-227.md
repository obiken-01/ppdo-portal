# RAL-227 — GSO PDF import: Program/Project/Activity truncated when description wraps across PDF lines

## Report (Ralph, live)

Uploading a GSO-exported PDF (or xlsx) to prefill Create PR — the Program/Project/Activity values that land in the form after parsing are sometimes truncated (cut short partway through the sentence).

## Root cause — confirmed, and already half-fixed once before

`PdfService.ParseGsoPRImport` (`backend/PPDO.Infrastructure/Services/PdfService.cs`) reconstructs table rows from raw PDF word positions (PdfPig gives no table structure). When a Program/Project/Activity description wraps across 2+ physical PDF lines, `BuildRows`'s wrap-merge step only re-joins a continuation line into its parent row if the vertical gap is ≤ `WrapMergeGap` (12pt). Real PDFs occasionally have a slightly larger gap for the wrap — when that happens, the continuation text becomes an orphaned standalone line instead of being merged back into the Activity/Program/Project cell, and everything from that point on is **silently dropped**.

This exact failure mode was already hit once in production and partially patched: `PdfServiceTests.ParseGsoPRImport_OrphanedActivityContinuationLine_StillFindsRealAccountCode` is a regression test for it — but that earlier fix (`IsAccountCodeShape`) only stopped the orphaned prose line from being misread as the Account No. (a *different* bug it was also causing). It never re-attached the orphaned text back onto Activity, so **Activity itself has been silently truncated in this scenario ever since that earlier fix shipped** — the existing test only ever asserted `AccountNo`, never `Activity`, so nothing caught it.

Confirmed with a new assertion on the existing test fixture: before the fix, `result.Activity` came back as `"...-004 - Procurement of office supplies and"` — missing `"materials, payment of subscription, communication allowance"` entirely.

Excel (`.xlsx`) GSO imports are **not** affected — `ExcelService.ParseGsoPRImport` reads each hierarchy line as one full cell string (`ws.Cell(row, 3).GetString()`); there's no line-wrap reconstruction needed since Excel's own cell wrapping is purely visual, the underlying string is always whole.

## Fix

Added `PdfService.ReattachOrphanedContinuationLines` — after building `hierarchyLines`, re-attach any orphaned line (prose: no `" - "`, not account-code-shaped) onto the tail of the immediately preceding *coded* hierarchy line, instead of leaving it to be silently dropped from `codedLines`. Only merges into a coded line (never into an account-code line), so `AccountNo` detection is unaffected — the existing regression test still passes unchanged, now with an added assertion that `Activity` is no longer truncated.

This is a second, content-shape-based safety net on top of the existing geometry-based `WrapMergeGap` merge — it specifically catches the case where the geometry heuristic under-merges.

## Known follow-up risk (not fixed here, no evidence yet)

Item table rows go through the same `BuildRows` wrap-merge geometry. If an item Description itself wraps across PDF lines and the gap exceeds `WrapMergeGap`, the orphaned continuation would currently fall into `hierarchyLines` instead of being re-attached to that item's Description — same root cause, different landing spot. No real sample PDF or test currently demonstrates this actually happening (all sample item descriptions seen so far are short/single-line), so not fixing speculatively — revisit if a real case surfaces.

## Out of scope

Not touching `ExcelService.ParseGsoPRImport` — not affected, see root cause above. Not changing `WrapMergeGap`'s value or the geometry-based merge logic in `BuildRows` — the semantic reattachment fix is more targeted and lower-risk than recalibrating a threshold tuned against one real sample file.
