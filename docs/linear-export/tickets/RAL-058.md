# RAL-58 — [v1.2] Security Hardening — Auth Layer (rate limiting, httpOnly refresh cookie, CORS allowlist)

## Overview

Security audit of the access/refresh token system found 3 gaps. **None were ever****
****implemented** — verified against the current `release``/1.2.0` line on 2026-06-30. The work
was scoped to v1.0.1 originally but that release branch was never merged forward, so the
production line (v1.1 → v1.1.1 → v1.2) still has all three gaps. Re-scoping to **v1.2**.

> ⚠️ Note vs. the original 2026-06-08 write-up: login is now by **username**, not email
> (changed in the username-login work), so rate limiting must key on **username**. And the
> CORS gap is **worse** than first described — see §3.

**Branch:** create `feature/v1.2-ral-58-security-hardening` off `release/1.2.0`. PR targets
`release/1.2.0` (NOT main).

---

## Current state (as of release/1.2.0 @ c6ddfe0)

* **Rate limiting:** ❌ absent. `AuthFunctions.Login` (`backend/PPDO.Functions/Functions/AuthFunctions.cs`)
  calls `_auth.LoginAsync(...)` with no attempt tracking.
* **Refresh token cookie:** ❌ absent. `Login`/`Refresh` return the refresh token in the JSON
  body (`LoginResponseDto`), and the frontend stores it in `localStorage` — the original TODO
  is still in `frontend/src/lib/auth.ts:10-11`.
* **CORS:** ❌ absent **and actively dangerous**. `backend/PPDO.Functions/Program.cs:37` echoes
  the request `Origin` header straight back into `Access-Control-Allow-Origin` **and** sets
  `Access-Control-Allow-Credentials: true`. Origin-echo + credentials means any website can
  issue authenticated cross-site requests on a logged-in user's behalf. This is a live vuln.

---

## Changes Required

### 1\. Rate Limiting on `/auth/login` — **HIGH**

**Risk:** brute-force passwords indefinitely with no slowdown.

**Fix:** login rate limiting on the backend (Azure Functions, isolated worker):

* Max **5 failed attempts per username** per 15-minute window (NB: keyed on **username**, not email).
* On exceeded limit, return `429 Too Many Requests` with a `Retry-After` header.
* Reset counter on successful login.
* Use in-memory cache (`IMemoryCache`) or Azure Table Storage for attempt tracking. In-memory
  is acceptable for a single Function instance; note the cold-start/scale-out caveat in the PR.

### 2\. Move Refresh Token to httpOnly Cookie — **HIGH**

**Risk:** refresh token in `localStorage` is XSS-stealable — any injected script can silently
re-authenticate as the user.

**Fix (Backend):**

* On `POST /auth/login` and `POST /auth/refresh`, set the refresh token via `Set-Cookie`:
  * `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/api/auth/refresh`.
* Stop returning `refreshToken` in the JSON body (drop it from `LoginResponseDto`, or null it).
* `Refresh` reads the token from the cookie, not the request body.
* `POST /auth/logout` clears the cookie (`Set-Cookie` with past expiry).

**Fix (Frontend):**

* Remove `localStorage.setItem(REFRESH_TOKEN_KEY, ...)` and the `getRefreshToken()` /
  `setRefreshToken()` / `clearRefreshToken()` helpers from `lib/auth.ts`.
* Refresh calls rely on `withCredentials: true` (already set in the axios instance —
  confirm in `frontend/src/lib/api.ts`); the cookie is sent automatically.
* Update the `lib/auth.ts` header comment (it still documents the localStorage strategy).

### 3. CORS Whitelist — **HIGH** (raised from MEDIUM)

**Risk:** current origin echo-back + `Allow-Credentials: true` accepts authenticated requests
from any origin.

**Fix (**`backend/PPDO.Functions/Program.cs` **CORS middleware):**

* Replace the origin echo with a config-driven allowlist read from `IConfiguration`
  (`Cors:AllowedOrigins`, comma-separated):
  * Dev: `http://localhost:3000`, `http://localhost:4280` (SWA CLI).
  * Prod: the actual Azure Static Web Apps URL.
* Only emit `Access-Control-Allow-Origin` (echoing the matched origin) **when the request****
****origin is in the allowlist**; otherwise omit the header (browser blocks it). Keep
  `Allow-Credentials: true` only for allowed origins.
* Preserve the existing OPTIONS-preflight handling (`CorsFunctions` + the 204 short-circuit).

## Acceptance Criteria

- [ ] Login returns `429` + `Retry-After` after 5 failed attempts within 15 min for the same username; counter resets on success.
- [ ] Refresh token is set as an `HttpOnly`, `Secure`, `SameSite=Strict` cookie scoped to `/api/auth/refresh`, and is no longer present in the login/refresh JSON body.
- [ ] `localStorage` no longer stores any token after login.
- [ ] Silent refresh still works on page reload (cookie sent automatically via `withCredentials`).
- [ ] Logout clears the httpOnly cookie server-side.
- [ ] CORS allows only whitelisted origins; an unlisted origin gets no `Access-Control-Allow-Origin` header.
- [ ] All existing auth flows (login, refresh, logout, `/me`) still work.
