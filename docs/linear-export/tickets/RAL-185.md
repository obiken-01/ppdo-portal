# RAL-185 — Cache config/reference lists (offices, divisions, accounts, funding sources) to cut DB round-trips

**Backlog** — not scheduled into a version yet. Backend-only optimisation.

## Why

On the current Azure subscription the **DB is the constrained resource**, not the query logic. Azure SQL (serverless/free tier) bills **vCore-seconds** against a capped free allocation and bills while it is "active." The four config/reference tables — `offices` (19 rows), `divisions` (10), `accounts` (148), `funding_sources` (16) — are read on nearly every Budget Planning request (WFP report, PPMP report, dashboard, allocation, WFP entry) but change rarely. Caching them in memory turns those repeated reads into ~zero DB work on a warm instance.

**The win is DB-budget headroom + less DB active time, NOT perceived speed** (cold start dominates page latency and is being accepted for now — see the audit discussion 2026-07-28). Modest at today's traffic; cumulative over the month and scales with traffic. Documented in `docs/PERFORMANCE_GUIDELINES.md` §8.

## Approach

* Use `IMemoryCache` — already registered (`AddMemoryCache()` in `Program.cs`; `AuthService` already uses it), so no new dependency.
* Cache the **full active list** for each of the four config tables, keyed per table (e.g. `config:offices:all`).
* **Invalidate on write** — bust the relevant key in each config service's Create/Update/Delete (`OfficeService`, `DivisionService`, `AccountService`, `FundingSourceService`). Cleaner than a TTL and gives immediate consistency; config edits are rare and admin-only. (A short fallback TTL, e.g. 30 min, is fine as a backstop.)
* Read paths route through the cache: the services' list reads (and the by-id/`FirstOrDefault(id)` lookups the reports do) resolve from the cached list instead of a fresh `GetAllAsync()`.

## Do NOT

* Do **not** cache transactional/report data — WFP expenditures, AIP hierarchy, report DTOs. It changes, is request-specific, low reuse; caching risks stale numbers.
* Do **not** cache `price_index_items` (6,398 rows) in this ticket — it's read via SQL-filtered search, not full-loaded; caching the whole table into each instance's memory is a separate call, only worth it if the WFP-entry search is proven hot.
* Do **not** introduce a distributed cache (Redis) — costs money, and the app is single-region/low-traffic. Accept that `IMemoryCache` is per-instance (dies on cold start, not shared across scaled-out instances); that's fine at this scale.

## Files to read first

* `PPDO.Functions/Program.cs` — `AddMemoryCache()` registration; `AuthService` for the existing `IMemoryCache` usage pattern.
* `PPDO.Application/Services/OfficeService.cs`, `DivisionService.cs`, `AccountService.cs`, `FundingSourceService.cs` — the read + write chokepoints.
* `PPDO.Application/Services/AllocationService.cs` — already does *within-request* memoisation (`_xCache ??= await …GetAllAsync()`); this ticket extends that to *cross-request*.
* `docs/PERFORMANCE_GUIDELINES.md` §8 — the rationale + Azure-tier reasoning.

## Acceptance

* The four config lists are served from cache on a warm instance (verify: a second Budget Planning request in the same instance issues no `SELECT` against those tables).
* Editing a config record (create/update/deactivate) is reflected on the next read (invalidation works).
* No behaviour change otherwise; existing tests green.
