# RAL-112 — Bug: WFP page shows a false "Could not load WFP data" toast for non-finance users

## Symptom

On the WFP page, selecting a fiscal year loads and displays the activity grid, but an **error toast "Load failed — Could not load WFP data"** appears immediately after. **Nothing shows in the server logs.** First seen as a GSO (non-PPDO office) user, but it affects **any non-finance WFP user**.

## Root cause

The WFP page checks whether a budget ceiling exists **for every user** — it's part of the setup-complete gate (`wfp/page.tsx`, ~line 750: *"Always check ceiling (applies to all users, all divisions)"* → `getCeiling(officeId, fy)`).

But `GET /api/budget-planning/allocation/ceiling` was gated on `CanManageAllocation` (finance-officer only, `AllocationFunctions.GetCeiling`). A non-finance user gets a **403**, and the frontend `getCeiling()` only swallows **404** (→ null) — it re-throws anything else. The 403 propagates to the WFP load's `catch` → the toast. Because it's an authorization denial (not a 500), **nothing is logged**. It appears *after* the grid because `getCeiling` runs after `setAipDetail`.

## Fix (PR #92)

Relax the **ceiling GET** to `CanAccessBudgetPlanning` — matching the `/allocation/status` endpoint, which is already readable by WFP users for the same gate. Ceiling/allocation/assignment **mutations stay finance-only** (`CanManageAllocation`). With a missing ceiling now returning 404 as intended, `getCeiling()` returns null and no toast fires.

## Verification

* `dotnet build` clean; allocation service tests pass (23).
* Manual: as a non-finance / office user, open WFP + pick FY → grid loads, **no error toast**.

## Note

Consistent with the existing budget-planning reads, the ceiling GET does not office-scope the `officeId` param (WFP List behaves the same). Low-sensitivity (a ceiling amount); a broader office-scoping pass on budget-planning reads can be a separate follow-up if wanted.
