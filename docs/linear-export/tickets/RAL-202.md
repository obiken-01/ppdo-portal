# RAL-202 — SEO: make the public site discoverable and indexable by search engines

Ralph wants the portal to actually show up on Google when someone searches "PPDO portal" or similar terms. Today the site has essentially no SEO infrastructure:

* Every route (public AND authenticated) shares one generic `<title>`/description from the root layout — there's no per-page metadata at all.
* No Open Graph / Twitter card tags — link previews (Messenger, Slack, Facebook) render blank.
* No `robots.txt` — nothing tells crawlers to skip the authenticated portal routes (`/dashboard`, `/inventory/*`, `/budget-planning/*`, `/config/*`, `/account`), which just redirect to `/login` anyway and are pure crawl-budget waste.
* No `sitemap.xml`.
* No structured data (JSON-LD) identifying this as a real government office.

## Known constraint — set expectations

Production is still on the default Azure Static Web Apps URL (`jolly-sky-0e3a2e310.7.azurestaticapps.net`), not a custom domain. On-page SEO work here is still worth doing (title/description tags, crawlability, structured data are prerequisites regardless), but ranking well for a human search like "PPDO portal" is unlikely without a real domain — Azure's auto-generated subdomains carry near-zero domain authority. A custom domain is a separate, non-code decision for Ralph to make later; this ticket doesn't block on it.

## Scope

* Per-page `Metadata` (Next.js Metadata API) for each public route: landing (`/`), `/about`, `/services`, `/contact`, `/login` — real title + description per page, not one generic string reused everywhere.
* Open Graph + Twitter card tags on the landing page (title, description, image — reuse an existing seal/logo asset).
* `robots.txt` — allow the public routes, disallow the authenticated portal tree.
* `sitemap.xml` listing the public, content-bearing routes (not `/login` — thin/duplicate content).
* JSON-LD structured data (GovernmentOrganization schema) on the landing page — name, address if available, logo.
* A `NEXT_PUBLIC_SITE_URL` env var (or equivalent) as the canonical base for sitemap/OG/canonical URLs, defaulting to the current Azure URL so this works today and is a one-line swap if a custom domain is added later.
* Canonical URL tags per page.

## Out of scope

* Buying/configuring a custom domain (Ralph's call, separate from this ticket)
* Submitting the sitemap to Google Search Console (manual step requiring Ralph's Google account — not something Claude Code can do)
* Any changes to authenticated/portal-only pages' metadata beyond making sure they're excluded from indexing

## Acceptance Criteria

- [ ] Each public page has its own accurate `<title>` and meta description
- [ ] Landing page has Open Graph + Twitter card tags with a real preview image
- [ ] `robots.txt` allows public routes, disallows the authenticated portal tree
- [ ] `sitemap.xml` lists public routes with correct absolute URLs
- [ ] Landing page has GovernmentOrganization JSON-LD structured data
- [ ] All URLs (sitemap, OG, canonical) derive from one configurable base URL, not hardcoded per file
