# RAL-234 — PWA groundwork: offline-honest /reconnecting, shared APP_VERSION, SWA config for service workers

The three AIP-independent items from the PWA feasibility study (`docs/PWA_Feasibility_Study.md` §12.1). All three ship in one branch — none of them changes shape once the v1.8.0 AIP rework requirements land.

Context doc: `docs/PWA_Feasibility_Study.md` (§6.3, §4.4, §7, and §12 for why these three specifically).

---

## 1. Offline honesty on `/reconnecting` (§6.3)

`/reconnecting` told **every** disconnected user *"The PPDO Portal server may be waking up after a period of inactivity"* — including a user whose own device has no connection, where that message blames the wrong party. It also burned both auto-retry attempts against a dead network interface before showing manual controls.

* `navigator.onLine === false` is reliable (no network interface), so it swaps the copy and stops consuming retry attempts.
* `navigator.onLine === true` is **not** reliable (an interface exists ≠ the internet is reachable), so it only ever softens the message — it never suppresses a retry.
* Regaining connectivity fires the `online` event, which resumes the retry automatically instead of leaving the user to find the button.
* Offline state shows a static indicator rather than a spinner — nothing is in flight while the device is disconnected.

Guarded against restarting a run once the page has already committed to navigating away (`phaseRef`), and reads `navigator` in an effect rather than during render, since this page is prerendered by the static export.

## 2. Consolidate `APP_VERSION` (§4.4)

The version string was hardcoded in three places — `Sidebar.tsx`, `login/page.tsx`, and as a bare string literal in `Footer.tsx` — with a standing warning in `CLAUDE.md` that all three must move together because they had already drifted.

All three now read `APP_VERSION` from the new `frontend/src/lib/version.ts`. A version bump becomes a one-line change. No visible change — still `v1.8.0` everywhere.

This is a prerequisite for the service-worker update prompt ("new version available — reload"), which needs one authoritative version to report.

## 3. SWA config for service workers (§7)

Three gaps in `frontend/staticwebapp.config.json`, each of which produces a confusing failure once a service worker exists. All are harmless before then:

* `mimeTypes` — Azure SWA has no built-in mapping for `.webmanifest` and may serve it as `application/octet-stream`. Added `application/manifest+json`.
* `Cache-Control: no-cache` **on** `/sw.js` — a CDN-cached service worker can pin users to an old build after a deploy. This is the standard recommendation for SW scripts.
* **Navigation-fallback excludes** — added `webp` and `webmanifest` so a missing asset 404s honestly instead of silently returning `index.html`. Hygiene, not a live bug: existing files were always served correctly, since the fallback only fires for paths that don't resolve.
