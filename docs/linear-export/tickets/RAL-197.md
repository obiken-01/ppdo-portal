# RAL-197 — Create PR: also accept the GSO PR PDF (not just xlsx) to prefill the form

Follow-up to [RAL-196](https://linear.app/ralphoksiprojects/issue/RAL-196/create-pr-import-the-gso-pr-export-to-prefill-the-form), which explicitly ruled PDF support out of scope ("reference-only, no upload feature needed"). Ralph reversed that 2026-07-31 after seeing the xlsx-only prefill working — see `docs/v1.7/GSO_PR_Import_Findings.md` for the updated findings, including a `pdfplumber` feasibility spike against the real sample PDF (confirmed: real vector/table PDF, not a scanned image — extracts cleanly).

## Problem

The GSO system's PDF export is the *signed* copy, and it has data the xlsx export never has: the signature block (Requested By, Position, Approved By, Approving Position). Today those four fields always have to be typed by hand, even after a GSO xlsx import. The PDF can fill them.

## Scope

1. `IPdfService`/`PdfService` (new, `PPDO.Infrastructure`, `UglyToad.PdfPig` package — MIT, no native deps) — `ParseGsoPRImport(Stream stream) : GsoPRImportRow` (same Domain return type `ExcelService.ParseGsoPRImport` already produces, so downstream logic is shared regardless of source format). Reconstructs table rows/columns from PdfPig word bounding boxes (cluster by Y for rows, bucket by X against the item table's own header-row column positions) — do NOT depend on PdfPig reading the PDF's vector line primitives, that's not reliable enough to build on. Header block (`Dept.:PPDO PR No.: ... Date.:...`) is one text blob per PDF table row, not separate cells — extract via label-anchored regex, not a lookup. Same hierarchy-line/account-code parsing rules as the xlsx (numbered `Item No.` = real item, `" - "` = coded Program/Project/Activity line, digits-only = Account No). Also extract RequestedBy/Position/ApprovedBy/ApprovingPosition from the signature block table (collapse embedded line breaks in Position values to a space); "Cash Availability" has no home in `CreatePRDto` — discard it, like Purpose.
2. Rename `ExcelParseException` → `ImportParseException` (still in `PPDO.Domain.Interfaces`, `IExcelService.cs`) — it's thrown by both parsers now, the old name is no longer accurate. Mechanical rename, no behavior change.
3. `GsoPRImportPreviewDto` gains `RequestedBy`, `Position`, `ApprovedBy`, `ApprovingPosition` (all nullable) — always null when the source was xlsx, populated when the source was PDF.
4. `PurchaseRequestService.PreviewGsoImportAsync` — detect format by sniffing the stream's magic bytes (`%PDF` vs the xlsx ZIP signature `PK\x03\x04`), never trust the client's declared Content-Type. Dispatch to `IExcelService.ParseGsoPRImport` or the new `IPdfService.ParseGsoPRImport` accordingly; everything downstream (account digits-only matching, StockNo/Items Master flagging) is unchanged and shared across both paths.
5. Frontend: the existing "Prefill from GSO Export" button/input's `accept` attribute gains `application/pdf,.pdf` alongside the xlsx MIME type — one button, not a second one. `handleGsoImport`'s header patch also carries `requestedBy`/`position`/`approvedBy`/`approvingPosition` from the response (falls back to the current field value when null, same `??` pattern already used for the other fields) — Division still can never be derived from either source and stays manual.

## Do NOT

Do not add a second, separate "Upload PDF" button — one upload action detects the format. Do not attempt to derive Division from the PDF — same reasoning as the xlsx (the document only ever has PPDO's own office/letterhead, never an internal division). Do not surface "Cash Availability" (the treasurer countersignature) anywhere — it has no corresponding field on the PR.
