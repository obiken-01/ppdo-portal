# RAL-225 — Create PR: Program/Project/Activity capped at 120 chars — should be unbounded like AIP

## Problem (reported live by Ralph, screenshot attached)

The Activity field on Create PR is a `textarea` (per CLAUDE.md's "Long text fields" convention), so typing is unrestricted client-side — but submitting rejects with a validation error once the text passes 120 characters, e.g.:

> `1000-000-1-01-010-001-023-007 - Posting and uploading financial documents of the province for the compliance to Full Disclosure Policy (FDP) and SGLG assessment`

(≈167 characters — a normal AIP-style activity description, not unusually long.)

## Root cause

`PurchaseRequestConfiguration.cs:57-65` caps `Program`/`Project`/`Activity` at `nvarchar(120)`, enforced again in `PurchaseRequestService.ValidateFieldLengths` (`PurchaseRequestService.cs:809-811` for create, `:825-827` for update) via `ValidateFieldLength(..., 120)`.

## Fix — base the length on AIP, per Ralph

The AIP module already stores the equivalent descriptive fields as unbounded free-text — `AipProgram.Name`, `AipProject.Name`, and `AipActivity.Name` are all `nvarchar(max)`, explicitly commented `// nvarchar(max) — AIP names are unbounded free-text` (`AipProgramConfiguration.cs:25-27`, `AipProjectConfiguration.cs:25-27`, `AipActivityConfiguration.cs:25-27`). PR's Program/Project/Activity are the same kind of field (often literally copy-pasted from an AIP activity description, as in the screenshot) and should follow the same convention instead of the arbitrary 120.

## Implementation

1. `backend/PPDO.Infrastructure/Data/Configurations/PurchaseRequestConfiguration.cs:57-65` — remove `.HasMaxLength(120)` from the `Program`/`Project`/`Activity` properties, matching the AIP comment style (`// nvarchar(max) — unbounded free-text, matches AipProgram/AipProject/AipActivity.Name`).
2. `backend/PPDO.Application/Services/PurchaseRequestService.cs` — remove the three `ValidateFieldLength("Program"/"Project"/"Activity", ..., 120)` lines from both `ValidateFieldLengths(CreatePRDto)` (809-811) and `ValidateFieldLengths(UpdatePRDto)` (825-827). Leave every other field length check untouched.
3. EF Core migration (naming convention: PascalCase description, e.g. `WidenPurchaseRequestProgramProjectActivity`) altering the three columns from `nvarchar(120)` to `nvarchar(max)` on `PurchaseRequests`.
4. Tests: extend `PurchaseRequestServiceTests.cs` with a case confirming a >120-char Program/Project/Activity value now succeeds (mirrors the AIP unbounded-field precedent) instead of the old `BadRequest`.

No frontend change needed — the textarea already allows unrestricted typing (CLAUDE.md's existing "Program, Project, Activity — textarea, min-height 44px, max-height 88px, resize vertical" convention); this was purely a backend-side rejection.

## Out of scope

Not touching any other PurchaseRequest field length (AccountTitle/AccountNo/etc.) — only Program/Project/Activity, since those are the only three with a documented AIP-side "unbounded free-text" precedent to align to.
