# RAL-148 — [bug] Recent Activity timestamps show browser-locale time, not Manila (RAL-147/RAL-136 area)

> 🌿 Working branch: `release/1.4.2` (off `main`). PR targets `release/1.4.2`. Child of epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> 📌 Frontend-only, small.

## Why

Ralph noticed on the Budget Planning Dashboard's "Recent Activity" panel that timestamps (e.g. "7/14/2026, 12:29:21 AM") don't read as Manila local time. Root cause: `frontend/src/app/(portal)/budget-planning/page.tsx:594` renders `new Date(entry.changedAt).toLocaleString()` with no `timeZone` option — this falls back to whatever timezone the *browser/OS* is set to, not Manila. CLAUDE.md's explicit rule is "Always use Manila time (UTC+8) for generated refs and timestamps," and the codebase already has an established pattern for this exact problem: `frontend/src/app/(portal)/dashboard/page.tsx:211-214` formats with `toLocaleDateString("en-PH", { timeZone: "Asia/Manila", ... })`.

## Scope

1. Update the Recent Activity timestamp render (`budget-planning/page.tsx:594`) to explicitly format with `timeZone: "Asia/Manila"` (and `locale: "en-PH"`, matching the dashboard page's existing pattern), instead of unqualified `toLocaleString()`.
2. Grep the frontend for any other unqualified `.toLocaleString()` / `.toLocaleDateString()` / `.toLocaleTimeString()` calls rendering a server-origin timestamp (audit log dates, created/updated dates, etc.) and apply the same fix — this bug class (relying on browser locale instead of pinning Manila) is easy to have recurred elsewhere.

## Out of scope

Backend timestamp storage/generation — `changedAt` etc. are already stored correctly as UTC per CLAUDE.md; this is a display-only fix.

## Commit message

```
fix(budget-planning): render Recent Activity timestamps in Manila time, not browser locale
```
