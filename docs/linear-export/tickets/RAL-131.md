# RAL-131 — WFP entry: Combined nature — dual procurement + non-procurement entry (Q2 resolution)

> 🌿 **Working branch: **`release/1.4.0`. PR targets it, **not **`main`. Child of epic [RAL-116](https://linear.app/ralphoksiprojects/issue/RAL-116/wfp-rework-epic-v14).
> 📌 Resolves the "Combined nature" half of Open Question Q2 (the other half, function bands, was resolved by [RAL-126](https://linear.app/ralphoksiprojects/issue/RAL-126/wfp-program-function-band-corestrategicsupport-activity-creation-flag)). Read `docs/v1.4/WFP_Rework_Requirements_Draft.md` §11 Q2 first.

## Why

The WFP entry wizard's amounts step currently renders a placeholder ("Combined entry — pending definition, contact PPDO...") whenever `nature = "Combined"`, per [RAL-123](https://linear.app/ralphoksiprojects/issue/RAL-123/wfp-entry-ui-context-picker-expenditure-wizard-shell)/124/125's decision to stub it out until Q2 was answered. The backend, however, already fully supports Combined: `WfpExpenditure` carries both `Periods` and `ProcurementItems` navigation collections simultaneously, `WfpExpenditureCalculator.MergePeriodAmounts` sums typed period amounts *and* Σ(qty×unitPrice×numberOfDays) from procurement items for the same period with no nature-specific branching, and `WfpExpenditureServiceTests`/`WfpExpenditureCalculatorTests` already cover this exact "Combined = both present, summed" behavior. The only gap is the frontend UI — there is no way to actually enter both procurement items and non-procurement period amounts under one Combined expenditure.

## Scope

* Replace the dashed-border placeholder in the amounts step (`ExpenditureWizard`, `nature === "Combined"` branch) with two toggle buttons below the nature selector — **"+ Add Procurement Items"** and **"+ Add Non-Procurement Amounts"**.
* Clicking a toggle reveals the corresponding *existing* component inline — `WfpProcurementItemTable` for procurement, `WfpFrequencyGrid` for non-procurement — reusing them unchanged with the same props they already receive in the single-nature branches. Both can be revealed/filled simultaneously (a Combined expenditure may carry both).
* Live combined total for the step's summary uses the already-existing `mergeWfpPeriodAndItemAmounts()` (`frontend/src/lib/wfp.ts`) — the client-side mirror of the backend's `MergePeriodAmounts`, so no new merge logic needs to be written.
* Reserve stays expenditure-level (shared `applyReserve`/`reserveAmount` state, rendered once above the amounts step) — no change to how reserve applies, just confirm it still reads correctly once both sections can hold data.
* Remove the "pending definition" caveat from `handleSave`'s Combined-nature toast now that real entry exists.
* No backend changes — `WfpExpenditureService.SaveExpenditureAsync` already persists both collections in one call for any nature.

## Acceptance Criteria

- [ ] Saving a Combined expenditure with both sections filled round-trips correctly (Total/Reserved/Net/Q1–Q4 match `WfpExpenditureCalculator`'s merged computation) — verify against the existing `Save_CombinedNature_MergesTypedPeriodAndProcurementItemsForSamePeriod` backend test, no backend change needed

- [ ] `docs/v1.4/WFP_Rework_Requirements_Draft.md` §11 Q2 marked resolved
