# RAL-261 — Expose the resolved landingPath on /auth/me

**V18-17** — plan: `docs/v1.8/Phase_Plan.md` §3.3. Depends on V18-16 ([RAL-251](https://linear.app/ralphoksiprojects/issue/RAL-251/landing-page-schema-resolution-chain-user-division-office-fallback)).

Resolve the landing page **server-side** and return it on `MeResponse` as `landingPath`, so there is exactly one authority for where a user goes.

The alternative — each client resolving the chain itself — puts the same rule in the login page, the portal layout, the sidebar and the PWA manifest. That is precisely how `APP_VERSION` drifted across three files, and this rule is more complex than a version string: it reads permissions.

**Scope:** call the V18-16 resolver in whatever builds `MeResponse`, return a path string, and keep the raw preference fields out of the response unless a page actually needs them (the `/account` selector will — see V18-20).

⚠️ `/auth/me` is fetched once and read everywhere via the shared context (`CLAUDE.md` — don't refetch per component). Adding a field here is free; adding a second endpoint would not be.

**Done when: **`GET /auth/me` returns a resolved, permission-checked path for every user, including one with no preference set anywhere.
