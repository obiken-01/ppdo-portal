# RAL-265 — Password reset backend — request + verify endpoints, throttle, audit

**V18-23** — plan: `docs/v1.8/Phase_Plan.md` §3.4 — the sub-decisions live inline in that same §3.4 table.

> ⚠️ **Corrected 2026-08-26.** This ticket previously cited `AIP_Requirements_Review.md` §2.6 (and §2.4 below). **That document does not exist in the repo and never has** — do not go looking for it. `docs/v1.8/Phase_Plan.md` §3.4 is the authoritative source.

Depends on V18-22 ([RAL-253](https://linear.app/ralphoksiprojects/issue/RAL-253/password-reset-schema-for-recovery-answer-mustchangepassword-attempt)).

Backend for Option B — self-service reset gated on the user's own recovery answer, no admin involvement and no email.

**Endpoints** (public, like `/auth/login` — no JWT):

1. `POST /api/auth/forgot-password` → given a username, return the **question key** to show.
2. `POST /api/auth/verify-recovery` → given username + answer, return a **randomly generated temporary password** shown once, set `MustChangePassword`, and write an audit entry.

**The rules that make this safe — each one matters:**

* ⚠️ **Identical response for a wrong answer and an unknown username.** Otherwise step 1 is a username-enumeration oracle.
* ⚠️ **The temporary password must be random, never a pattern.** A deterministic value (e.g. a date-derived string) is computable by anyone and turns this endpoint into account takeover. The flow's original proposal used a date-derived temporary password and was withdrawn for exactly this reason.
* **Lock reset attempts after 5 failures in an hour**, or the answer is brute-forceable.
* ⚠️ **Normalize through **`RecoveryAnswerNormalizer` (shipped in [RAL-253](https://linear.app/ralphoksiprojects/issue/RAL-253/password-reset-schema-for-recovery-answer-mustchangepassword-attempt), `PPDO.Application/Common/`). Do **not** reimplement trimming/lowercasing here — [RAL-266](https://linear.app/ralphoksiprojects/issue/RAL-266/force-recovery-answer-setup-at-next-login-rollout-over-existing) sets the answer through that same function, and any divergence between setting and verifying silently locks users out of their own answer.
* Answer matching is **case-insensitive and trimmed** — "Manila " vs "manila" is a support call, not a security boundary.
* Every reset writes to the audit log (V18-07).

TDD: service-level tests first — wrong answer, unknown user, lockout, successful reset.
